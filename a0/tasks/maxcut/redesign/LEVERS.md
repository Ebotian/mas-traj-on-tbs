# `redesign/LEVERS.md` — the levers that could restore headroom, measured

Owner: the redesign/measurement workstream. Authority: `../INTERFACE.md` (v1.1)
and the assignment naming this directory. **Measurement only**: the frozen
suite, the gate thresholds, `references/targets.json`, the candidate set `C*(T1)`
and every upstream runtime are untouched. Every interpretation this directory had
to make is in `DEVIATIONS.md`.

Zero model spend. Everything below is local CPU, reproducible with one command:

```bash
cd a0/tasks/maxcut/redesign && sh gen/run_all.sh      # resumable; see §7
```

The question this answers: the pre-registered admissibility gate failed on the
**headroom** half (dev median `ρ = 0.1588`, need `≥ 0.30`, 0/4 families), while
the improvement half passed comfortably (`Δ = 0.2479 ≫ 0.03`, 4/4). A
one-flip local search injected from a random start already reaches 94.3 % of the
reference target and closes 82.6 % of the baseline→target gap. Which change would
restore measurable headroom, and what does each cost?

**Answer in one line.** The **weaker-but-published positive control (L2)** works,
on the *existing* suite, with no re-freezing: e.g. `one_exchange` bounded to
**10 improving swaps** gives `Δ = 0.1166` (3.9× the bar) **and** median
`ρ = 0.6156` (2.05× the bar), passing both gates in **4/4 families**. The
**instance-size lever (L1) is the one I would not recommend**: `ρ` is flat (and
if anything falling) in `n` for `ER:p080`, and for `RR:d4` it only crawls from
`0.29` to `0.32` at 8× the size, at the price of re-freezing the suite, the
targets, the timeout calibration and `C*(T1)` — and it forces a PC change anyway,
because at `n ≥ 512` the frozen positive control itself exceeds `τ = 30 s`.

## 1. The gate's quantities, verbatim

From `../gates/gate_config.json` (frozen; its sha256 is stamped in every verdict):

| quantity | definition | threshold |
|---|---|---|
| `Δ_i` | `(p_i − b_i) / |E_i|`, exact rational | overall mean ≥ 0.03 **and** ≥ 0.02 in ≥ 3 of 4 families |
| `ρ_i` | `(T_i − p_i) / (T_i − b_i)`, exact rational | global median ≥ 0.30 **and** ≥ 0.30 in ≥ 3 of 4 families |
| saturation NO-GO | median `(T_i − b_i)/T_i` | veto below 0.05 |

`T_i = OPT_i` when SCIP certifies, else `R_i` (the ensemble incumbent, a lower
bound on the optimum). All reductions below use `fractions.Fraction`; every
decimal is a display field. Median of an even count = midpoint of the two central
order statistics (the frozen definition).

## 2. L2 — weaker, still published positive controls (measured on the frozen dev suite)

**Sample.** The 24 frozen dev graphs, read-only. `b_i` from the frozen E* Outcomes
in `../gates/values/dev.baseline.json`; `T_i` from the existing
`../references/targets.json`. Each candidate is run through `../e_star.py
evaluate` at the pre-registered `θ = (seed 1337, τ 30 s)`; 24 graphs × 8 variants
= 192 Outcomes, all `ok`, all `determinism.identical: true`.

Candidates (`redesign/candidates/`, generated by `gen/make_l2_candidates.py`):

* `exchange_opt` — the pinned `one_exchange` to local optimum (the current PC);
* `exchange_k{K}` — the same descent truncated after `K` accepted improving swaps;
* `greedy` — classic greedy construction in a seeded random node order (L2c);
* `rand_part` — `nx.approximation.randomized_partitioning` (L2d, the Δ floor).

Reading it:

* **The gate is satisfiable without touching the suite.** `exchange_k10` clears
  both halves with room: `Δ` is 3.9× the required mean and `ρ` is 2.05× the
  required median, in all four families. `k5` and `k25` also clear it; of the
  tested truncations `k25` is the strongest that still passes, and its binding
  family is `BA` (`ρ = 0.2631 < 0.30`), so it passes on the 3-of-4 rule rather
  than unanimously.
* **Truncation is a real weakening, not a trick.** `k10` still moves the baseline
  by 11.7 % of the instance's edges and closes 38.4 % of the baseline→target gap;
  it is a normal, honest local search that just stops earlier. `k1` shows the
  other failure mode: one improving swap is too weak for `Δ`.
* **A published greedy construction does *not* rescue the gate.** `greedy` passes
  `Δ` (0.2287, 4/4) yet fails `ρ` in every family (median 0.2399). It is nearly as
  strong as one exchange by the objective, so it leaves even *less* relative
  headroom. "Use a weaker published heuristic" only works if the heuristic is
  actually weaker.
* **The floor behaves.** `rand_part` is a random cut, so `Δ ≈ 0` and it fails —
  and its `ρ > 1` merely reflects `p_i < b_i`, i.e. it sometimes does worse than
  the baseline. Nothing here folds a non-improving run into a pass.

### 3.2 The verdict for L1

* **`ER:p080`: `ρ` is flat in `n`, and if anything declines.**
  `0.1768 → 0.1483 → 0.1298 → 0.1338` over an 8× size increase. It never
  approaches 0.30. The upper end of the rigorous bracket rises only to `0.3244`
  (median), i.e. even the most optimistic reading of an uncertified incumbent
  leaves `ER:p080` at the bar, not above it. This is the answer the assignment
  asked for: **flat, so flat.**
* **`RR:d4`: a marginal, non-monotone rise.** `0.2901 → 0.2586 → 0.2907 → 0.3189`.
  It dips at `n = 256`, and only at `n = 1024` (4 graphs) does the cell median
  clear 0.30 — by 0.019. At `n = 128` the frozen suite's own `RR:d4` pair gives
  `0.2826 / 0.2917` (median 0.2871), consistent with the fresh `0.2901`, so the
  whole effect is `≈ 0.03` of `ρ` for a 8× increase in `n`.
* **Sample size is the honest caveat.** For `ER:p080` at `n = 128`, the frozen
  dev pair gives median `ρ = 0.2736` (0.2558, 0.2914) while the fresh pair gives
  `0.1768` (0.1353, 0.2183) — a **0.097** swing on the *same* generator, density
  and `n`. Instance-level noise is therefore comparable to the entire effect the
  lever is supposed to buy. The `n ≥ 256` cells use 4 graphs to reduce this, but
  the L1 verdict should be read as "no large effect", not "an effect of size x".
* **The trap, stated.** 26 of the 28 targets are uncertified, so `T_i` is a
  feasible value and a lower bound on the optimum. With `p_i > b_i` (true
  throughout), `ρ(T)` is increasing in `T`, so the reported `ρ(R)` is a **lower
  bound** on the true headroom and `ρ(U)` an upper bound; both are reported per
  graph. `U_i` is not tight — where a true optimum is known (`RR:d4`, `n = 128`,
  `OPT = 218/220`) the project's `U` is `230.7/232.4`, i.e. `≈ 5.8 %` above the
  optimum, so `ρ(U)` overstates the headroom by roughly that much.
* **The 4× top-up barely moves `R`.** On the 16 graphs with `n ≥ 512`, the 120 s
  runs beat the 30 s incumbent on **2** graphs, by 2 and 3 edges (0.008 % and
  0.012 %). So the reference is not badly under-trained, and the `ρ(R)` values are
  not artifacts of an under-budgeted ensemble — but they are still lower bounds.
* **The frozen PC does not survive large `n`.** At the frozen `θ = (1337, 30 s)`,
  the pinned `one_exchange` **times out** on all four `ER:p080` graphs at
  `n = 512` and `n = 1024`, and on 3 of 4 `RR:d4` graphs at `n = 1024`
  (`instances/logs`-adjacent Outcomes in `out/l1_outcomes/pc/`). The pin recomputes
  `cut_size` over all edges for every candidate swap every round
  (`O(rounds·n·m)`), so its cost grows faster than the instance. `p_i` for those
  cells is therefore taken from the verified-equivalent efficient transliteration
  (`DEVIATIONS.md` D-RD-2): `gen/run_l2.py` asserts equality on all 24 dev graphs,
  and `gen/l1_eval.py` asserts it on every L1 graph where the pin completes.
  **Consequence:** L1 is not a standalone lever — it drags in a PC change too.

## 4. L3 — family mix: which lever helps which family

| lever | ER | RR | BA | Planted | source |
|---|---|---|---|---|---|
| L2 `exchange_k10` (Δ / ρ) | pass 0.1068 / 0.6219 | pass 0.1313 / 0.6345 | pass 0.1263 / 0.5704 | pass 0.1020 / 0.6051 | L2, all four families |
| L2 `exchange_k25` | pass 0.1904 / 0.3275 | pass 0.2441 / 0.3476 | Δ pass 0.2085 / **ρ fail 0.2631** | pass 0.1765 / 0.3224 | L2; `BA` is the binding family |
| L2 `greedy` | Δ pass / **ρ fail** | Δ pass / **ρ fail** | Δ pass / **ρ fail** | Δ pass / **ρ fail** | L2; no family helps |
| L2 `rand_part` | **Δ fail 4/4** | | | | L2 |
| L1 size (`ER:p080`) | **ρ fail at every `n`** | — | not sampled | not sampled | L1 |
| L1 size (`RR:d4`) | — | **ρ passes only at `n = 1024` (0.3189)** | not sampled | not sampled | L1 |

So:

* The **bounded-exchange lever is family-uniform**: `k10` passes both gates in
  all four families, not just on average. If a stronger PC is wanted, `k25` is
  the largest of the tested truncations that still passes, and it fails only on
  `BA`.
* The **size lever is family-specific and mostly negative**: it does nothing for
  `ER:p080` at any `n`, and helps `RR:d4` only at `n = 1024`. It was measured on
  the two strata the gate named, so it says **nothing** about `BA` or `Planted`
  — an inference about those families would be unsupported by this sample.
* `greedy`'s failure is uniform, which is the useful negative: no family is
  rescued by swapping one_exchange for a greedy construction.

A threshold revision (e.g. lowering `ρ_min`) is the coordinator's option and is
**out of scope here**; it is a contract change, not a measurement, and this
directory did not evaluate or advocate it.

## 5. The decision table

| | L1 — raise `n` (re-draw strata) | L2 — weaker positive control | L3 — family re-mix |
|---|---|---|---|
| what changes | suite instances; `R_i`/`U_i`; §7 `τ` calibration; possibly `C*(T1)` expected rows | the contract's definition of `PC_i` (truncate the descent) | nothing, by itself |
| measured `ρ` effect | `ER:p080` 0.177→0.134 (none); `RR:d4` 0.290→0.319 (marginal, only at 1024) | median `ρ` 0.159→0.616 at `k10` | — (qualifier) |
| measured `Δ` effect | still passes everywhere (0.070–0.289) | 0.248→0.117 at `k10` (3.9× the bar) | — |
| families | `RR:d4` only; `BA`/`Planted` not sampled | 4/4 at `k10`; `BA` binds at `k25` | — |
| must be re-frozen | suite files + `manifest.json`, `references/targets.json`, `τ` (calibration set), `C*(T1)` expected — and the PC, since the pin times out at `n ≥ 512` | the PC candidate + its identity; re-run the gate (24 graphs, milliseconds) | nothing |
| cost | full reference pipeline per graph (30 min ensemble for 16 graphs here + 120 s SCIP/graph + minutes of UB at `n = 1024`) | minutes of local CPU | — |
| verdict | **works only for `RR:d4`, marginally, at high cost** | **works, uniformly, cheaply, on the existing suite** | lets you see where a lever bites |

**Why the numbers make L2 the cheap answer.** `k10`'s `ρ` median (0.6156) is
2.05× the bar and its `Δ` (0.1166) is 3.9× the bar; both halves pass unanimously
across families, and the only artifact that changes is the definition of the
positive control — no instance, no target, no timeout, no `C*(T1)` row. By
contrast, the *strongest* thing L1 can show is a `ρ` of 0.3189 in one stratum at
`n = 1024`, at 8× the instance size, with 26/28 targets uncertified.

## 6. The lever I would not recommend, and why

**I would not recommend L1 (raise `n` / re-draw strata at larger size).**

1. **It does not move the binding quantity for the strata that fail worst.**
   `ER:p080`'s median `ρ` goes `0.1768 → 0.1483 → 0.1298 → 0.1338` for
   `n = 128 → 1024` (table §3.1) — flat, indeed slightly negative. Even the upper
   end of the rigorous `U`-bracket only reaches 0.3244, i.e. the bar, not above it.
2. **Its one apparent success is marginal and within noise.** `RR:d4` reaches
   0.3189 at `n = 1024` (4 graphs), 0.019 over the bar, after dipping to 0.2586 at
   `n = 256`. On the same generator at `n = 128`, two independent graph pairs give
   `ER:p080` medians of 0.2736 (frozen) and 0.1768 (fresh) — a 0.097 swing, so the
   `RR:d4` "gain" of ≈0.03 is not separable from instance noise at this sample size.
3. **It is the most expensive lever.** Changing instances re-freezes
   `suite/**` + `manifest.json`, `references/targets.json` (`R_i` must be re-run,
   and at `n ≥ 256` SCIP certifies almost nothing, so `OPT_i` becomes `null` and
   `ρ` becomes an estimate), the §7 timeout calibration (the calibration set would
   have to be re-drawn), and possibly `C*(T1)`'s `conformance.expected.json`.
4. **It does not even stand alone.** At `n ≥ 512` the pinned `one_exchange`
   exceeds `τ = 30 s` (measured: all four `ER:p080` graphs at 512 and 1024; 3 of 4
   `RR:d4` at 1024). So any large-`n` suite must also change the positive control —
   at which point L2 is available directly, and is cheaper and family-uniform.
5. **Net:** the maximal L1 effect on the worst stratum is ≈ 0.03 of `ρ` at 8× the
   size and a suite-wide re-freeze; the L2 effect is +0.46 of `ρ` at no re-freeze.
   The evidence does not support choosing L1.

**What I would point the coordinator at instead.** L2, with `K = 10` as the
measured point of a comfortable pass (both gates, all four families), and `K = 25`
if a stronger PC is preferred (passes on 3/4 families, `BA` binding). The choice
of `K` is a contract decision, not a measurement; this directory only supplies the
curve. If the coordinator wants *both* more headroom *and* a harder task, L1 is
not the way to get it — a stronger reference target would lower `ρ` further, and
L1's measured effect is in the wrong direction for `ER:p080`.

## 8. What could not be verified

* **`ρ` is a lower bound for 26 of 28 L1 graphs.** SCIP certified only `RR:d4` at
  `n = 128` (2/28). For the rest, `OPT_i = null`, `T_i = R_i`, and the true
  headroom lies in the reported `[ρ(R), ρ(U)]` bracket. The bracket's upper end is
  loose: at the one graph where `OPT` is known the project's `U` sits ≈ 5.8 %
  above it.
* **The L1 per-cell numbers are estimates from 2–4 graphs.** The frozen-vs-fresh
  `n = 128` `ER:p080` comparison (§3.2) is the measured size of that noise
  (≈ 0.10 of `ρ`). An L1 conclusion finer than "no large effect" / "a marginal
  effect for `RR:d4`" is not supported by this sample.
* **`BA` and `Planted` were not sampled in L1.** The size lever's family mix for
  those two families is unmeasured, and this document says so rather than
  generalising.
* **The `U` bounds at `n = 1024` use a reduced iteration budget** (400 SDP-dual
  iterations vs the project's 4000; `DEVIATIONS.md` D-RD-6). Reduced iterations
  weaken the bracket; they do not invalidate it.
* **The frozen candidates are currently un-evaluable by E*** (D-RD-1): their
  executable bit was added after the gate ran, and `stage_candidate` does not
  preserve it, so `e_star.py evaluate --candidate positive_control/pc …` returns
  `candidate_entry_failed` today. This directory used byte-identical mode-`0644`
  mirrors with the frozen `candidate_source_sha256`, but it did not fix E* (not
  this workstream's artifact). If the coordinator wants `gates/gate_runner.py
  --force` to work again, that is the thing to fix.
