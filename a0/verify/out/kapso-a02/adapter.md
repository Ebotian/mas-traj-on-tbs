## `EID_r -> EID*` mapping (contract §5.2)

```
EID_r  = manifest_fingerprint(kapso_evaluation/)       # KAPSO native (evaluation_integrity.py:112-119)
       = sha256(json.dumps({relpath: sha256(file)}, sort_keys=True, separators=(",",":")))
       = manifest:<value recorded as eid_r.value on every trace event>
```

The registered tree is two files, generated by the adapter from `EID*` alone:

| file | role |
|---|---|
| `kapso_eval.py` | the KAPSO-side execution of `E*`; prints exactly one `KAPSO_EVAL_MANIFEST {...}` line |
| `a0_locator.json` | `EID*`'s `EvaluatorSource` records (per-file sha256), the five component digests, canonical `theta_E`, `MetricDefinition`, the frozen `C*` member digests, the pinned `E*` interpreter, a default state root |

The state root is *not* part of the tree: it is passed per run through
`A0_KAPSO_EVAL_STATE_ROOT`, so `EID_r` is a function of the frozen `EID*` and two adapter
source files only — and indeed the same `EID_r` appears in both the A0.1 and A0.2 traces of
one run and across runs (`runs/a0-01/a01` and `runs/a0-01/a02`).

Two legs make the mapping recomputable **and enforced**, not merely declared:

1. **Identity leg.** On *every* invocation `kapso_eval.py` re-hashes `e_star.py` and
   `e_star_child.py` and compares them with the `EvaluatorSource` records carried in the
   locator, which came from `EID*`. A mismatch aborts with exit 3 and no manifest line.
   Falsified in-run: `conformance.json.controls.e_star_source_drift` (one digest corrupted →
   exit 3, no score) versus `controls.e_star_source_intact` (exit 0, score present).
2. **Tree leg.** `sync_registered_evaluation` overwrites the branch's `kapso_evaluation/`
   with the registered head before every frame run (`registered_evaluation.py:193-200`), and
   `conformance.json` records, per candidate, the fingerprint of the branch's *committed*
   tree — all 14 equal the registered evaluator id.

**KAPSO's manifest carries no evaluator field.** `parse_manifest_line`
(`maintainer.py:64-83`) requires `fidelity, fraction, seed, items, total_items` and `score` is
read separately, so the A01.4 assertion is over the **triple** `(fidelity, fraction, seed)`.
A test written from the protocol's wording ("manifest triple
`(evaluator, fidelity, fraction, seed)`") would look for a field that does not exist:
`conformance.json` records, per candidate,
`manifest_field_check.kapsos_contract_keys` = `[fidelity, fraction, items, score, seed,
total_items]` with `evaluator_identity_field_in_kapsos_keys = false`, and lists the adapter's
own extra keys separately in `adapter_extra_keys`. The identity leg (A01.5) is asserted out of
band: the recorded attempts' `evaluator_id` and the executed tree's fingerprint both equal the
registry head's fingerprint.

## Evaluator invocation (KAPSO path)

KAPSO composes it itself — `evaluation_command()` (`maintainer.py:56-61`):

```
python kapso_evaluation/kapso_eval.py --fidelity full --fraction 1.0 --seed 1337
```

run with `cwd` = the tree being measured (session folder for a session, branch worktree for a
frame run, workspace root for the registration calibration). `python` is resolved through
`PATH` **by KAPSO's own contract**; the adapter pins that `PATH` to its 3.12 venv and records
the pin in `closure.json`. `E*` itself is invoked by the wrapper with the EID*-pinned
interpreter and absolute `--candidate` / `--out` / `--state-dir`, so no path is ever resolved
against a worktree (a relative state root there would have written into a candidate tree — the
adapter was fixed to resolve every path absolutely, and the run state now lives below
`--run-dir`).

### Verdicts are reproduced, never collapsed

`kapso_eval.py` prints the manifest line **without** a `score` key when `E*` returns
`invalid` / `error`, and exits 2 / 3. KAPSO's own consumption path then records **no**
measurement: `manifest_of_record` returns None exactly for this shape
(`registered_evaluation.py:100-102`), `execute_registered_evaluation` returns None on a
non-zero exit (:256-261), and `record_evaluation_attempt` is skipped because
`node.score is None` (:137-143). Evidence, per candidate, in
`a01/conformance.json.candidates[*]`: `registered_channel.score = null`,
`frame_run.score = null`, `frame_run.attempt_count = 0`, `reference.objective = null` — while
the *verdict* (`ok` / `invalid` / `error`) and the exit code match `E*` exactly. No numeric
zero is ever substituted for a candidate `E*` refused.

## Candidate-set gate (the `allow_unfrozen_candidate` decision)

The registered wrapper refuses any `solution.py` whose sha256 is not a member of the frozen `C*`
(the `DataManifest` half of `EID*`). The closure sentinel — a candidate that opens a TCP
connection — is deliberately outside `C*`, so *something* has to admit it.

**Decision: the capability is a property of the tree, never of the environment.** The wrapper
reads `a0_locator.json: allow_unfrozen_candidate`; that file is part of the registered tree and
therefore part of `EID_r`, and `sync_registered_evaluation` overwrites the frame-run worktree's
`kapso_evaluation/` from the registered head before every evaluation
(`registered_evaluation.py:193-200`). A session that sets an environment variable, edits the
locator, or swaps the tree therefore cannot open the gate: the first has no effect, the second
and third break `enforce_evaluation_integrity` and void the measurement.

The earlier revision read `A0_KAPSO_ALLOW_UNFROZEN_CANDIDATE=1` from the environment. That was
the wrong shape and a real session proved it: it read `kapso_evaluation/kapso_eval.py`, found
the variable, and used it to score a candidate of its own choosing (attempt 1 in
`runs/e2e-attempts/`). Only the closure probe needs the capability, and only for a scratch tree
it builds itself and never registers.

Bounds on what remains:

* the flag defaults to `False` and the adapter never sets it for a registered tree
  (`conformance.json.controls.candidate_set_gate.registered_tree_locator_flag == false`);
* with the flag off, a session-style environment override produces **exit 3 and no manifest**
  (measured, on both the registered tree and a scratch tree);
* with the flag on, the manifest records `candidate_identity.in_frozen_set: false`, so an
  out-of-set measurement is self-identifying in any log that keeps the manifest line.
