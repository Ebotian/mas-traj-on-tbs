# A0.2 / A0.1 / A−1 acceptance checklist

Concrete, checkable assertions only. Each item names the artefact that carries the
evidence, the exact comparison, and the source citation that fixes the expected value.
Derivations behind every number: `DERIVATIONS.md`; machine-readable values:
`expected_values.json` (generated by `simulate.py --emit-json`).

Legend: **[F]** = freezable config condition that must be recorded with the result.
**[E]** = evidence artefact. **Trap** = a way this item can pass while being wrong.

Path convention. Runtime citations are relative to each runtime's checkout root — EvE
`/tmp/eve/src/scaling_evolve/`, KAPSO `/home/ebt/kapso_ck/kapso/src/kapso/`, Loreley
`/tmp/lor/loreley/` — matching `a0/contract/SPEC.md` §9. `DERIVATIONS.md` §2 spells KAPSO
paths with the `src/kapso/` prefix; both denote the same files. Paths beginning `a0/` are
workspace-relative.

Result vocabulary. Every A0.2 observation carries exactly one outcome label, and the label
counts affect the run's failure accounting (§4.4): `pass`, `mechanism_mismatch` (the runtime
did not consume scores the way it claims), `resolve_failed` (the run could not produce the
observation at all), `comprehension_failed` (the observation is unreadable/ambiguous),
`infra_failed`. `mechanism_mismatch` and `resolve_failed` are counted separately and never
merged.

## 2. A0.1 — the evaluator is faithfully executed

For every runtime `r` and every candidate `c` in the frozen set `C*`:

| id | assertion | how to check |
| --- | --- | --- |
| A01.1 | `E_r(c; theta_E) = E*(c; theta_E) ± epsilon` with `epsilon` stated before the run (not after seeing the numbers) | compare the runtime's recorded score with an independent run of the reference evaluator on the same candidate; the reference evaluator is the one frozen in A−1, executed outside any runtime |
| A01.2 | the comparison is over the **scalar projection** `F_r`, and the fold from `E*`'s multi-field output to that scalar is declared and frozen (hard constraint #3: `E*` may be multi-field; scalarization is the adapter's job) | adapter's declared `F_r` + the raw multi-field `E*` output in the trace |
| A01.3 | `epsilon` covers every source of evaluator nondeterminism that was actually observed; if repeats of the *same* candidate differ by more than `epsilon`, `epsilon` is re-frozen or the candidate is dropped, and the drop is recorded | ≥3 repeat evaluations of one candidate; report min/max/spread |

**KAPSO manifest-triple invariant (mandatory, separately reported).**

| id | assertion |
| --- | --- |
| A01.4 | For every attempt that produced a counted score, the printed `KAPSO_EVAL_MANIFEST` line's `(fidelity, fraction, seed)` equals the *granted* decision's `(eval_fidelity, eval_fraction, registered_subsample_seed)` — exact string match for fidelity, `|Δfraction| ≤ 1e-9`, exact int for seed |
| A01.5 | The evaluator identity leg is checked **separately** and out of band: the head's `evaluator_id` (SHA-256 over the sorted `kapso_evaluation/` file manifest) equals the `EID*`-derived child id, and the tree actually executed is the registered head's (re-sync happens before every frame run) |
| A01.6 | `mode != off` **and** any mismatch in A01.4 or A01.5 ⇒ **that round is an A0.1 failure**; it is not silently dropped and not counted as a pass |

**Trap A01-T1 (the manifestation the protocol warns about, but stronger than stated):** a
class mismatch only *prints* and returns `None`; the node keeps whatever score the session
reported. "The runtime reported no mechanical score of record" is **not** evidence the
invariant held. Assert A01.4 by reading the manifest line and the grant from the trace and
comparing them yourself. Also note the check uses the **last** manifest line in the session
output, so a session that prints several is only checked at the end.

**Trap A01-T2:** the protocol phrases the invariant as a four-element "manifest triple"
`(evaluator, fidelity, fraction, seed)`. The manifest line has **no evaluator field**
(required keys: `fidelity, fraction, seed, items, total_items`, plus `score`). A test written
from the protocol's wording will look for a field that does not exist. See
`DERIVATIONS.md` §2.3.

**Trap A01-T3:** `full_eval_score` (used for the deliverable ranking) averages all
`fidelity == "full"` attempts and ignores fraction and seed, while `project_score` requires
an exact class match. If the two disagree for a candidate, the run has two "best" answers;
report it as `mechanism_mismatch` rather than picking one.

## 3. A0.2 — score → search contract, per runtime

### 3.1 EvE

**[F]** `loop.sampling.working_optimizer = RankSoftmaxSampler(temperature=1.0,
replacement_mode=auto)`; `loop.sampling.solver_examples =
RankExponentialSumSampler(features.score={weight:1.0, temperature:1.0},
replacement_mode=no_replacement)`; `loop.n_solver_examples_phase2 = 4`;
`loop.n_workers_phase2 = 2`; the population size `N` at sampling time; the seed solver's
presence; the exact score payload shape written by the evaluator. (All from
`configs/eve/loop/default.yaml`.)

| id | assertion | expected value |
| --- | --- | --- |
| A02-E1 | Unit-level frequency test on **the runtime's own sampler class**: population = `{c1, c2}` with `E(c1) > E(c2)`, `num = 1`, `T = 1`, `no_replacement`; statistic = fraction of draws whose position 0 is `c1` | `p = 1/(1+e^-1) = 0.7310586`; reject H0 at the n from §3.4 |
| A02-E2 | Same, `num = 4`: position 0 | `p = 0.7310586` (the first draw always uses the full weight vector) |
| A02-E3 | Same, `num = 4`: **inclusion** of `c1` in the returned set | `p = 1` (exactly; `num` is capped at `N = 2`). This is a *must-pass-by-construction* assertion, not a frequency test — asserting a frequency here has zero power |
| A02-E4 | Direction/shape: the score consumed is `scalar(score) = score["score"]`, ranks are best-first, and the probability is **invariant under the score gap** (a 0.001 gap and a 10^6 gap give the same p) | p unchanged across gaps; a test that expects gap sensitivity is mis-specified |
| A02-E5 | The `solver_examples` site is exercised through the runtime: the position-0 entry of the rendered `solver_examples` block in the Phase-2 workspace README is the higher-scoring candidate at the A02-E2 rate | same n as A02-E2 |
| A02-E6 | **Control:** the `solver_prefill` / `solver/` overlay is score-independent — `P(first == c1) = 1/N` (0.5 at N=2, 0.25 at N=4) and is unchanged when the scores are permuted while the candidate set is fixed | 0.5 / 0.25; permutation-invariant |
| A02-E7 | If the population is frozen with `N = 4` instead of 2, position 0 must be `1/(1+e^-1+e^-2+e^-3) = 0.6439143`, not 0.7310586 (this is the population-size-sensitive alternative) | 0.6439143 |
| A02-E8 | Second and later draws are **not** re-ranked: given rank-1 drawn first, `P(rank-0 next)` is `1/(1+e^-2)` at `N=3` and `1/(1+e^-2+e^-3)` at `N=4` — a re-ranking implementation returns 0.8807971 for both | 0.8807971 / 0.8437947 |
| A02-E9 | `optimizer_examples` and `produced_optimizers` are out of scope unless the optimizer population at sampling time is frozen too; if exercised, their num is 3 and 2 respectively and the exclusion rule must be recorded | — |

**Trap A02-E-T1 (false green):** the `solver_prefill` segment looks like a score-consuming
sampler in the workspace but is a `UniformSampler` that discards scores. Any "test" that
reads `solver/` after prefill will report ≈1/N and can be mistaken for the 0.731 result if
the population is small or `N` is mis-stated. A02-E6 exists to detect this.

**Trap A02-E-T2:** asserting on the *set* returned by the `n = 4` config instead of the
*order*. With `N ≤ 4` the set is always the whole population, so the set statistic is 1 for
any implementation, correct or not.

**Trap A02-E-T3:** the run-level RNG is unseeded, so a single observation proves nothing;
and the frequency must be counted per **iteration** (sampling happens once per iteration and
is shared by all workers), not per worker, or `n` is inflated by the worker count.

### 3.3 Loreley

**[F]** single island; single objective `composite_score` (`direction=max`);
`mapelites_pareto_epsilon = 1e-9`; `mapelites_pareto_front_max_size`; `admission_policy =
"pareto"`; a **strict** score gap `|Δ| > epsilon`; the two candidates' `measures` chosen to
land in the intended cells; `mapelites_sampler_seed` recorded.

| id | assertion |
| --- | --- |
| A02-L1 | **Positive, same cell:** `c1` admitted with `E(c1) > E(c2) + ε` and matching `measures` ⇒ `retained is True`, `removed_commit_hashes == (c2,)`, `archive.front(cell) == (c1,)`, `c2 ∉ archive.records()`, and the persisted cell row now names `c1` |
| A02-L2 | Candidate admissions are applied **one at a time**: `removed_commit_hashes` is only populated for a single-candidate batch |
| A02-L3 | **Negative control, cross cell:** `c1` with a higher score but `measures` in another cell ⇒ `retained is True`, `removed_commit_hashes == ()`, and the other cell's front is byte-identical before and after (`c2` still a member) |
| A02-L4 | **Negative control, no global argmax:** a strictly *worse* candidate admitted into a free cell ⇒ `retained is True` and it stays a member alongside the higher-scoring one |
| A02-L5 | **Report branch:** the best-primary-commit query (archive-membership join, primary metric, tie-break by `commit_hash` ascending) returns `c1` after A02-L1. Do **not** use this as the cross-cell control (the report is a global max over *retained* members) |
| A02-L6 | **ε guard:** if `|Δ| ≤ ε` the outcome is decided by `commit_hash` order, not by score ⇒ the test must assert `|Δ| > ε` or it passes for the wrong reason |
| A02-L7 | **Sampling is score-independent:** with a frozen archive, the base-commit pick frequency is uniform per cell (binomial CI over ≥10^4 draws with a fixed sampler seed) and **unchanged** when the front members' scores are permuted while `measures` are fixed |
| A02-L8 | **Truncation:** a front exceeding `max_front_size` is cut by crowding distance, so a newcomer can be dropped even with the highest primary objective. This requires a multi-objective configuration; under the default single objective every cell front has exactly one member and the archive is the per-cell argmax — record which regime the run is in |

**Trap A02-L-T1:** assuming "no global-argmax guarantee" holds under the default
single-objective contract. It does not: with one objective the archive is the per-cell
argmax and the report is the global argmax of everything evaluated. Designing the negative
control as "a globally best candidate fails to be retained" will fail against correct code.

### 3.4 Required trial counts and decision rule (EvE)

Statistic: `Z = (p̂ - p0) / sqrt(p0(1-p0)/n)` against `p0 = 0.7310586`, with the exact
binomial interval used for the exact counts. `alpha = 0.05`, power = 0.90. Rejection is
**two-sided by default**; a one-sided test is only legitimate if the direction of the
expected deviation was pre-registered (it was, here: "weaker score dependence than
claimed"), and the one-sided counts are given for that case.

Order statistic (H0 = 0.7310586):

| alternative | p_alt | n (2-sided, normal) | n (1-sided, normal) | n (exact, 2-sided) |
| --- | --- | --- | --- | --- |
| uniform / no score dependence, N=2 | 0.5 | 43 | 36 | 46 |
| uniform over N=4 | 0.25 | 9 | 8 | 12 |
| wrong population size, N=4, num=4 | 0.6439143 | 290 | 238 | 295 |
| wrong population size, N=3, num=4 | 0.6652409 | 502 | 411 | 515 |
| T mis-set to 0.5 | 0.8807971 | 74 | 59 | 74 |
| T mis-set to 2.0 | 0.6224593 | 189 | 155 | 194 |

**Decision rule:** run at least **515** independent iterations if the test must be able to
reject *any* of these alternatives at 5%/90% two-sided (the N=3 alternative is the binding
one). If only the "no score dependence" alternative is pre-registered as the primary
alternative, **46** iterations suffice and the rest are secondary — state which one is
primary before running. Count iterations, not workers.

Inclusion statistic (for an auditor who cannot read the rendered order): H0 = exact
Plackett–Luce inclusion, H1 = uniform `m/N`. `N=4` is **degenerate** (both are 1.0, no test
can separate); `N=5` → 11, `N=6` → 6, `N=8` → 4, `N=10` → 3 iterations. Note these rows test
*a* score dependence, not the value 0.731 — so they cannot substitute for the order test.

Deterministic runtimes (KAPSO, SimpleLoop): **n = 1 with power 1** against any alternative
that changes the selection. Repetition is not the control that matters. The controls that
do: counterbalanced candidate order, a same-score pair to pin the tie-break, and a
highest-nominal-score node that must lose (error/invalid/tier-gated).

## 4. False-green traps (each must have a dedicated, named check)

### T1 — EvE: an evaluation exception silently becomes `failure_score` 0.0

* Mechanism: `workflow/evaluation.py:161-165` wraps the whole evaluation in
  `except Exception: return (self.evaluation_failure_score, ...)`, and
  `configs/eve/evaluation/circle_packing.yaml:8-10` sets
  `failure_score: {score: 0.0, summary: "evaluation failed"}`. The boundary-check path has
  its own `{score: 0.0, summary: "boundary check failed"}` (`application/circle_packing.yaml:12-14`).
  `configs/eve/evaluation/circle_packing/evaluation.sh:56-72` does the same for a non-zero
  evaluator exit code, and `:96-111` for unparseable output.
* Why it is a false green: a candidate whose evaluation crashed is numerically
  indistinguishable from a candidate that genuinely scored 0.0, so "the evaluator ran and
  returned 0" can be asserted on a run where the evaluator never ran.
* **Required check:** assert on a *side channel*, not on the number. For every candidate
  whose score equals the failure score, assert `summary != "evaluation failed"` /
  `!= "boundary check failed"`, assert `logs/evaluate/step_XX_*/status.txt == "ok"`, and
  assert `error.txt` is absent or empty. If any candidate with a failure-shaped summary is
  in the population, the run is `infra_failed`, not a pass.
* Note the mitigation already present: the failure payload carries a distinguishing
  `summary`. The numeric comparison alone is what is unsafe.

### T2 — Loreley: evaluation timeout synthesizes a failure

* Mechanism: the evaluator runs the plugin in a spawned process, kills the process tree on
  deadline and raises `EvaluationError("... timed out after {timeout}s")`
  (`core/worker/evaluator.py:1859-1912`, `:2586-2617`), with
  `worker_evaluator_timeout_seconds` default `900` (`config.py:561-564`).
* **Where the error goes — corrected.** It does **not** become a `candidate_failed` fate.
  There are two paths and neither yields `CANDIDATE_FAILED`:
  - non-phased: `except (EvaluationError, EvaluationRuntimeError)` re-raises
    `EvolutionWorkerError` (`evolution.py:1560-1563`), classified as
    `("evaluation", "evaluator_infrastructure_failed")` (`evolution.py:2866-2874`), i.e. a
    worker-level failure with no `EvaluationOutcome` at all;
  - phased: `_phased_evaluation_failure` (`evolution.py:1892-1940`) builds an outcome with
    `outcome_kind="infrastructure_failed"` (`:1909`), `failure_stage="evaluation"` (`:1911`),
    `failure_kind="phased_evaluator_failed"` (`:1912`).
  `infrastructure_failed` / `evaluator_failed` / `inconclusive` are exactly the values
  `candidate_fate` classifies as **`UNKNOWN`**, "candidate-owned fate is not established"
  (`core/candidate_fate.py:46-50`, `:207-211`). So the timeout produces an
  *infrastructure* failure, not a bad candidate — and no score of record is synthesized
  (the outcome carries a failure result, not a score).
* **Required check:** assert that every observation counted in A0.2 has
  `outcome_kind == "passed"`; assert that no candidate whose outcome is
  `infrastructure_failed` / `evaluator_failed` / `inconclusive`, or whose workspace shows
  `failure_kind == "phased_evaluator_failed"`, is counted as an A0.2 observation; and report
  the excluded-candidate count (as `resolve_failed`, per §4.4's accounting) next to the
  result. A run with a non-zero timeout/infrastructure count is not a clean A0.2 run.
* **Do not mis-bucket `UNKNOWN`.** The `UNKNOWN` fate is the specific hazard here: it is
  neither "passed" nor "candidate is bad", so it is easy to silently drop from the
  denominator, which would inflate the pass rate. Assert the count directly rather than
  inferring it from a fate label.
* **Extra audit point (read, not executed).** A failure outcome may still carry
  `measurement_payload` / `measurement_executed` from a measurement that had already run
  (`evolution.py:1926-1932`). Assert that an outcome with `outcome_kind != "passed"`
  contributes no score of record even when it carries a payload.

### T3 — Loreley: metrics beyond a 64-item limit are truncated

* Mechanism: `evaluator.py:2304-2310` truncates `result.metrics` to
  `self.max_metrics`, and `worker_evaluator_max_metrics` defaults to **64**
  (`config.py:565-568`).
* Why it is a false green: if the frozen `E*` emits more than 64 metrics and any objective
  beyond position 64 is used for dominance, the archive silently ranks on a truncated
  vector, and the archive/Dominance assertions still pass.
* **Required check:** assert that the frozen evaluator's metric count is at most
  `worker_evaluator_max_metrics` (default 64) — i.e. a truncation cannot have fired — and
  record `worker_evaluator_max_metrics` and the raw metric count in the run record. Also
  assert the enumerated metric names cover every name in `mapelites_objectives`: a *missing*
  configured objective raises `ObjectiveContractError` and is therefore loud, but a
  truncation that drops the objective *after* the point where the contract is resolved
  would be silent, which is why the count check is the one that matters.

### T4 — Loreley: a persistent cache reuses stale scores

* Mechanism: the phased evaluator attempts `_reuse_phased_measurement` before measuring
  (`evolution.py:1650-1654`), and the outcome carries `measurement_cache_key`,
  `reuse_kind` and `reused_from_attempt_id` (field definitions `evaluator.py:748-796`;
  provenance attached at `:1677-1745`). The flag's value is set at the decision points:
  `reuse_kind = "measurement"` on the reuse path (`evolution.py:1768`), `"none"` on a fresh
  measurement (`:1875`, `evaluator.py:1730`/`:1744`), and
  `"measurement" if state.cached is not None else "none"` on the failure path
  (`evolution.py:1927`). So `"none"` really does distinguish fresh from reused.
* Why it is a false green: a "correct-looking" score can be a value computed under a
  previous evaluator head or a previous candidate tree.
* **Required check:** for every observation used in A0.2, assert `reuse_kind == "none"` and
  `reused_from_attempt_id is None`; if cache reuse is unavoidable, assert the source
  attempt's `(evaluator_id, fidelity, fraction, seed)` equals the current granted class and
  that the candidate's `commit_hash` is unchanged. Report the reuse count per run
  (`reuse_kind == "measurement"` count).

### T7 — closure: prove no autonomous egress by probe, not by config

* **Required check:** with the runtime's own config in place (not a modified one), run a
  probe that attempts an outbound network call from inside the agent session and from inside
  the evaluator step. It needs **both controls**: an unblocked posture must reach, and the
  blocked posture must fail. Record the probe command, the observed error/returncode, and
  the wall-clock budget. A probe that timed out, or that only shows a tool being absent,
  establishes nothing and must not be reported as closed; a config-only claim is not
  evidence. (Executed records: `a0/closure/closure.{eve,kapso,loreley,simpleloop}.json` and
  their reconciliation in `a0/closure/closure.reconciliation.json`.)
* **EvE — the driver switch, not a config flag.** The protocol's recipe
  (`codex_tmux` + `sandbox_mode: workspace-write` + `allow_network: false` +
  `web_search: disabled`) is implemented, but it is unreachable from the shipped driver.
  `allow_network` **does** exist and is plumbed: profile defaults
  (`providers/agent/config.py:24-32`), typed field (`config.py:86`), runtime policy object
  (`providers/agent/python_runtime.py:20,27`) enforced at `python_runtime.py:332` by
  `if not bool(policy.get("allow_network", True))` blocking `socket.connect` /
  `create_connection`, and `algorithms/eve/runtime/driver.py:380-387` mapping it to
  `danger-full-access` (true) or `workspace-write` (else). `codex_tmux`'s defaults are
  `sandbox_mode="workspace-write"`, `web_search="disabled"`
  (`providers/agent/drivers/codex_tmux.py:200-201`).
  The trap is the shipped path: `configs/eve/driver/codex_max.yaml:6,12` selects
  `codex_exec` with `web_search: live`; `CodexExecSessionDriver.__init__` has **no sandbox
  parameter at all** (`providers/agent/drivers/codex_exec.py:79-100`) and its argv hardcodes
  `--dangerously-bypass-approvals-and-sandbox` (`:419-436`, flag on `:434`). The mapper is
  wired only into the tmux builder (`runtime/driver.py:201`);
  `_build_codex_exec_driver` (`runtime/driver.py:211-238`) never reads `sandbox_mode` or
  `approval_policy`, and nothing rejects those keys on that path (opencode does refuse them,
