### 1.2 The induced distribution

`RankSoftmaxSampler.sample` (`rank_softmax.py:162-183`):

```python
173:  scalar_scores = [scalar(score) for score in scores]
174:  ranked_indices = sorted(range(len(items)), key=lambda index: scalar_scores[index],
175:                          reverse=True)                      # stable: ties -> input order
179:  total_weights = [0.0 for _ in items]
180:  for rank, item_index in enumerate(ranked_indices):
181:      total_weights[item_index] = math.exp(-(rank / self.temperature))
183:  return self._sample_by_mode(items, total_weights, num=num, rng=rng)
```

`RankExponentialSumSampler.sample` (`rank_softmax.py:83-108`) with the single configured
feature `score: {weight: 1.0, temperature: 1.0}` computes (line 104)

```python
104:  total_weights[item_index] += feature_weight * math.exp(-(rank / temperature))
```

which is **the identical weight vector**. The module docstring states the equivalence
explicitly (`rank_softmax.py:50-51`): "With a single configured feature,
`RankExponentialSumSampler` is equivalent to `RankSoftmaxSampler` when the same
temperature is used."

So both classes induce weights

```text
w_rank = exp(-rank / T),   rank = 0, 1, ..., N-1      (T = 1, one scalar feature)
```

and the direction is "rank 0 = highest `scalar(score)`" (`reverse=True`, line 175/101).
`scalar()` (`populations/score.py:9-31`) projects the score PyTree: a plain number as-is,
a one-key mapping by its only value, otherwise by the `score` key. For the frozen
evaluator the score is `{score: float, summary: str}` (or the judge-pipeline dict, which
also carries a headline `score`), so **`F_r = score["score"]`**, and its sign convention is
`higher is better` (`immutable_assess/README.md:24`: "each a float in [0, 1], higher is
better").

`_sample_by_mode` (`samplers/base.py:18-39`):

- `replacement` → `rng.choices(items, weights, k=num)` (line 76) — i.i.d. draws.
- `no_replacement` → `_weighted_sample_without_replacement(..., num=min(num, len(items)))`
  (lines 30-36) — **num is capped at the population size**.
- `auto` → no-replacement for `min(num, N)` draws, then top up with replacement if still
  short (lines 78-101).

`_weighted_sample_without_replacement` (`samplers/base.py:41-64`) is the key routine:

```python
49:  remaining = sorted(list(zip(items, weights)), key=lambda p: p[1], reverse=True)
55:  for _ in range(min(num, len(remaining))):
56:      chosen_index = rng.choices(range(len(remaining)),
58:                                 weights=[weight for _item, weight in remaining], k=1)[0]
61:      item, _weight = remaining.pop(chosen_index)
62:      result.append(item)
63:      remaining.sort(key=lambda pair: pair[1], reverse=True)
```

Two facts follow, and both matter:

1. **The weights are never recomputed.** After a draw the item is removed but every
   remaining item keeps its original weight; `random.choices` renormalises internally, so
   draw *k* is proportional to the **original** weights restricted to the survivors. The
   re-sort on line 63 is cosmetic (a single weighted choice is invariant under permuting
   the index↔weight pairing, and the pop uses the same sorted list for items and weights).
   This is exactly the Plackett–Luce / successive-sampling-with-fixed-weights scheme. It is
   equivalent to ordering independent `Exp(rate = w_rank)` variates (memorylessness), which
   I use below as an interpretation check.
2. **There is no re-ranking of the remainder.** A candidate that was rank 1 is still
   "rank 1" (weight `e^-1`) for every later draw. A re-implementation that re-ranks after
   each removal is *not* equivalent, and §1.5 gives the discriminating number.

### 1.3 Case A — one draw (the protocol's `P(c_1) = 1/(1+e^-1)`)

Population `{c1, c2}` with `E(c1) > E(c2)`, `T = 1`, `num = 1`, any replacement mode.
Ranks are 0 and 1, weights `w = (1, e^-1)`. The first draw is proportional to the full
weight vector for **any** `num ≥ 1`, because the weight vector is built before the first
`choices` call. Therefore

```text
P(the higher-scoring candidate is picked) = w_0 / (w_0 + w_1) = 1 / (1 + e^-1)
                                          = 0.7310585786300049
```

**Confirmed against the implementation** by executing EvE's own classes: §6 row 1a gives
closed form 0.731059 vs simulated 0.731408 at 10^6 draws (|diff| 3.5e-4, inside the
3σ MC half-width 1.3e-3); row 1d shows `RankExponentialSumSampler` reproducing the same
number. **The protocol's 0.731 checks out**, and it is the *first-draw* probability.

Note what this 0.731 actually depends on: `T = 1` and the *rank gap of 1*. It does **not**
depend on the score gap — a 0.001 and a 10^6 point gap give the same p, because the
sampler ranks. The test must therefore state that it checks **rank-softmax consumption of
score order**, not magnitude sensitivity. Any test that tries to detect score-gap
sensitivity will fail against correct code; that is a would-be "false red", not a bug.

### 1.4 Case B — `solver_examples`: n = 4, `no_replacement`

Frozen: `num = 4`, `no_replacement`, weights `exp(-rank)`. Two things change relative to
case A, and **neither of them is the sampler class** (proven in §1.2):

1. `num = min(4, N)` (base.py:34). For `N ≤ 4`, **every** population member is returned;
   the returned *set* carries no information and only the *order* does.
2. The later draws use the reduced-by-removal original weights.

Worked values (all exact; generated by the subset DP in `simulate.py` and reproduced by
10^6 real-sampler draws in §6 rows 1b/1c/1d/1h/1i):

| population | observable | exact value |
| --- | --- | --- |
| N=2, num=4 | P(c1 is position 0) | `1/(1+e^-1)` = **0.731058579** |
| N=2, num=4 | P(c1 in the returned set) | **1** (num capped to 2) |
| N=3, num=4 | P(c1 is position 0) | `1/(1+e^-1+e^-2)` = **0.665240956** |
| N=3, num=4 | P(c1 in the returned set) | **1** |
| N=4, num=4 | P(c1 is position 0) | `1/(1+e^-1+e^-2+e^-3)` = **0.643914260** |
| N=4, num=4 | P(c1 in the returned set) | **1** |
| N=5, num=4 | P(c1 in the returned set) | **0.999650086** |
| N=8, num=4 | P(c1 in the returned set) | **0.999368279** |
| N=10, num=4 | P(c1 in the returned set) | **0.999354001** |
| general N | P(c1 is position 0) | `1 / Σ_{r<N} e^-r` |
| general N > 4 | P(c1 in the returned set) | `1 - Σ_{|B|=4, B⊆others} h(B)`, `h` the ordered-subset DP of `pl_set_probabilities()` |

**Second and later draws** (the part the protocol asks to be derived separately). Given the
first drawn item is `j`, the next draw is proportional to the *original* weights of the
survivors:

```text
P(c1 second | j first) = w_0 / (W - w_j)
```

Concretely: with `N = 3` and `c2` (rank 1) drawn first, `P(c1 next) = 1/(1+e^-2) =
0.8807971`; with `N = 4` and the same condition it is `1/(1+e^-2+e^-3) = 0.8437947`. Both
are verified against the real code in §6 row 1e (sim 0.880507 / 0.844133). The marginal
`P(c1 is position 1)` is tabulated in §6 row 1i and converges to ≈0.282889 for large `N`.
A **re-ranking** implementation would answer 0.8807971 for both `N=3` and `N=4` and would
report `P(c1 position 0) = 0.7310586` for a `N=4` population — those are the two
discriminating signals, and they are what the "second and later draws" clause buys you.

`replacement_mode: auto` (the `working_optimizer` site, `num = 2`) behaves as
no-replacement first and then i.i.d. draws with the *original* weights, so its top-up slots
each carry `w_0/W` = 0.7310586 (§6 row 1g: 4th slot sim 0.731775).

### 1.5 What is observable end-to-end (this decides the test design)

- The `solver_examples/` directory **set** is observable: one subdirectory per sampled
  entry, named by `entry.id`, each containing `solver/`, `logs/evaluate/` and a
  `score.yaml` with `{example_id, score}` (`solver_workspace.py:148-179`). So an auditor
  can read *which* candidates were sampled and their scores from the artifacts alone.
- The **order** is also observable, contrary to a first guess: the immutable block
  `{solver_examples_block}` (`configs/eve/optimizer/circle_packing/immutable/README.md:136`)
  is rendered by `_render_solver_examples_block` (`immutable_renderers/base.py:179-196`),
  which iterates `solvers` **in the sampled order** and writes
  `` - `solver_examples/<id>/` `` plus `prior score:` for each; the file is written into the
  worker workspace by `write_immutable_assets` (`solver_workspace.py:194-219`,
  called at `phase2.py:158-165`). The block also marks the entry that the `UniformSampler`
  chose with `<- prefill`.
- The prefill overlay itself is score-independent: `solver/` starts as the problem
  snapshot and is overwritten by the prefill entry's files
  (`solver_workspace.py:188-191`), and the prefill sampler is the `UniformSampler` which
  **discards the scores** (`uniform.py:34`: `_ = scores`). §6 row 1f measures 0.5 / 0.25 /
  invariance under score permutation. **The A0.2 test must not use the `solver/` contents as
  evidence of score consumption** — that is the protocol's explicit warning, and the
  UniformSampler is the control that proves it.

### 1.6 Consequences for the contract (pre-registered)

1. The 0.731 claim is confirmed, and it is a statement about the **position-0 draw**, not
   about inclusion. With the frozen `n = 4` (`loop/default.yaml:9`) and a two-candidate
   population the *inclusion* event is degenerate (`p = 1`), so an inclusion-based test has
   zero power; only the order statistic tests anything.
2. Under the frozen unit-test conditions `k=2, T=1, num=1`, `RankSoftmaxSampler` and
   `RankExponentialSumSampler` are **distributionally identical** (§6 row 5c). "The other
   sampler's p" therefore does not exist at those conditions; distinguishing the classes
   requires `N ≥ 3` or `num ≠ 1`.
3. `F_r(E*) = scalar(score) = score["score"]`, and score *order* (not magnitude) is what is
   consumed. This must be declared and frozen per §4.2.2.

### 2.1 Verifying the protocol's claim

The protocol cites `parent_policy = "best"` at `strategy.py:198,212`. Both lines check out:

```text

101: def normalize_parent_policy(value: Any) -> str: ...   # raises unless in PARENT_POLICIES
198:  - parent_policy: Parent branch selection: best or baseline (default: best).
211:  parent_policy = normalize_parent_policy(
212:      (config.params or {}).get("parent_policy", "best")
401:  self.parent_policy = parent_policy
```

(`src/kapso/execution/search_strategies/generic/strategy.py`.) So the default *is* `best`,
and a checkpoint cannot silently change it: `strategy.py:1586-1599` refuses to resume when
the saved and configured policies disagree.

**Parent = max score.** `_select_parent` (`strategy.py:1374-1403`):

```text
1376:  if self.parent_policy == "baseline":  return ParentSelection("main", None)
1378:  best = self.get_best_experiment()
1379:  if best is not None: return ParentSelection(best.branch_name, best.node_id)
```

and `get_best_experiment` (`strategy.py:1424-1434`):

```text
1425-1428:  "Return the best successful SCORED node — a node whose evaluation never
           completed (score=None) can never be best; on minimize metrics it would
           otherwise key as 0 and out-rank every real score."
1429:  valid = [n for n in self.node_history
1430:           if not n.had_error and n.evaluation_valid and n.score is not None]
1433:  return max(valid, key=lambda x: x.score if self.problem_handler.maximize_scoring
                                        else -x.score)
```

Three gates — `had_error`, `evaluation_valid`, `score is not None` — must all pass, and the
direction comes from `problem_handler.maximize_scoring`, whose base default is `True`
(`environment/handlers/base.py:48`, `handlers/generic.py:53`). **The direction is a config
property, not a free choice: if the circle-packing handler sets it False, the argmax
becomes an argmin and the expected parent flips.** The A0.2 test must assert
`maximize_scoring` equals whatever the frozen value is (and it is currently `True` unless
overridden).

**The round representative is not the same object as the parent.** `_select_parent` uses
`get_best_experiment`, but the deliverable/checkout uses `get_deliverable_experiment`
(`strategy.py:1436-1453`), which prefers a *tier walk*:

```text
1446:  if self.registered_evaluator_id:
1447:      committed = select_committed_candidate(self.node_history,
1448:          evaluator_id=self.registered_evaluator_id,
1449:          maximize=self.problem_handler.maximize_scoring)
1450:      if committed is not None: return committed
1453:  return self.get_best_experiment()
```

and `select_committed_candidate` (`execution/fidelity.py:184-213`):

```text
 28-30: TIER_FULL = 2, TIER_VALIDATED = 1, TIER_PROBE = 0
197-203: eligible = [n for n in nodes
                    if not had_error and evaluation_valid
                    and evidence_tier(n, evaluator_id) > TIER_PROBE]
206-212: return max(eligible, key=lambda n: (evidence_tier(n, evaluator_id),
                                             sign * full_eval_score(n, evaluator_id)))
```

with `evidence_tier` = 2 if a `fidelity == "full"` attempt exists under that evaluator id
and `build_fidelity == "full"`, 1 if the build was fast, 0 otherwise
(`fidelity.py:156-168`), and `full_eval_score` = mean over that node's `evaluator_id`
matching, `fidelity == "full"` attempts (`fidelity.py:171-182`). `checkout_to_best_experiment_branch`
(`strategy.py:1479-1491`) switches the workspace to the *deliverable's* branch.

**So the expected assertion depends on the fidelity mode.** With `fidelity.mode = "off"`
(the `FidelitySpec` default, `fidelity.py:244`), `FULL_PASSTHROUGH` gives every experiment
`build_fidelity="full", eval_fidelity="full", eval_fraction=1.0` (`fidelity.py:304-310`),
so both candidates sit at `TIER_FULL` in the same `ComparabilityClass`, the tier keys tie,
and the score decides. Then parent and deliverable agree.

### 2.2 The exact expected assertions

Frozen conditions: `parent_policy = "best"`; `fidelity.mode = "off"`; `maximize_scoring =
True`; one registered evaluator head; both candidates evaluated in the same round with
`E*(c1) > E*(c2)`; `c1` and `c2` each have a commit on their own branch.

1. **Parent:** the next round's `parent_branch_name`/`parent node_id` equals `c1`'s branch
   and `c1`'s node id. (Not "the round representative", not "the newest" — see the
   committed-but-unevaluated fallback at `strategy.py:1385-1402`, which is only reached
   when *no* validly scored node exists; the test must have `get_best_experiment() is not
   None`, otherwise the assertion is vacuous.)
2. **Deliverable / best-experiment return:** `checkout_to_best_experiment_branch()` returns
   `c1`'s branch, and `get_deliverable_score()` returns `c1`'s score. Under the frozen
   `mode = off` this is `select_committed_candidate` = `c1`; the test must *also* assert
   `evidence_tier(c1) == evidence_tier(c2) == TIER_FULL` and that both attempts' grants
   are the same class, otherwise a tier mismatch makes the assertion illegitimate (§2.3).
3. **Negative controls (all deterministic, one round each):**
   - `c2` with `had_error = True` (or `evaluation_valid = False`) and a *higher* raw score
     must not become parent or deliverable. §6 row 3 verifies this by transcription.
   - `c2` with `score = None` must never be deliverable (`score=None can never be best`).
   - A `fast`-only `c1` (score 9.0) must lose the deliverable to a `full` `c2` (score 1.0):
     `TIER_PROBE` is not even eligible (`fidelity.py:202`). §6 row 3 confirms this via the
     transcription — and it is the single most likely way an A0.2 test passes falsely by
     asserting the wrong object.
   - Equal scores: Python's `max` returns the **first** maximal element, so the parent is
     the earlier node in `node_history` (insertion order). Freeze that tie-break explicitly;
     it is not documented in the protocol.

### 2.3 The manifest-triple invariant (A0.1, with a correction)

The protocol writes the invariant as `(evaluator, fidelity, fraction, seed)`. **There is no
evaluator field in the manifest.** `parse_manifest_line` (`evaluation_maintainer/maintainer.py:64-83`)
requires exactly `fidelity, fraction, seed, items, total_items` (plus `score`, read
separately), and the maintainer prompt that defines the contract lists exactly
`fidelity, fraction, seed, items, total_items, score`
(`prompts/setup_build.md:19-21`, `prompts/setup_provided.md:11-14`). The accepted check
(`registered_evaluation.py:87-99`) is a **triple**:

```text
87:  if (manifest["fidelity"] != granted_fidelity
89:      or abs(float(manifest["fraction"]) - granted_fraction) > 1e-9
90:      or int(manifest["seed"]) != registered_subsample_seed):
97:      "... — no mechanical score of record"
99:      return None
```

Evaluator identity is enforced **out of band**, by two other mechanisms:
`registered_evaluator_id = manifest_fingerprint(build_evaluation_manifest(kapso_evaluation/))`
(`maintainer.py:216-218`; SHA-256 over a sorted JSON file manifest,
`evaluation_integrity.py:112-119`), and `sync_registered_evaluation` overwriting the
branch's evaluation tree with the registered head before any frame run
(`registered_evaluation.py:193-200`, with the stated reason "a bridge labeled v2 executed
the branch's v1 tree"). So the A0.1 assertion is
**(fidelity, fraction, seed) from the manifest == the granted decision** *plus* the
evaluator head's fingerprint == `EID*`'s derived child, and the adapter must assert both.

Three traps inside this invariant:

- A mismatch **only prints and returns `None`** (`registered_evaluation.py:92-98`). The node
  keeps whatever `node.score` the session reported. "The runtime returned None" is *not*
  evidence that the invariant held; the check must read the printed manifest line and the
  grant from the trace and compare them itself.
- `manifest_of_record` uses the **last** manifest line in the session output
  (`registered_evaluation.py:74-78`). If a session prints several, only the last is checked.
- `record_evaluation_attempt` records `fidelity=node.eval_fidelity` and
  `fraction=decision.eval_fraction` (`registered_evaluation.py:144-158`), while
  `select_committed_candidate`'s `full_eval_score` averages **all** `fidelity=="full"`
  attempts regardless of fraction or seed (`fidelity.py:171-182`) even though its docstring
  says "any fraction=1.0". `project_score`, by contrast, requires an exact
  `ComparabilityClass` match including fraction and seed (`fidelity.py:44-50, 142-154`). So
  `node.score` and `full_eval_score` can disagree when attempts differ in fraction/seed —
  which is precisely what the manifest invariant exists to prevent. Cite `fidelity.py:171-182`
  when writing the test; do not trust the docstring.

### 2.4 The other KAPSO traps

- Hard constraint #2 (counters/logs must not live in a reverted directory): KAPSO's
  candidate worktree carries `kapso_evaluation/`, and every frame run re-syncs that
  directory from the registered head (`registered_evaluation.py:193-200`); a `git checkout`
  of a branch also reverts it. Any counter written there is destroyed. Counters must live
  outside the worktree.
- `evaluation_status == "candidate_failed"` → `CANDIDATE_FAILED`,`failure_stage == "policy"`
  → `POLICY_FAILED`, and outcomes `evaluator_failed` / `infrastructure_failed` /
  `inconclusive` map to `UNKNOWN` with "candidate-owned fate is not established"
  (`core/candidate_fate.py:46-50`, `:191-211`). A test that treats `UNKNOWN` as "the
  candidate scored badly" is wrong.
- An evaluator **timeout** lands in that non-candidate bucket, not in `CANDIDATE_FAILED`:
  the non-phased path re-raises `EvolutionWorkerError` (`evolution.py:1560-1563`, classified
  `("evaluation", "evaluator_infrastructure_failed")` at `:2866-2874`) and the phased path
  builds an outcome with `outcome_kind="infrastructure_failed"`,
  `failure_kind="phased_evaluator_failed"` (`evolution.py:1892-1912`, fields on `:1909-1912`).
  See `ACCEPTANCE.md` T2.

## 3. Loreley — QD archive

Source: `/tmp/lor/loreley/...`, verified blob-identical to the pin `4c375920` (§0.1). The archive class is
`ParetoGridArchive` in `core/map_elites/pareto_archive.py` — a **numpy-only module**, so
`simulate.py` imports and drives it directly; §6 section 2 is real-code execution, not a
transcription.

### 3.1 The verified rules, with citations

- **A bounded Pareto front lives in every fixed grid cell** (`pareto_archive.py:1`, `:123-148`).
  Cell membership comes from `measures` **only**: `index_of` (`:168-189`) clips and floors
  `measures` into the grid; `objective_scores` are never consulted. Score can therefore
  never move a candidate between cells.
- **Replacement is per cell only.** `add` → `add_many` (`:201-263`) groups the incoming
  batch by cell (`_group_by_cell`, `:365-373`) and calls `_select_front` **once per affected
  cell** with `(*self._fronts.get(cell_index, ()), *additions_by_cell.get(cell_index, ()))`
  (`_merge_affected_cells`, `:375-386`). No cross-cell set operation exists anywhere in the
  class. `_detach_commits` (`:347-363`) only removes the *incoming* candidate's own old
  membership.
- **Non-domination with an epsilon**: `_dominates(first, second)` = `all(first >= second -
  ε)` and `any(first > second + ε)` (`:459-468`), `ε = mapelites_pareto_epsilon` whose default
  is `1.0e-9` (`config.py:924-927`). Objective-equivalent candidates (all coordinates within
  ε) are deduplicated *before* domination, keeping the one with the smallest `commit_hash`
  (`:424-431`).
- **Truncation by crowding distance** when the non-dominated set exceeds
  `max_front_size` (default `8`, `config.py:920-923`): boundary points get `inf`, interior
  points accumulate `(next - prev)/span` per objective with a `span <= ε` skip, then the
  front is sorted by `(-crowding, commit_hash)` and cut (`:442-450`, `:470-500`).
- **Sampling is score-independent**: `ParetoGridArchive.sample` picks a uniform occupied
  cell and then a uniform member of that cell's front (`:265-278`); the runtime's job
  sampler does the same at the commit level, `_select_base_candidate` choosing
  `effective_rng.choice(available_cells)` then `effective_rng.choice(commits)`
  (`core/map_elites/sampler.py:531-559`), with cells and commits sorted before the choice.
  The sampler RNG is *not* the archive RNG: it is derived from
  `mapelites_sampler_seed` (default `0`, `config.py:953-956`) + island id + job ordinal
  (`sampler.py:405-417`), so it is reproducible even though EvE's is not.
- **Admission policy**: `mapelites_admission_policy` defaults to `"pareto"`
  (`config.py:928-930`); the alternative `"fresh_comparison"` uses
  `replace_if_current` (`pareto_archive.py:204-242`), which insists on a single objective,
  an exactly-matching cell, and an incumbent match, and **refuses to replace a
  multi-member front**. Freeze `"pareto"` or state which one is frozen.
- **Objective contract**: default `(ObjectiveSpec(name="composite_score", direction="max"),)`
  — a **single** objective (`config.py:916-919`). Dominance scores are the values with
  `min` objectives negated (`objectives.py:118-133`). Direction is validated against the
  evaluator's own `higher_is_better` flag and a conflict raises
  (`objectives.py:125-130`).
- **The reported "best" is a global argmax over retained members**:
  `_resolve_best_primary_commit` (`scheduler/main.py:876-931`) selects from `Metric` rows
  **joined to `MapElitesArchiveCell`** (archive membership) ordered by
  `Metric.value DESC` (or ASC for a min primary) with tie-break `commit_hash ASC`, `LIMIT 1`;
  the CLI's `_load_best_commit_status_payload` (`cli.py:559-603`) does the same for the
  status panel.

### 3.2 The exact expected assertions

Frozen conditions: single island; single objective `composite_score` (`direction="max"`);
`ε = 1e-9`; `max_front_size` as configured; `admission_policy = "pareto"`; a *strict* score
gap `|Δ| > ε`; and the two candidates' `measures` chosen to land in the intended cells.

**Positive (same cell).** Add `c2` then `c1` with `E(c1) > E(c2) + ε` and identical
`measures`:

- `ParetoAddOutcome(commit=c1).retained is True`
- `ParetoAddOutcome(commit=c1).removed_commit_hashes == (c2,)`
- `archive.front(cell)` == `(c1,)`; `c2 ∉ archive.records()`; `c2 ∉ state.commit_to_index`
- persisted: `ingestion_status_code == 1` (retained) and the `MapElitesArchiveCell` row for
  that cell now names `c1`; c1's `candidate_fate_label` is `elite_inserted`/`elite_replaced`
  depending on the (unreachable-in-`pareto`-mode) status code — see §5 finding F5
- report branch: the best-primary-commit query returns `c1`

§6 section 2a verifies the first three against the real class. `removed_commit_hashes` is
only populated when the batch has exactly one candidate (`_build_add_outcomes`,
`:407`: `removed_for_candidate = removed if len(candidates) == 1 else ()`) — so the
assertion must add candidates **one at a time**, not as a batch.

**Negative control 1 (cross cell, higher score must not evict).** `c2` in cell A, `c1` with
`E(c1) > E(c2) + ε` and `measures` placing it in cell B:

- `ParetoAddOutcome(commit=c1).retained is True` **and** `removed_commit_hashes == ()`
- `archive.front(cellA)` still contains `c2`; `c2` is still an archive member
- §6 section 2b verifies exactly this.

**Negative control 2 (admission is not a global argmax).** With `c_high = 9.0` in cell A,
admit `c_low = 1.0` with `measures` in cell B: `retained is True`, nothing removed, and both
are members (§6 section 2b2). This is the control that actually demonstrates the QD
semantics; the report branch will point at `c_high`, so **the report assertion must not be
used as the cross-cell control**.

**Negative control 3 (ε-tie decides by `commit_hash`, not by score).** A score gap below ε
is not dominance; the dedup keeps the lexicographically smallest `commit_hash`
(`:424-431`). §6 section 2c shows an incumbent `zzz` at 1.0 being replaced by `aaa` at
`1.0 + 1e-12` — the *score* did not decide. **A0.2 must therefore assert `|Δ| > ε`, or the
positive assertion passes for the wrong reason.**

**Negative control 4 (sampling ignores score).** Freeze a two-cell archive with scores 1.0
and 99.0, draw ≥10^4 samples with a fixed rng, assert the per-cell pick frequency is
~0.5/0.5 (binomial CI), and assert the distribution is *unchanged* when the score order is
permuted while `measures` are held fixed. §6 section 2f verifies the uniformity.

## 4. SimpleLoop — the deterministic baseline

The protocol fixes the definition in §4.4 (line ~608):

```text
c_0 = baseline
c_{t+1} = Agent(c_t, H_t)
c*_t = argmax_{i <= t} E(c_i)
parent_{t+1} = c*_t
forbidden: archive/QD, evolved harness/guidance, multi-island, learned operator
           selection, external retrieval (at A1), undeclared special prompts
```

There is **no upstream implementation** to cite: SimpleLoop is the study's own substrate,
owned by `a0/contract/**`, so the expectation is a specification, not a source derivation.
Stated as an assertion: after a round in which `E(c1) > E(c2)`, the next `parent` is `c1`,
and the reported best candidate is `c1` — a deterministic argmax over all candidates
evaluated so far (`c*_t` is a running max, so it is monotone and never loses a previously
best candidate).

Two gaps that must be closed in `a0/contract` before A0.2 means anything:

1. **Tie-break is undefined.** `argmax` on equal scalars is not specified. Freeze it
   (recommend: earliest index, or lexicographically smallest candidate id) and test it.
2. **The scalarization is unspecified.** §4.2.2 says `F_r(E*) = scalar(E*)` for the A1 first
   round but does not give the fold for the multi-field `E*` output. Freeze it too.

Power: **one trial has power 1** against any alternative that changes the selected parent.
Repetition buys nothing here; what establishes the test's meaning is
(a) counterbalanced candidate order (assert the argmax follows the scores, not the
insertion order — §6 section 4 does this on the transcribed rule), (b) a same-score pair to
pin the tie-break, (c) a highest-nominal-score node that must *not* win.

## 5. Findings — where the protocol or the source is suspect

**F1 — "the other sampler's p" does not exist at the frozen unit-test conditions.**
`RankSoftmaxSampler` and `RankExponentialSumSampler` with one scalar feature of equal
weight and temperature produce *identical* weights (`rank_softmax.py:104` vs `:181`,
docstring `:50-51`). §6 row 5c measures both at 0.7310586. The protocol is right that
`solver_examples` needs a separate expectation, but the reason is `num = 4` +
`no_replacement` + population size, **not** the sampler class. A pre-registered
"distinguish the two classes" frequency test at `k=2, num=1` is unfalsifiable.

**F2 — 0.731 is a rank-gap statement, not a score-sensitivity statement.** Because the
sampler ranks (`reverse=True` on `scalar(score)`), the probability is invariant to the score
*magnitude*. Any A0.2 analysis that expects score-gap sensitivity is mis-specified.

**F3 — the order IS observable, and that is the only usable observable.** The `n=4`
frozen config caps `num` at the population size, so inclusion is degenerate (`p = 1`) for
`N ≤ 4`. The draw order survives only in the rendered `README.md` block
(`immutable_renderers/base.py:179-196`). If that rendering were ever changed to sort by
score or by id, the A0.2 order test would silently lose its measurement — **the test should
assert its own observable exists before asserting the frequency**, and the study should
record this dependency.

**F4 — EvE's closure recipe in §4.3 is implemented, but it is unreachable from the
shipped driver — and the trap is not a missing parameter.** §4.3 says closure for EvE is
achieved by `codex_tmux` with `sandbox_mode: workspace-write` + `allow_network: false` +
`web_search: disabled`. All three of those knobs **exist**:

- `allow_network` is a first-class, plumbed parameter: policy-profile defaults
  `benchmark_safe: allow_network False` / `open_agent: allow_network True`
  (`providers/agent/config.py:24-32`), the typed field `allow_network: bool | None = None`
  (`config.py:86`), the runtime policy object (`providers/agent/python_runtime.py:20,27`)
  enforced at `python_runtime.py:332` — `if not bool(policy.get("allow_network", True))`
  replaces `socket.socket.connect`, `connect_ex` and `create_connection` with a blocker.
- `algorithms/eve/runtime/driver.py:380-387` maps it to a sandbox mode:
  `_sandbox_mode_from_driver_cfg` returns `danger-full-access` when `allow_network` is true
  and `workspace-write` otherwise.
- `codex_tmux`'s own defaults are `sandbox_mode="workspace-write"`,
  `web_search="disabled"` (`providers/agent/drivers/codex_tmux.py:200-201`).

The actual trap is that on EvE's **shipped** full-run path none of this can be reached.
The circle-packing config selects `codex_exec` (`configs/eve/driver/codex_max.yaml:6,12`:
`driver: codex_exec`, `web_search: live`); `CodexExecSessionDriver.__init__` has **no
sandbox parameter at all** (`providers/agent/drivers/codex_exec.py:79-100`), and its argv
hardcodes `--dangerously-bypass-approvals-and-sandbox` (`codex_exec.py:419-436`, the flag on
`:434`). `_sandbox_mode_from_driver_cfg` is wired only into the tmux builder
(`runtime/driver.py:201`); `_build_codex_exec_driver` (`runtime/driver.py:211-238`) never
reads `sandbox_mode` or `approval_policy`, and nothing rejects those keys on that path —
unlike opencode, which refuses them loudly (`runtime/driver.py:275-284`). So
`driver.sandbox_mode=workspace-write` **and** `driver.allow_network=false` are **silently
ignored** on the shipped path, and under it Codex's `workspace-write` network guarantee
never applies. Closure for EvE requires a *driver switch* (`driver: codex_tmux` with
`web_search: disabled`) or an external network cut, and then a probe; a config-only closure
verdict on the shipped path is a false green.

**Scope of the two records (quote both together).** `a0/closure/closure.eve.json` is
authoritative for the per-mechanism/posture breakdown: the `codex_tmux`/`workspace-write`
lane is CLOSED by an executed end-to-end canary with the model turn completing
(`rc=0`, canary persisted `dns/tcp/https fail, local=ok, egress=BLOCKED`), with the
unsandboxed posture OPEN by the same probe. `a0/runtimes/eve/out/run001/closure.json` is
authoritative for **"EvE as shipped"** — verdict `egress_detected`, i.e. OPEN. The split is
recorded in `a0/closure/closure.reconciliation.json` → `per_runtime[eve].contradictions`
("theirs for 'EvE as shipped'; this workstream's for the per-mechanism/posture
breakdown"). Study verdict: EvE is **CONDITIONAL** — closed only under the named posture,
shipped default open. This finding's own text is a static source read and cites no probe
result; the executed records above are the evidence.

**F5 — Loreley's "no global-argmax guarantee" is only true with ≥2 objectives.** With the
default single objective (`config.py:916-919`) no two strictly different scores are
non-dominated, so every cell front has exactly one member (`:433-451`) and the archive is
the per-cell argmax; the report query (`scheduler/main.py:876-931`) is then the argmax over
everything evaluated. §6 section 2d demonstrates this (12 candidates, 11 evicted, `k11`
retained). The cross-cell and crowding-truncation controls are still meaningful, but the
"a higher score may not be kept" claim needs a multi-objective configuration to be
exercised — §6 section 2e shows crowding truncation only bites with 2 objectives.

**F6 — `candidate_fate`'s `ELITE_INSERTED` branch looks unreachable under the default
admission policy.** `_archive_acceptance_fate` reports `elite_inserted` when
`ingestion_status_code == 2` (`candidate_fate.py:219-231`, "entered an empty archive
niche"). But in the `pareto` path the code is `MapElitesInsertionResult.status` ←
`ParetoAddOutcome.status` ← `1 if retained else 0` (`pareto_archive.py:109-111`,
`archive_ops.py:100-109`, `manager.py:903-929`), and `ingestion_status_code =
insertion.status` (`scheduler/ingestion.py:988`). I found no producer of status `2`
anywhere in the tree. If that is right, every successful archive entry reports
`elite_replaced` ("improved an occupied archive niche"), even into an empty niche.
**Unresolved:** it may be produced by the `fresh_comparison` policy or by a snapshot/DB path
I did not trace. The A0.2 assertion should key on `retained` / `removed_commit_hashes` /
`archive .front()` rather than on this label.

**F7 — KAPSO's `full_eval_score` ignores fraction and seed** while `project_score` requires
an exact `ComparabilityClass` match (`fidelity.py:171-182` vs `:142-154`). Within
`mode = off` both are `1.0`/fixed seed so it cannot currently bite, but the deliverable
ranking is not class-safe by construction; the manifest invariant (§2.3) is what keeps it
honest.

**F8 — KAPSO's manifest has no evaluator field,** so the protocol's four-element "manifest
triple" is really a three-element mechanical check plus an out-of-band evaluator
fingerprint (§2.3). A test written from the protocol's wording would look for a field that
does not exist.

### 6.2 Reading the simulation

- Every closed form agrees with the real sampler/archive within the 3σ Monte-Carlo
  half-width; the largest observed discrepancy is 7.2e-4 at 10^6 draws.
- One genuine disagreement was found and fixed **during** this derivation, and it is worth
  recording because it is exactly the class of error the exercise is meant to catch: I first
  predicted `P(c1 second | c2 first) = 1/(1+e^-2) = 0.880797` for a 4-candidate population,
  i.e. I silently dropped the 4th candidate's weight. The implementation returned 0.844289.
  The source was right and my closed form was wrong; the correct value is
  `1/(1+e^-2+e^-3) = 0.8437947`, which the simulation then matched (0.844133). This is
  reported rather than papered over because the same mistake in the other direction — a
  closed form that ignores the remainder and thereby *matches* a re-ranking implementation —
  would have made the test blind to exactly the bug it exists to find.
