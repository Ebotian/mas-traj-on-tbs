## 0. 一句话背景

我们研究的是：**让算法搜索系统自己去外部世界找资料（别人的代码、现成实现、论文），能不能真的让它改进算法？值不值得？** 我们已经把"尺子"造好并通过独立审计，现在要设计**第一次真正的实验**（A1）。缺的不是技术，是**一个具体的实验任务**和**一套预算/统计口径**。

## 1. 研究问题与本阶段目标

### 1.1 最终假设（两个）

- **H_A**：给搜索系统一份**普通的外部既有实现**（不是精挑细选的），它的算法搜索会变好吗？
- **H_O**：让系统**主动去开放世界检索**，比只给固定的资料更值吗？

两者的答案都是同一个量：**Δ——在固定预算下，"已验证的算法进步"的差异**。这个 Δ 必须能归因：如果两臂用的是不同的评测器、不同的模型路线、或不同的预算口径，Δ 就不可解释。

### 1.2 实验链与当前位置

```
A-1   冻结评测器身份（canonical EvalContract）        ✅ 已完成并通过独立审计
A0.1  四套 runtime 是否忠实执行同一个冻结评测器        ✅ 已完成（结论见 §2.6）
A0.2  各 runtime 是否按它声称的选择语义消费分数        ✅ 已完成
A1    选出后续实验的 substrate（实验台）              ⬅ 本阶段，未开始
B0+   正对照：外部工件能被这个 substrate 利用吗（通道存在性）
B0    普通外部既有实现是否提升搜索（H_A）
B1    主动开放世界检索是否值得（H_O）
```

**关键点：A1 不测假设。A1 选实验台。** 它的产物是"哪一套搜索运行时可以作为后续 H_A/H_O 实验的载体"，判据是**测量链是否成立**，不是"谁更聪明"。

### 1.3 为什么要选任务

A0 用的是我们自己的"plumbing（管道）任务"（圆的堆叠），它的评测是闭式公式，选它只为**验证管道通不通**。它对 A1 **不合适**，两条理由：

1. **它快打满了**：基线 0.25，极简基线已到 2.54–2.63，目标 2.635，已知网格最优只高约 5.7%。在快打满的任务上测出"没提升"，无法区分"方法没用"与"没余量可赚"——阴性等于零信息。
2. **它是 plumbing，不是科学任务**。

## 2. 已经建成的测量链（你只能用这些，不能假设更多）

这一节是硬事实清单，决定了哪些任务**在原理上可行**。所有结论都有本机实测支撑，由两名独立验证者复核。

### 2.1 冻结的评测器身份

- 我们为任务定义了一个**外部**（在 runtime 之外）的评测器 `E*`，它的身份是：
  `EID* = H(EvaluatorSource, DependencyLock, DataManifest, Config, MetricDefinition)`，五个分量各有可复算哈希。
  当前值：`664115e0d63ad2e1113559e1bc4d4a47042daf1131c9a9b2b9d6c868d75e9328`。单项输入变更只改对应分量。
- **重要**：`E*` 是**我们自己实现的**规范评测器，不是上游示例里的那份。理由：上游那份与 runtime 实际加载的那份差 1 ULP，且无法表达 `invalid`/`error` 两种判定。
- 冻结的候选集 `C*` 有 14 个成员：5 个 `ok`、4 个 `invalid`、5 个 `error`；内含一对**位相同但内容不同**的候选、一对近并列（Δ=1e-4），最大—最小可判定间隔 = `2.2019205208433132`。
- 评测器必须满足三条硬约束（协议要求，也是我们实测的）：**不依赖 cwd/PATH**、**不把计数/日志写进会被还原的目录**、**输出可以是多字段**（收敛成单标量是 runtime 侧的事）。

### 2.2 A0.1 / A0.2 的含义

- **A0.1**：对每个候选，runtime 的评测结果必须等于 `E*` 的结果 ± ε；对 `invalid`/`error` 候选必须**按判定**一致，而不是记成 `0.0`。这条的意义是：防止"把崩溃静默算成 0 分"这类假绿。
- **A0.2**：分数必须真的进入搜索的选择逻辑（例如 KAPSO 是"父代取最大"、EvE 是 rank 加权采样、Loreley 是 QD 归档同 cell 替换）。各 runtime 的语义不同，所以检验连同配置条件一起冻结。

### 2.3 身份必须由 harness 度量（最近一次加严）

我们原本让适配器**自述**"我用的评测器是 `E*`"。一个故意构造的反例证明这不可靠：存在 `E' ≠ E*`，它在 `C*` 上**逐位与 `E*` 一致**，却通过旧检查器。

现在改为：harness 从自己的评测 sweep 签发每候选一个**计量令牌**（绑定候选字节、`EID*`、评测参数、行为摘要、运行 nonce），适配器行必须回显令牌并声明身份，**缺失即不接受**。

**残余风险（很重要，写在这里是为了让你不要把 A1 的数字当成"已证明"）**：绑定值在冻结的参考表里是公开的，所以一个**照抄令牌绑定值**的 lane 仍然能通过。真正的关闭方式是"由 harness 拥有评测调用"，那会改变 A0.1 所测的问题，尚未采纳。

### 2.4 封闭性（"没有自主外部获取"）

协议要求：**用探针证明**，不能只说"配置里关了"。我们已有可复用的探针与一个可用的零 root 拓扑：docker `--internal` 网络 + 一个双宿主白名单代理；实测两对照成立（未白名单的出不去、白名单的进得去），且四套 CLI 都在封闭网络里跑通过真实轮次。

**边界（不要高估）**：代理本身是可信软件而非内核规则；宿主机可以直连容器 IP 绕过；目前只验过文本轮次与一次完整工具轮。四套 runtime 的封闭性判定是 **CONDITIONAL**（只有我们自建的 SimpleLoop 是 CLOSED）。

### 2.5 模型路线与成本口径

- 可用的模型入口是 **DeepSeek**：`https://api.deepseek.com`（OpenAI 兼容）与 `/anthropic`（Anthropic 兼容）；`deepseek-flash` 为主、`deepseek-v4-pro` 允许混用，**OpenRouter 已排除**。`/v1/responses` 可用，所以基于 codex 的 lane 也能用。
- 四套 runtime 的 agent lane 都是 CLI（`codex` / `claude` / `opencode` / `kilo`）+ 我们自己的适配层。
- **三个 CLI 自报的成本都不可信**：claude 的 `total_cost_usd` 对 DeepSeek 高 10–20×；kilo/opencode 一律报 `$0`；KAPSO 的 `node.cost_usd` 恒为 0。**因此 token 上限只能在代理层计量**——我们的封闭拓扑里正好有一个必经代理，这是天然的计量点。
- 实测成本量级（供你做预算设计）：一次极简 codex 调用 ~1 万 token；一次 EvE 真实 agent 轮次 ~28 万秒级墙钟、~5.9 万 token；KAPSO 两轮 campaign 合计 22,447 token、每轮约 20 秒（另有一次 636 秒的异常值）。
- 机器：RTX 3050 6 GB 显存、容器内**无 GPU**；30 GB 内存；Docker 可用、无需 root 的隔离手段只有 `docker --internal` / `docker network none` / `unshare -rn`。

### 2.6 四套 runtime 的现状（A1 的候选实验台）

| runtime | 是什么 | 当前 A0.1 状态 | 其他 |
|---|---|---|---|
| **SimpleLoop** | 我们自写的极简基线：提案→评测→取最大 | **接受**（14/14 且已按新标准接线） | 封闭性 CLOSED；有真实模型轮次记录 |
| **KAPSO** | 第三方开源框架（有注册化评测、双 lane） | 不接受：`MISSING_ATTESTATION`（数字仍 14/14 一致） | 有**已验证的两轮真实 campaign**；封闭性 CONDITIONAL；它的分数必须由**会话内部**产生 |
| **EvE** | 第三方开源框架（共同进化 solver 与 guidance） | 不接受：同上，且 A0.1 是 **5/14 实测 + 9 个声明合成** | 评测接口无法表达 `invalid`/`error`；bridge 仅 ATTEMPTED；封闭性 CONDITIONAL |
| **Loreley** | 第三方开源框架（QD 归档 + 多目标） | 不接受：同上 | bridge ATTEMPTED；封闭性 CONDITIONAL；接线成本最低（评测插件是我们自己的 Python 模块） |

**"不接受"的含义**：不是它们测错了（数字都一致），而是它们还没交身份证明。这是**我们主动调严的标准**。

## 3. 选择 A1 任务的硬约束

### 3.1 评测器必须可冻结（最重要的约束）

任务必须能提供一个**确定、便宜、无副作用、可固定实现**的评测器，供我们冻结成 `EID*`。具体要满足：

- 存在一份**可哈希的评测实现**（源码级，能固定到具体文件与提交）；
- 存在**可哈希的数据/输入清单**与**配置**；
- 指标定义可写成文本并哈希；
- 评测**无外部依赖**（不联网、不依赖隐藏测试集、不依赖排行榜、不需要训练模型）；
- 评测能区分**真零分**与**评测失败**（`invalid` / `error`），而不是把两者压成同一个数；
- 单次评测足够便宜，可以在一轮 experiment 里被调用几百上千次。

**因此直接排除**：隐藏测试集的 benchmark、需要训练才出分的任务、依赖外部服务/排行榜的任务、评分含随机性或人工判断的任务。

### 3.2 余量、正对照、难度、成本

- **有真实改进余地**：否则阴性不可解释（§1.3）。
- **存在一个已知有效的外部工件**（正对照）：必须能找到一个"我们**已有证据**知道它能改善这个任务"的外部实现，用来先证明注入通道存在（B0+）。找不到就做不到正对照。
- **难度超过单次会话**：否则 agent 一轮写对就做满，测的是"一次性写码能力"而不是搜索机制。
- **单次评测便宜**：预算要固定，评测要反复调用。

### 3.3 必须与 A0 的 plumbing 任务不同

交接明确要求"A1 换独立任务"。否则等于用被调过参数的任务去挑实验台，自我印证。建议：**A1 的任务与最终 B0/B1 的任务同族但不必同一个**；最好不同，以免把实验台的选择过拟合到评测任务上。共同点只需是同一 genre：**算法改进，目标可判定**。

## 4. 需要你设计的预算与统计口径

### 4.1 硬预算向量 `B_hard`

我们倾向的构成是 `(T_wall, N_evaluatorCalls, C_LLM, P_concurrency)`，其中 `C_LLM` 是**模型 token/费用上限**。理由：只限墙钟与评测次数不够——不同 runtime 完全可能靠多花 5 倍 token 换优势，那"固定预算"这个前提就失效了。

**原则（请遵守并检查我们是否违反）**：**预算约束资源，不约束内部算法行为。** 不要规定"每套必须生成 10 个候选""必须做相同次数的反思"——那会把不同的搜索机制强行改造成同一个算法。

### 4.2 重复数与功效

搜索过程是随机的（LLM 采样未播种，runtime 内部 RNG 也未播种）。请给出：最小必要的 campaign 重复数 `R`、你建议的统计量与判据、以及"在什么精度下这个 R 才有意义"的说明。若你认为 `R` 与 `C_LLM` 需要权衡，请明确写出权衡曲线（我们观察到一次两轮 campaign 约 2.2 万 token、每次评测是本地 CPU，所以重复的**现金成本可能远低于直觉**——但请你独立核算，不要照抄）。

### 4.3 正对照与执行顺序

- **正对照**：给出"如何构造一个已知能改善该任务的工件"的具体做法与通过判据（例如：某外部既有实现本身就该比初始解好 X%）。
- **交错执行**：请给出各臂的执行顺序方案，使**服务端模型漂移/负载/时间变化**成为 block effect 而不是 runtime effect。这不是理论顾虑：本机实验期间发生过 relay 中断、外部改写配置导致模型 id 变化（`gpt-5.6-sol`→`gpt-5.6-terra`）、容器随重启消失。
