门类说明:凡"钱、token、时间、效率"相关的材料都收在这里,不再散落在各文件里。三条纪律先写在前面,因为它们都已有过代价:

## 1. Φ_θ 的实例:三个 provider 三张价目表

计价被写成一个独立映射 `C = Φ_θ(m)`,θ = provider / model / pricing policy。已核的三张:

### 1.1 DeepSeek(【已核】2026-10-08 抓 `api-docs.deepseek.com/quick_start/pricing`)

原文:「**Off-peak rates are half of the peak rates. Peak hours are 01:00 - 04:00 and 06:00 - 10:00 UTC, Monday through Friday, excluding Chinese public holidays.** All other hours are off-peak, including weekends and Chinese public holidays in full.」

USD / 1M tokens:

| | deepseek-flash | deepseek-v4-pro |
|---|---|---|
| 输入·**缓存命中** 低谷/高峰 | 0.003 / 0.006 | 0.022 / 0.044 |
| 输入·**缓存未命中** 低谷/高峰 | 0.15 / 0.30 | 0.66 / 1.32 |
| 输出 低谷/高峰 | 0.60 / 1.20 | 1.98 / 3.96 |

同页还写明:`deepseek-v4-flash` 是**已退役的遗留名**,仍被接受、请求由 DeepSeek-V4.1-Flash 服务、**按 Flash 价计费**。
⇒ **名字 / 被服务的模型 / 价目是三个可分离的层** —— 这是"计费是一张映射表"的活样本(本机 `settings.json` 用的正是这个遗留名)。

### 1.2 qianwen Token Plan(【已核】2026-10-06,出处:`related_files/1006/model_society_as_allocation.typ` §2.2)

Credits 是计量单位、**月度硬上限、超限停机、不结转**;boost 包 ¥100 = 20,000 Credits ⇒ 影子价 **¥0.005/credit**;**并发是合同条款**(Lite→Pro 1–2 / 2–3 / 3–4 / 6–8 agents);**夜间 22:00–08:00 命名模型 0.4×/0.5×**。
⇒ **这也是 TOU**,且与 DeepSeek 的窗口不同 ⇒ 同一份 token 向量在两家、不同钟点,钱数都不同。

### 1.3 GLM-5.2 公开价(【已核】2026-10-07,Zhipu 一方)

¥8 / ¥28 / ¥2 per M(输入 / 输出 / 缓存命中);**无峰谷**;thinking tokens **按输出计费**;1M 上下文不分档。
⇒ 第三张 Φ_θ,**不含时间维度** —— 所以"价目表是时间的函数"不是普遍性质,而是**逐 provider 的性质**。

**收进来的意义**:三张表说明 θ 至少有三个维度(provider、钟点、缓存桶),而"钱"是它们之上的派生量。⇒ 任何跨时间比较都必须先问 θ 是否变了。

## 2. 三层架构:测量 / 策略 / 计价

来自用户 2026-10-08 在项目对话里新开的一轮。他的原话:

> 我之前有做bess优化,我想到一个很像的例子,tokens是更可以被直接测量的量,就像bess里面的电气量,但是账单规则是允许变化的结构化数据,以适应随时可变的定价映射.你怎么看

对应关系(BESS → agent):

| BESS | agent |
|---|---|
| physical dynamics | **execution dynamics**(token / tool / state) |
| dispatch | **orchestration policy**(OPL routing) |
| market settlement | **economic settlement**(pricing map `Φ_θ`) |

底层只记可测、与定价解耦的量:`m = (N_input_tok, N_output_tok, N_cached_tok, N_tool_call, T_wall, T_GPU/CPU, N_requests, …)`;账单 `C = Φ_θ(m)`。
**架构边界**:ADA 负责测量真实资源流 `m_t` 与 outcome / state / trajectory;OPL 只决定怎么花 `a_t = π(s_t)`;**计价层 `Φ_θ` 既不属于 ADA 也不属于 OPL**。

**我加的两处限定**:

- **解耦成立的前提是"分类规则不变"。** 一个 token 落进哪个价目桶,由 provider 定义(缓存命中/未命中、reasoning token 是否计费、tool call 的计量单位)。⇒ **计量口径也要版本化**,不只价格。
- **可测 ≠ 可控。** 用户指出"tokens 的分布无法完全由本地决定" —— 我同意,但把它归位:可测性归测量层(那条禁令守得住),可控性归 OPL 的策略问题(方差与预算规划)。两者别混。

**一个具体的洞(顺带发现)**:上一条对话提出的 OPL 动作集是 `{继续、批处理、并行、取回上下文、验证、重试、停止}` —— **没有"排到低谷时段"**。有了 TOU,调度就是一条合法的优化动作,并制造出**墙钟 ↔ 金钱**的显式权衡(为省 50% 而推迟,花的是被列为约束的墙钟)。

## 3. 两个效率口径(不要混)

| 口径 | 定义 | 适用 |
|---|---|---|
| 资源效率 | `η_token = Q / N_token` | **跨时间比较**(价目不进入分子分母) |
| 经济效率 | `η_$ = Q / Φ_θ(m)` | **部署决策**(含当时的真实价目) |

理由:provider 一次降价 50%,agent 一行未改却会显得"效率翻倍" —— 那是 θ 变了,不是系统变了。

## 4. 「Never persist money without persisting the underlying meter readings」的三次独立来源

原话(该轮回复):**Never persist money without persisting the underlying meter readings** —— 「可以存账单,但绝不能只存账单」。

| # | 来源 | 表述 |
|---|---|---|

| 2 | 本文件的 §1–§2(BESS/TOU) | 价目是可变结构化数据 ⇒ 只存钱无法解释"为什么这次贵" |

**更正(2026-10-08,外部复核指出,我核过)**:此前本表还列了冲突 `bench-validity` 作第二个来源 —— **那是误归属**。`bench-validity` 的原文要求的是*结果携带有效性条件*(报成元组:倍数、CI、硬件、基线、正确性覆盖、隐藏鲁棒性、重放稳定性),它**不**要求保存账单底层的计量读数;两者是**相邻但不同**的命题。故当前只有**两条**来源。

⇒ **两条来源**指向同一条规则(是否真"独立"另有一个限定:来源 1 那份报告是由**读过本项目 D 线报告**(`filecite turn29file0`)的同一会话产出的,故"独立"只指*不同的祖先文本*,不指*不同的知识来源*)。**按项目方法这是 `r`(独立再证)候选**,但**尚未登记**(升格需用户裁定)。
**强更强的一点**:TOU 让同一条 token 轨迹在高峰期贵 2×、缓存桶差 50× —— 只存钱会把"换了个钟点"记成"效率变了"。

## 5. harness 经济学:与价目无关的"过程层"成本(【转述】来自两条已入库对话)

| 证据 | 内容 |
|---|---|
| **Scaffold Effect**(固定模型、50 个 Terminal-Bench Pro 任务、300 次) | 通过率只差 **0–8pp**、多数 CI 含 0,但**每题解决的 token 差约 40×**(Goose 28k–37k vs OpenCode 1.15M–1.55M);平均轮数只差约 1.2× ⇒ 钱花在**每轮上下文膨胀、工具序列化、历史重发、空转轮**(OpenCode 2.0–2.16 no-action turns/task vs Goose 0.2–0.3) |
| **`T_solved = ΣT_i / Σ1[pass_i]`** | 墙钟宜按"每题解决"计,而非平均每题耗时 |
| **LoopX LHTB 三臂** | Plain 0.4218 / $213 / **7-of-46**;Heartbeat 0.4948 / $552 / **7-of-46** ⇒ mean reward +17.3% 而严格通过数不变;单题 $4.63 → $11.99 |
| **METR 受控长程对比** | 产品级 scaffold 相对简单 ReAct/Triframe **无统计显著**视野优势(50.7% / 14.5% bootstrap) |

**两个可落地的杠杆**:①**排程**(低谷/夜间窗口);②**缓存友好**:把稳定前缀放前面,让后续输入落进 cache-hit 桶 —— DeepSeek 该桶比 miss 便宜 **50×**(这一条是官方挂牌价,可直接用),Token Plan 的 max 缓存价 33.3 vs 输入 1737 cr/M(≈52×,**但这是条件点估计** —— 见 §6:它依赖未检验的线性与取定参数 d=0,不能当作已验证的调度收益)。本机 qwen-code 的提示组装已经是「多层 section + 稳定前缀作 cache 锚」⇒ 提示结构是**价目桶分配**问题,不是风格问题。

## 6. 我们自己的计量记录:它就是 Φ_θ 的标定(以及它的残余不确定性)

`related_files/1006/credit_meter_calibration.typ` 是对 **Token Plan** 的 `Φ_θ` 标定:平台倍率 `k`、缓存率、图像费率 `d`。它已记下的边界与本文件直接相关:

- **线性是假设、不是已验证的结论**;两方程在取定 `c = 3a` 与 `d = 0` 后才解出两未知数;`d` **未被识别**(只有非负上界);无非拟合留出检验。
- glm-5.2 的 `k ≈ 0.735` 与 max 的 `k ≈ 0.724` 相符**不是独立证据**:glm 的净 credits 由周期总量**减去 max 的贡献**得到,扣减误差被放大 **8.42×** ⇒ 「k≈0.73 是平台级倍率」是**与数据相容的假设**。
- ⇒ 与我 §2 的限定合起来:**这份标定本身就是"计量口径不确定"的实例** —— 它标定的是 θ 里的率,而口径(哪些 token 算哪一类)是另一层,需要单独版本化。
