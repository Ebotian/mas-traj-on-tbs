1. 从你们已有任务中选一个：基线可重跑、产物可保存、正确性可独立检查、单次运行便宜。优先利用已有载体；先查它是否合适，不预设必须换掉。

**交付物：**一个启动命令、一组固定样本、一张逐运行结果表。

**原因：**这一步会告诉我们，当前瓶颈究竟是判据、接线还是生成能力。它并不要求先完成整个验证器研究，也不要求同时支持两个 harness。

### 2. 先比较“信息”与“编排”：哪一个更值得买？

目前材料中一个很值得追的启发是：**编排看起来无效，可能是因为执行者缺少必要操作信息；编排看起来有效，也可能只是它顺带补齐了信息。**

可以做一个小型交叉实验：

|  | 最简执行循环 | 增加一次检查与修正 |
|---|---|---|
| 只有任务说明 | A | B |
| 补充接口、环境和验证方法 | C | D |

**具体执行：**

- 固定模型、任务、预算及最终评分器。
- 补充材料只包含可合法获得的操作信息，不含参考答案；记录制作成本。
- 四格使用同一批任务，多次运行；先看逐任务结果，不急着合成总分。
- 比较信息效应 `C−A`、编排效应 `B−A`，以及交互作用 `(D−C)−(B−A)`。

**原因：**这比直接比较两个完整 harness 更容易解释。若只有 D 有效，说明信息与编排互相依赖；若 C 已接近 D，复杂编排可能暂时不是主要投入方向。

### 3. 把多模型问题拆成两问：有机会吗？能提前认出来吗？

我认为这是目前最有研究价值的一条。**“另一动作事后更好”与“当时能选中它”之间，可能正是整个路由研究的难点。**

**具体执行：**

1. 从真实运行中保存一小批决策检查点。
2. 在相同状态下比较三个动作：继续当前会话、同模型重新尝试、换模型尝试。
3. 先做离线分支实验：给各动作明确的增量预算，记录独立最终评分及费用、墙钟。
4. 再只用动作发生前可见的信息，预测该选哪个；按原任务划分开发集与留出集，不能把同一任务的分支拆到两边。
5. 对照最好的固定动作，计算选择器扣除判断开销后的收益。

**原因：**它会区分三种完全不同的状态：

- 没有值得利用的动作差异；
- 有差异，但现有信息辨认不了；
- 能辨认，而且收益超过判断成本。

第三种才值得继续做在线路由。前两种也很有信息，不必被记成“模型组合失败”。

Elo 曲线可以提供观察角度，但我们不必先相信某个通用停止阈值。

**具体执行：**

- 在几个预先指定的检查点，分配相同的额外预算给：
  1. 延长当前会话；
  2. 从头开启同模型新会话；
  3. 从冻结状态开启新分支。
- 三种方式都保留历史最佳产物，并通过同一个独立评分器选择可交付结果。
- 记录每笔增量预算得到的改善、成功概率和等待时间；把启动、恢复、选择成本算进去。
- 在一批任务上提出停止规则，再用另一批任务检验。

**原因：**“继续变慢”不等于“重启更划算”。重启可能丢失有价值状态，也可能摆脱错误方向。这个实验直接比较可执行动作，甚至能帮助解释：收益来自新随机性，还是来自摆脱旧上下文？

它也能与方向 3 共用检查点和日志，减少重复建设。

- 给恢复后的执行者同一组问题：当前目标是什么、哪些尝试已失败、哪个结论被撤回、下一动作依赖什么证据。

**原因：**最终成功率相同，可能掩盖不同的记忆损伤。检查点实验能先定位损伤在哪里；但它只测试你预先列出的信息需求，不能据此证明一般意义上的“状态充分”。

G_H=
\mathbb E_H\!\left[\max_a\mathbb E[U_a\mid H]\right]

其中 \(H\) 只含决策前可见信息；不是直接使用 \(\mathbb E[\max_a U_a]\)。这里的 \(U\) 需要预先定义，或者分别在固定费用／时间约束下比较成功率。

建议把这次实验定义为：

> **在统一模型池、工具、信息与预算下，任务开始时配置多智能体系统，与执行中逐步选择模型，分别能带来什么收益？收益来自针对状态的选择，还是仅来自更多计算或不同模型使用比例？**

下面给出可执行的 **v1 实验协议**。论文事实与我的设计建议分开说明；样本量、预算和阈值都是实验设计参数，不冒充论文结论。

**1．先明确两篇论文分别承担什么角色**

| 论文 | 主要控制对象 | 本实验中的作用 |
|---|---|---|
| [MasRouter，2502.11133](https://arxiv.org/abs/2502.11133) | 根据任务选择协作模式、角色及模型配置 | 检验“任务级系统配置”的价值 |
| [EvoRoute，2601.02695](https://arxiv.org/abs/2601.02695) | 根据历史经验，在执行的各步骤选择模型 | 检验“执行中模型选择”的价值 |

MasRouter 使用级联控制器构造系统，并通过性能—成本反馈优化；官方仓库已经公开。EvoRoute 使用经验检索、Pareto 过滤及随机选择机制。**直接比较两套完整系统，不能把差异全部归因于路由粒度。**genui{"citation":{"refs":["turn13view0","turn13view2","turn12view2"]}}

因此分两层：

- **机制层**：固定协作结构与角色，只比较模型分配方法。
- **系统层**：允许 MasRouter 选择结构，比较完整系统及组合方案。

当前我能确认 MasRouter 仓库可访问；EvoRoute 的论文链接本次未成功取回，不能据此认定仓库不存在。若需要自行实现，必须标成 **“按论文重实现”**；修改了核心规则，则标成 **“EvoRoute-inspired”**，不能直接使用论文方法名报告成绩。

**2．实验任务：先代码，再真实仓库，不同时铺开所有基准**

推荐三层任务，各承担不同用途。

| 层级 | 数据集 | 用途 | 本轮地位 |
|---|---|---|---|
| L0 | MBPP+，必要时 HumanEval+ | 接线、评分器检查、低成本机制诊断 | 开发与桥接实验 |
| L1 | DS-1000 | 检验多步骤代码求解中的配置与路由 | **主实验** |
| L2 | SWE-bench Verified | 检验仓库状态、工具调用和长轨迹迁移 | 后续确认实验 |

选择理由：

- EvalPlus 提供增强测试，适合识别“简单测试通过、实际仍错”的产物；数据版本曾调整，所以必须固定版本和任务清单。genui{"citation":{"ref":"turn15view1"}}
- DS-1000 提供官方执行评分，按库划分任务，且与 EvoRoute 的评测对象有交集。它仍是代码生成任务；加入迭代循环后，应明确报告为 **“DS-1000 上的受控 agent 协议”**，不能直接与原始单次生成榜单混比。genui{"citation":{"refs":["turn14view1","turn13view3"]}}
- SWE-bench 的官方执行环境与评分流程适合最终验证，但运行成本高，不宜承担最初的调试。genui{"citation":{"ref":"turn14view2"}}

**数据划分建议：**

DS-1000 按其库类别分层，并尽量将近重复问题归为同组：

- TRAIN：约 200 题，用于控制器训练和经验库构建。
- DEV：约 100 题，用于超参数、预算和固定配置选择。
- TEST：其余约 700 题，封存。

实际分组后数量可以略变，输出最终 `split_manifest`。这是本实验自定义划分，不称为官方划分。

预算有限时，可以在打开 TEST 之前，从中固定抽取 200 题作为探索测试。**不能先看这 200 题结果，再决定是否追加到显著。**正式样本规模应由 DEV 上的方差估计和总预算提前决定。

MBPP+/HumanEval+ 用于开发后，不再称为完全未见的外部测试集。公共基准可能进入模型预训练；这里的“未见”仅指未用于本次控制器开发。

**3．统一实验环境与可见信息**

先固定一个共同执行器，不让 qwen-code、kimi-code 的其他差异混进首轮。

执行器需要：

- 相同文件、终端和 Python 执行工具；
- 相同初始任务文本和环境说明；
- 相同产物格式与最终提交接口；
- 相同上下文截断、超时和错误处理规则；
- 模型适配层只处理格式，不偷偷改变任务信息。

可以使用现有 harness 作为底座，但所有实验臂必须运行在同一版本上。

**固定三个角色：**

1. Planner：分析问题与提出方案；
2. Coder：生成、修改代码；
3. Reviewer：根据可见证据检查并提出修改意见。

固定结构 \(G_0\) 建议为：

\[
\text{Planner}\rightarrow\text{Coder}\rightarrow\text{Reviewer}
\rightarrow\text{Coder},
\]

最后一个修正步骤可因预算不足而不执行；是否允许提前提交必须各臂一致。

**严格区分两种测试：**

| 测试 | 执行过程中可见？ | 用途 |
|---|---:|---|
| 题目公开示例、agent 自写测试 | 是 | 运行中修正与选择 |
| 官方最终测试、参考答案、隐藏断言 | 否 | 实验最终评分 |

DS-1000 的 `code_context` 包含评分和参考信息，不能原样放进 agent 工作目录；只提供题目允许的执行上下文。官方资料还提示部分任务存在进程状态影响，因此每题独立进程／环境执行。genui{"citation":{"ref":"turn15view2"}}

TRAIN 可以在一次轨迹结束后，把最终评分用于训练；DEV 用于选配置；TEST 的最终评分只进入实验报告，不回流到路由器。

**4．模型池：先固定三个，不把模型采购也变成实验变量**

建议三个具有不同费用／能力特征的模型：

- \(M_1\)：你们日常低成本主力；
- \(M_2\)：能力更强、成本更高的模型；
- \(M_3\)：另一模型家族，用于检验互补性。

具体型号在本地 API 可用性检查后固定，不先假定“参数更多就是更强”。

每个模型登记：

- 精确模型 ID、提供商与路由地址；
- 推理模式、温度、输出上限；
- 上下文容量及统一使用的有效上限；
- 输入、缓存、输出、工具等计费口径；
- 是否允许固定种子；
- 测试日期与价格版本。

**模型池冻结后，所有实验臂相同。**不支持某项功能时，应统一禁用，或将差异作为明确的实验条件。

先在 DEV 的 20–30 题上运行单模型基线，得到费用和耗时量级。这一步用于校准预算，不用于挑选 TEST 上表现好的模型。

**5．实验臂：六个主体，两个针对性诊断**

| ID | 协作结构／角色 | 模型分配 | 回答的问题 |
|---|---|---|---|
| B-Homo | 固定 \(G_0\) | 所有角色使用同一个 DEV 选定模型 | 多角色但同模型能做到什么 |
| B-Fixed | 固定 \(G_0\) | DEV 选出的固定角色—模型映射 | 简单静态异构是否已经足够 |
| M-Role | 固定 \(G_0\) | MasRouter 的模型分配部分，任务开始时决定 | 任务条件的角色分配是否有效 |
| E-Step | 固定 \(G_0\) | EvoRoute 逐步骤选模型 | 执行中选择是否值得 |
| M-Full | MasRouter 选择结构、角色和模型 | 任务级配置 | 完整 MasRouter 的系统价值 |
| Hybrid | MasRouter 选择结构和角色 | EvoRoute 负责逐步骤模型选择 | 两个层次是否互补 |

两个需要明确的限定：

- **M-Role 是消融版本，不是完整 MasRouter。**
- Hybrid 中，MasRouter 的模型分配阶段不参与决策；不能再把收益解释成“完整 MasRouter 加完整 EvoRoute”。

为防止“多花计算”造成假优势，再加两个诊断：

**B-Resample：同模型多试。**  
在相同总预算下生成多个候选，用同一个公开测试／选择协议提交一个结果。隐藏最终测试不得用于挑候选。它不属于主体结构比较，但必须出现在资源公平性分析中。

**B-Mix：内容无关的模型混合。**  
在 DEV 上估计 E-Step 的模型使用比例，TEST 上按该固定比例随机选模型，且不读取任务内容。若 E-Step 只胜过便宜模型、却不胜过 B-Mix，尚不能把收益归因于针对状态的选择。

按角色分层的随机比例可以进一步控制“某个角色通常用强模型”这一因素。

**6．先注册假设，再跑数据**

以下建议设为两个主要假设，其他作为次要或探索性分析，避免事后挑胜出的比较。

| 假设 | 主要比较 | 可支持的结论 |
|---|---|---|
| H1：执行中路由有部署价值 | E-Step vs M-Role | 在固定结构下，整个逐步路由方法优于任务级模型分配 |
| H2：结构与角色自适应有部署价值 | M-Full vs M-Role | 放开结构与角色选择带来净收益 |
| H3：状态针对性有价值 | E-Step vs B-Mix | 收益不只是模型使用比例不同 |
| H4：组合有额外价值 | Hybrid vs M-Full、E-Step | 两个控制层次具有互补性 |
| H5：异构不是算力替代效应 | 最优候选 vs B-Homo、B-Resample | 收益不能仅由同模型多算解释 |
| H6：收益能迁移到仓库任务 | 冻结候选 vs 冻结基线，SWE-bench | 收益在该迁移条件下仍存在 |

注意：H1 即使成立，也不能单独证明“逐步决策这个粒度”是唯一原因，因为算法本身也不同。

为进一步定位，可增加 **E-RoleFrozen** 消融：仍使用 EvoRoute 的检索与选择机制，但每个角色首次选择后不再换模型。E-Step 与它的差异更接近“允许执行中重新选择”的价值。

**7．指标与判定标准**

每次完整运行记录：

\[
Y_{ir}\in\{0,1\},\qquad C_{ir},\qquad T_{ir},
\]

其中：

- \(i\)：原始任务；
- \(r\)：重复运行；
- \(Y\)：官方最终测试是否通过；
- \(C\)：所有运行中模型、路由、嵌入、工具等直接支出；
- \(T\)：从任务启动到最终提交／预算终止的端到端墙钟。

最终离线评分的耗时另报；如果某种验证在真实运行中被策略调用，其成本必须计入 \(C,T\)。

**主报告同时给：**

- 成功率；
- 所有运行的平均费用、平均墙钟；
- 费用与墙钟的中位数、P90；
- 超时、预算耗尽、工具错误、基础设施错误的比例；
- 路由器本身的费用与耗时占比。

不要只统计成功任务成本，也不要把 `pass@k` 当作系统实际提交一个答案的通过率。

**建议的工程验收阈值：**

以下是一套可直接预注册的默认值：

- 成功率允许下降不超过 **3 个百分点**；
- 平均费用至少降低 **10%**；
- 平均墙钟增加不超过 **10%**。

令新方法与基线的差异为：

\[
\Delta p=p_{\rm new}-p_{\rm base},\quad
R_C=\frac{\bar C_{\rm new}}{\bar C_{\rm base}},\quad
R_T=\frac{\bar T_{\rm new}}{\bar T_{\rm base}}.
\]

“经济型改进”要求同时满足：

\[
L(\Delta p)>-0.03,\qquad U(R_C)<0.90,\qquad U(R_T)<1.10.
\]

这是一项**工程选择标准**，不是“数学上必须如此”。若你们不能接受任何成功率损失，就把 \(-0.03\) 改为 \(0\)，但样本需求通常更高。

判定分三类：

- **支持**：置信区间整体满足预注册条件；
- **不满足该工程目标**：某一条件的区间整体落在不接受的一侧；
- **未决**：区间跨越边界。

“未显著下降”不能替代成功率非劣检验。H3 则应另检验针对性收益，不能仅凭模型占比接近就宣布成立。

**8．预算设置：同预算上限，不强迫同样花完**

用 DEV 单模型基线校准，不凭空设美元值。

设：

- \(c_0\)：B-Homo 在 DEV 上每题费用的中位数；
- \(t_0\)：对应墙钟中位数。

探索阶段检查三档共同预算：

| 档位 | 每题费用上限 | 每题墙钟上限 |
|---|---:|---:|
| 紧 | \(c_0\) | \(t_0\) |
| 中 | \(2c_0\) | \(2t_0\) |
| 宽 | \(4c_0\) | \(4t_0\) |

在 DEV 上选定**一档作为主要测试条件**，其他档位若要正式检验，必须预先分配样本与统计检验额度。

费用到顶或时间到顶即终止，并提交当前可交付产物。没有有效产物记失败。模型调用前应检查剩余预算，记录不可避免的单次请求超额。

并发与缓存也要固定：

- 主机制实验先固定最大并发数，例如 1，减少调度混杂；
- 并行结构的部署收益另跑统一并发上限下的系统实验；
- 每个任务使用独立会话；任务内自然缓存可以保留；
- 禁止某实验臂复用另一实验臂生成的答案缓存。

**9．训练与经验库构建**

**MasRouter：**

1. 先跑通官方实现的最小例子；
2. 确认论文中的三个控制部分确实参与训练和推理；
3. 使用 TRAIN 中的任务与最终评分训练；
4. DEV 选择检查点与成本权重；
5. TEST 前冻结参数。

**EvoRoute：**

1. 用 TRAIN 任务收集探索轨迹；
2. 保存角色、模型、决策前状态、工具执行、费用、耗时与最终结果；
3. 构建检索和选择机制；
4. 在 DEV 调整检索、权重与稀疏数据回退规则；
5. TEST 前冻结经验库。

尤其注意：

- 工具执行成功不等于任务正确，两个字段分开；
- 当前任务的最终结果在决策时不可见；
- 当前步骤实际用了哪些工具，在选择模型前不可作为输入；只能使用已发生历史或事前预测；
- 无匹配记录、只有一个观测、方差为零时，必须有明确回退规则，不允许产生未定义后验或静默默认值。

EvoRoute 原文的经验记录含任务最终结果，且存在专门冷启动过程，所以**经验构建成本与信息时序必须审计**。genui{"citation":{"ref":"turn13view4"}}

**训练资源公平性：**

两种方法设置相同的训练任务范围、最高环境 rollout 数和费用上限，先到者停止；同时报告实际消耗。原方法若在该预算下没有收敛，结论是“此训练预算下的表现”，不能推广为方法无效。

超参数搜索也计入训练成本。建议首轮每种方法最多 6 组配置；若开发过程超出，完整登记，不只保留胜出的配置。

**10．按阶段执行，避免一开始花掉全部预算**

**阶段 A：实现与评分器验收**

准备 12 个固定产物，包含正确、边界错误、格式错误与伪造完成说明。

检查：

- 正确产物能被接受；
- 已知错误被拒绝；
- 自述改变不影响相同产物的最终评分；
- 超时、执行异常与不正确分开记录；
- 隐藏测试、参考答案不出现在模型输入和检索库；
- 费用日志可以逐请求加总回总账。

通过后才开始真实模型实验。

**阶段 B：低成本桥接**

在 MBPP+ 上固定 40 题，每臂重复 2 次。

六个主体臂共有：

\[
40\times6\times2=480
\]

次系统运行。它用于发现接线问题、预算不足、结构退化和指标饱和，**不承担微小优势的确认**。

若所有方法几乎满分，或者几乎全失败，应调整开发协议后再冻结主实验；不能到 TEST 才改。

**阶段 C：DS-1000 开发**

完成 TRAIN/DEV 的训练与校准。

输出并冻结：

- 六个主体臂配置；
- 主要预算；
- 主要假设与阈值；
- TEST 样本清单；
- 运行顺序；
- 分析脚本。

**阶段 D：主测试**

建议每题每臂重复 3 次。重复用于估计随机运行波动，不能把同题三次当作三个独立任务。

- 200 题探索版：\(200\times6\times3=3600\) 次；
- 700 题完整版：\(700\times6\times3=12600\) 次。

以上不含训练、诊断臂与消融。预算不够时，应在测试前缩减假设和实验臂，而不是测试后只保留好看的比较。

每个任务的不同臂随机交错运行，避免某个方法集中在高峰期或低谷期。提供商故障按预注册规则重跑整个相关配对块，保留原始失败记录和实际费用。

**阶段 E：诊断与迁移**

主结果之后：

- 用新的开发数据定位失败原因；
- 冻结候选和基线；
- 在 SWE-bench Verified 上进行一次独立迁移实验。

若使用该基准的一部分做适配，剩余部分才是本次未见测试。不能把适配后的子集成绩直接包装为完整官方榜单成绩。

**11．统计分析：以任务为单位，允许结论是“未决”**

主要分析按任务分组：

1. 对同题重复运行先求平均；
2. 计算配对成功率差、平均费用比、平均墙钟比；
3. bootstrap 时整组重采样任务，保留该题全部方法与重复运行；
4. 按 DS-1000 库类别分层，保持预注册权重；
5. 报告逐库结果，整体平均不能掩盖某类明显退化。

H1、H2 各有三项主要指标，共六项。可以使用保守且易实现的方案：

- 为六项构造各自约 **99.17% 的双侧区间**；
- 用 Bonferroni 控制整体覆盖率至少约 95%；
- 按前述边界作支持／不满足／未决判断。

不要保证 200 或 700 题一定足以检验 3pp 非劣界限。举例：若配对成功／失败不一致的比例约 20%，即使 700 个独立任务，单次配对成功率差的普通 95% 区间半宽也可能约 3.3pp，尚未计多重比较。重复可以降低部分运行噪声，但不能创造新的任务多样性。

因此在 DEV 上用配对方差估计检验力，**先确定能付得起的精度，再封存样本量**。

---

**12．单独回答“有机会”与“能选对”**

主实验之外，从 DEV 保存检查点，进行小规模分支诊断：

- 相同状态；
- 相同增量预算；
- 分别续跑当前模型、同模型重试、换模型；
- 每个动作多次采样；
- 最终由独立评分器评分。

这里必须分开两项：

\[
G_{\rm realized}
=\mathbb E[\max_a U_a]-\max_a\mathbb E[U_a],
\]

与

\[
G_H
=\mathbb E_H[\max_a\mathbb E(U_a\mid H)]
-\max_a\mathbb E(U_a).
\]

前者包含事后挑中随机好运的收益；后者才对应事前信息可能提供的选择价值。

**验证方式：**

- 不用同一批随机结果既挑动作又评价动作；
- 一个采样批次用于估计动作价值，另一批次评价选出的动作；
- 选择器按原任务留出；
- 与最佳固定动作、内容无关混合分别比较；
- 给出选择器扣除自身成本后的实际收益。

这项诊断用于解释主实验，不用它替代完整动态测试。

---

**13．训练成本与部署成本分开结算**

每种方法报告：

\[
C_{\rm total}(N)=C_{\rm build}+N\bar C_{\rm deploy}.
\]

其中 \(C_{\rm build}\) 包括：

- 训练及探索；
- 经验库构建；
- 嵌入；
- 超参数搜索；
- 必需的数据标注或判定调用。

若新方法部署更便宜，给出相对基线的成本摊销点：

\[
N^*=
\frac{C_{\rm build,new}-C_{\rm build,base}}
{\bar C_{\rm base}-\bar C_{\rm new}},
\]

只在分母为正时解释，并且只有成功率满足预定要求后，才讨论这个经济优势。

墙钟应区分每题延迟与整个实验吞吐量；不能用高并发实验完成得快，替代单任务延迟改善。

建议将 **E-Decision 对 E-Native** 设为新增实验的主要比较；E-Chat 用于解释机制，置信度接管作为后续实验。

| 假设 | 比较 | 支持该假设需要什么 |
|---|---|---|
| H-D1：决策模型具有部署价值 | E-Decision 对 E-Native | 通过率非劣，同时总成本实质下降，时间不过度增加 |
| H-D2：专门决策服务优于通用模型决策 | E-Decision 对 E-Chat | 在相同输入下，任务结果不差，且决策开销或全任务开销改善 |
| H-D3：置信度可以用于选择性接管 | E-Gated 对前两者 | 开发集选定的阈值，在测试集仍能改善整体结果 |

沿用原方案的示例门槛，H-D1 需要同时满足：

\[
\begin{aligned}
\operatorname{LCB}(p_D-p_E)&>-0.03\\
\operatorname{UCB}(\bar C_D/\bar C_E)&<0.90\\
\operatorname{UCB}(\bar T_D/\bar T_E)&<1.10
\end{aligned}
\]

含义是：通过率下降不超过 3 个百分点、平均总成本至少降低 10%、平均时间增加不超过 10%，且不确定性也支持这些判断。

这些门槛应按你们的实际容忍度修改。区间跨过门槛就是**证据不足**；不能因为“没有显著变差”就宣布非劣。按任务聚类计算置信区间，多次运行不能当作独立任务；若把多个比较都列为主要结论，要同步调整多重比较方案。

同时报告一个开销分解：

\[
C_{\text{total}}
=C_{\text{执行}}+C_{\text{决策}}+C_{\text{状态构造}}+C_{\text{其他运行环节}}
\]

决策模型可能降低执行成本，却因每步调用增加总成本。这是需要捕捉的失败结果。

**6．置信度回退值得做，但应晚一步**

不要直接照搬文档示例的 `confidence ≥ 0.9`。该阈值是示例，官方也要求按误判成本调整。genui{"citation":{"ref":"turn19view0"}}

这里应测的是**覆盖率—任务收益—额外成本**关系，而不是只画“置信度高不高”。如果置信度不能区分有益与有害的接管，就不应将它用于控制权限。回退之前已经发生的决策调用，其成本仍必须计入。

- agent 可以运行题面示例、自写测试；不能访问最终隐藏测试。
- 所有方法面对同样的可见信息。

预算有限时，可事先从测试部分抽取 200 题。但这更可能得到“精度不足”，不能保证识别 3 个百分点的差异。

**3．统一执行环境**

采用三个固定执行模型 \(M_1,M_2,M_3\)，覆盖不同成本与能力特征。具体型号在接线阶段确定，记录完整模型标识、供应商和日期。

所有方法共用：

- 工具集合、权限与沙盒；
- 角色提示模板和上下文压缩规则；
- 公开测试与最终评测程序；
- 单任务金额、墙钟时间和最大步数限制；
- API 失败处理与产物提交规则。

固定协作结构建议为：

\[
\text{Planner}\rightarrow\text{Coder}\rightarrow\text{Reviewer}
\rightarrow\text{Coder 修订}
\]

在预先规定的条件与预算内重复审查—修订。所有固定结构组使用相同条件。

每个角色可以包含多次模型调用。“逐步选模”明确指：**每次执行模型调用之前选择模型**。

先使用一个共同运行器完成主实验，再把领先方案移植到 kimi-code 或 qwen-code；不要在第一阶段同时改变宿主和路由算法。

**4．实验组：共同基线、两个比较模块**

| 编号 | 方法 | 协作结构 | 模型选择 |
|---|---|---|---|
| B0 | 单模型基线 | 固定 | 开发集选定的一个模型 |
| B1 | 固定异构配置 | 固定 | 开发集选定的角色—模型映射 |
| B2 | 同模型多次尝试 | 固定尝试协议 | 同一模型，多次候选后选择 |
| M0 | MasRouter 固定结构消融 | 固定 | 保留适配后的模型分配机制 |
| M1 | MasRouter 完整版 | 可变 | 协作方式、角色、模型联合选择 |
| E0 | EvoRoute | 固定 | 原逐步选模机制 |
| E1 | EvoRoute + 通用对话决策 | 固定 | 通用模型选择下一执行模型 |
| E2 | EvoRoute + 千问决策模型 | 固定 | `decision-model-preview` 选择 |

B2 的候选只能根据公开测试或冻结的选择器筛选。不能用隐藏测试挑出最佳候选，再报告该结果。

**5．千问决策模型如何接入**

运行器在每次执行调用前构造状态：

```text
任务与本步目标
当前角色、当前产物
最近工具结果、公开测试反馈
剩余金额、时间和步数
候选模型的价格与历史表现
检索到的训练经验、样本数与不确定性
```

E2 使用 `choice` 返回候选模型标识。预算约束、合法选项检查、超时与回退由程序执行。

第一阶段只开放**选模权限**，不同时开放最终验收、修改测试或提前宣布成功的权限。

固定以下规则：

- 非法输出或调用失败：按预注册规则退回 E0。
- 重试次数与超时固定。
- 回退前已经产生的费用、延迟全部计入 E2。
- 没有历史证据的模型明确标为未知，不能伪造成功率。
- 状态构造若调用额外模型，计入其成本。

`probabilities` 是选项分布，不能直接当作各执行模型的任务成功率；`confidence` 也需要经验验证后才可用于接管阈值。

**6．先验证评测链，再比较算法**

第一项实际测量是对最终评测适配器做挑战测试。

从训练或开发题中选取约 30 题，每题准备：

1. 已知正确、可独立核验的产物；
2. 未实现要求的空白或未完成产物；
3. 看似合理但有明确语义错误的产物；
4. 只匹配题面示例、不能泛化的产物。

运行与主实验相同的最终评测路径，检查：

- 正确产物是否因环境、路径或封装错误被拒绝；
- 明确错误是否被接受；
- 超时、异常、空输出是否误计为通过；
- 重复评测结果是否稳定；
- 提交产物是否确实是被评测的那一个。

**任何已确认的适配器错误必须先修正。** 这批测试通过只证明检查过的路径正常，不证明验证器完美；报告挑战样本数与错误率，不写“已验证绝对可靠”。

**7．训练、调参与执行步骤**

| 阶段 | 具体操作 | 产出及进入下一阶段的条件 |
|---|---|---|
| A．冻结接口 | 定义状态、动作、日志、预算与评测接口 | 所有方法可接入同一运行器 |
| B．评测链挑战 | 执行上述正确/错误产物测试 | 已知适配器缺陷清零，保留剩余局限 |
| C．接线试跑 | 约 40 题，检查完整轨迹 | 无隐藏信息泄漏；调用与计量可追踪 |
| D．训练与经验收集 | 仅使用训练集 | MasRouter 参数与 EvoRoute 初始经验库 |
| E．开发比较 | 100 题开发集上调参与比较 | 冻结全部配置、主预算、样本量和主要比较 |
| F．正式测试 | 所有冻结方案跑独立测试集 | 一次性统计预注册指标 |
| G．消融与迁移 | 针对剩余问题追加实验 | 明确标为后续探索或独立确认 |

训练公平性分两层：

- 共用训练题与可访问的信息；
- 为每种方法设置相同的最大数据收集预算、调参预算，并记录实际消耗。

不要求不同方法执行完全相同的训练流程；方法本身的样本效率就是比较对象。若某方法在预算内未训练充分，也要如实报告。

主实验冻结经验库。持续在线更新另设实验，避免测试顺序成为隐含训练过程。

**8．预算、计量与停止规则**

在开发集上确定单任务主预算：

\[
B=(C_{\max},T_{\max},K_{\max}),
\]

分别表示金额、墙钟时间与模型调用次数上限。所有组共用相同上限，不要求花完预算。

低、中、高预算可做探索，但正式主比较只选一个预注册档位，避免同时扩张样本规模。

计量至少分开：

\[
C_{\mathrm{运行}}
=C_{\mathrm{执行模型}}
+C_{\mathrm{决策}}
+C_{\mathrm{检索与摘要}}
+C_{\mathrm{其他运行资源}}.
\]

另记训练、经验构建和调参成本 \(C_{\mathrm{构建}}\)，报告：

\[
C_{\mathrm{累计}}(N)
=C_{\mathrm{构建}}+N\bar C_{\mathrm{运行}}.
\]

保存原始 token、缓存命中、供应商计量、实际账单及计价版本。**不同模型的 token 不直接当作等价成本单位；无法可靠换算的套餐 credits 单列，不强行折美元。**

停止规则统一：

- 主动提交；
- 达到金额、时间或步数上限；
- 遇到预定义的不可恢复错误。

超时后评测截止前最后一个完整产物；没有有效产物则失败。预算内成功与否是可观察结果；如果额外分析“最终要多久才能成功”，未成功轨迹属于删失数据，不能记为恰好在超时时成功。

**9．主要假设与验收**

v2 建议只预注册两项主要比较：

| 假设 | 比较 | 能得出的结论 |
|---|---|---|
| H1：动态路由具有部署价值 | E0 对 B1 | 该动态系统是否优于固定异构配置 |
| H2：专门决策模型具有增量价值 | E2 对 E0 | 替换选择环节是否值得 |

其余为次要比较：

- M1 对 M0：改变协作结构与角色配置的贡献；
- E2 对 E1：专门决策服务与通用模型决策的差异；
- 候选方案对 B0/B2：是否优于同模型及同模型多试；
- M1 对 E0：完整方法的部署表现。

对 H1/H2，建议保留前述工程验收条件：

\[
\begin{aligned}
\operatorname{LCB}(\Delta p)&>-0.03,\\
\operatorname{UCB}(\bar C_A/\bar C_B)&<0.90,\\
\operatorname{UCB}(\bar T_A/\bar T_B)&<1.10.
\end{aligned}
\]

即：通过率下降不超过 3 个百分点，平均运行成本至少下降 10%，平均时间增加不超过 10%，且置信区间支持这些判断。

**这是一种部署偏好，不是唯一科学成功标准。** 若通过率显著提高但成本也提高，应报告新的性能—成本取舍，不能简单归为“算法失败”。同时给出完整三指标结果与 Pareto 图。

三种判定：

- 全部达到预注册门槛：支持部署价值。
- 明确跨向不可接受一侧：不满足该部署目标。
- 区间跨门槛：精度不足，未决。

**10．统计、样本量与运行规模**

每题建议运行三次，用于估计随机性；但独立统计单位仍是**任务**。按任务聚类、按库分层计算配对置信区间，不把三次运行当三道题。

开发结束后，根据观察到的配对差异与方差做功效模拟，冻结测试样本量。700 题也不保证足以确认 3 个百分点的非劣界限。

主要比较采用预注册的多重比较控制，例如 Holm 校正或同时置信区间。不得因为某一组结果较好，临时提升其为主要假设。

规模上：

- 八组 × 200 测试题 × 三次 = **4,800 条完整轨迹**；
- 八组 × 700 测试题 × 三次 = **16,800 条完整轨迹**。

因此，预算有限时建议采用两层安排：

1. 开发集上比较全部八组；
2. 正式确认优先保留 B1、E0、E2；若要正式声称优于通用决策，再保留 E1；
3. MasRouter 模块使用同一预封存测试集独立安排预算，未完成前不下胜负结论。

测试必须按题目分块、组间随机交错运行，减少供应商负载变化的影响。

**11．主实验之后才做的消融**

| 消融 | 检验的疑问 |
|---|---|
| 根据开发集模型使用比例随机选模 | 收益是否只来自多用了强模型，而非状态匹配 |
| EvoRoute 每个角色只选一次模型 | 逐步调整是否有额外价值 |
| E2 去掉检索经验 | 决策模型依赖真实经验，还是仅凭模型描述 |
| E2 低置信度退回 E0 | 置信度是否能支持选择性接管 |
| MasRouter 结构 + EvoRoute 逐步选模 | 两种机制能否互补 |
| 在第二个 harness 中复跑 | 效果是否依赖宿主实现 |

置信度阈值只能在开发集选择；测试时报告接管覆盖率、任务收益和总成本。高置信度不自动代表选择正确。

**HumanEval+ / MBPP+：先把实验仪器接对**

这类任务通常给出函数要求、输入输出约定或示例，让模型补全实现。例如：“实现一个函数，判断列表中的元素是否满足某种关系。”

“+”主要加强了测试：EvalPlus 在原 HumanEval、MBPP 的基础上增加测试用例，帮助发现只通过简单示例、却在边界输入上失败的代码。官方仓库也记录过题目和参考解修正，所以需要固定数据与评测器版本。genui{"citation":{"ref":"turn21view0"}}

我选择它们有三个原因：

- **运行成本低**：容易反复检查 API、代码提取、沙盒、超时和日志。
- **错误容易定位**：失败通常能追到具体函数或测试，便于检查评测适配器。
- **适合制造已知错误**：可以构造空输入、重复元素、边界条件等错误产物，检查验证器能否拒绝假进展。

预计先选约 40 题，覆盖不同题型。每组获得相同题目、公开示例和工具权限；agent 可以自写测试，提交后由独立进程执行增强测试。

它们主要回答：**我们的比较系统是否工作正常？增加审查、路由或决策调用，是否产生了可观察的开销与行为变化？**

它们不适合作为长程实验的核心。若大多数模型一次就答对，强行加入 Planner、Reviewer 和多轮修改，会主要测出编排开销。出现这种情况应保留为接线测试，而不是人为制造复杂轨迹。

**DS-1000：在可控成本下观察任务差异与模型选择**

DS-1000 包含 1,000 道数据科学代码任务，涉及 NumPy、Pandas、SciPy、Matplotlib、Scikit-learn、PyTorch 和 TensorFlow。任务提供代码上下文，要求补出满足要求的实现；官方评测包含执行检查，部分题还有代码形式检查。genui{"citation":{"ref":"turn22view2"}}

例如，任务可能要求：

> 对给定 DataFrame 分组、处理缺失值并得到指定结果。

这类题的价值在于：正确实现不只依赖通用算法，还依赖库 API、数据形状、索引语义和数值行为。

选择它作为第一轮主实验，是因为它提供了一个合理折中：

- 题目数量足以建立训练经验、调参和独立测试。
- 不同库和任务类型带来可观察的异质性，**有机会**检验模型是否各有所长。
- 可以让 agent 执行、观察报错和修订，产生真实的决策状态。
- 比完整仓库修复便宜，适合比较多个实验组。

不过，“存在异质性”不保证路由一定有收益。开发阶段必须先检查：三个执行模型是否真的存在稳定的相对优势。如果某个模型几乎处处更好且成本也低，路由收益可能很小。

预计这样使用：

1. 按库分层，并将近重复或同源变体放进同一划分，形成约 200 题训练、100 题开发、700 题测试。
2. 训练题用于收集不同模型的轨迹、结果、成本和时间；构造路由经验库或训练控制器。
3. 开发题用于选择固定模型配置、决策输入模板和预算。
4. 测试题在所有配置冻结后运行；经验库不吸收测试结果。
5. 每题独立进程执行，避免库的状态污染；固定 Python、依赖和评测环境。

这里的“训练集”指**我们训练路由器、构造经验库的划分**，不是默认微调执行 LLM。

需要特别隔离 `code_context`：它包含最终测试与参考解，不能放进 agent 工作目录。公开题面和示例可见，最终评测材料由独立评测端持有。官方也指出部分执行具有状态性，并承认可能存在少量标注或解释问题。genui{"citation":{"ref":"turn22view2"}}

我们在 DS-1000 上允许多步工具调用，因此应报告为：

> **基于 DS-1000 的预算约束多步 agent 实验。**

不能直接把成绩当作官方单次代码生成分数。也不能把一个题目的最终成功，直接归功于其中某一次路由选择；局部选择的价值要通过保存状态、分支续跑等额外实验检验。

**SWE-bench Verified：检验短代码上的收益能否进入真实工程**

SWE-bench 给 agent 一个代码仓库和真实 GitHub issue，要求生成解决问题的补丁。Verified 是其中经过工程师确认可解的 500 个实例；官方提供 Docker 评测机制。genui{"citation":{"refs":["turn22view1","turn22view0"]}}

它更接近你们的 kimi-code / qwen-code 使用场景。agent 往往需要：

- 找到相关文件与调用链；
- 理解现有实现和约束；
- 复现问题；
- 修改代码、运行测试；
- 根据结果继续修订。

因此，同一任务中会自然出现不同阶段：搜索、理解、编码、诊断、审查。这比短函数任务更适合检查**逐步选模是否优于固定角色分配**。

预计先做迁移实验，而不是让全部八组直接跑满 500 题：

1. 从完整集合预先按仓库分层抽取约 50–100 题，固定题目清单。
2. 用另外的不重叠实例调试环境；检查 Lite 或其他集合是否与正式样本重叠，不能只凭数据集名称判断。
3. 首轮保留固定异构基线、EvoRoute、EvoRoute＋决策模型，以及需要迁移检验的 MasRouter 方案。
4. 每题恢复到规定的基础提交，提供 issue 和原始仓库。
5. agent 可以运行原仓库测试和自写测试；参考补丁、评测测试补丁及目标测试清单留在评测端。
6. 最后按官方机制评测提交补丁，记录解决率、费用、时间、模型切换与失败原因。

官方数据结构包含参考补丁、测试补丁及 `FAIL_TO_PASS`、`PASS_TO_PASS` 等评测字段，接入时要明确区分 agent 可见输入和评测材料。genui{"citation":{"ref":"turn22view0"}}

“Verified”也不意味着测试能证明补丁在所有方面正确。它支持的是**在规定环境与测试标准下解决该 issue**。此外，数据集结果不能自动推广到超大仓库重构或开放式算法优化；少量抽样题也只能提供迁移迹象，通常不足以确认很小的通过率差异。

**对当前选择，我会增加两个前置检查**

第一，检查**任务是否给路由留下了机会**。在开发题上先运行三个单模型，观察：

- 是否存在模型间的互补，而非单一模型全面占优；
- 是否存在需要修订的轨迹，而非几乎全部一次完成；
- 决策服务的费用和时间，占整题开销的比例是否过大。

这些检查用于开发与选型，不能根据测试题的结果筛掉“不利于路由”的任务。

第二，检查**结论的适用范围**。三个数据集都公开已久，自定义留出划分只能避免我们自己的训练泄漏，不能证明执行模型预训练时没见过题目。最终若要支持你们真实的 ADA/OPL 工作，还应追加一批私有、未公开的仓库任务或算法优化任务，使用冻结测试与人工抽查。

所以当前安排是合理的起点：先用 EvalPlus 检查实验链，用 DS-1000 比较方法，再用 SWE-bench Verified 检查工程迁移。**若你们最关心的是仓库级长程执行，SWE-bench Verified 的结果必须进入核心证据，DS-1000 的胜负只能作为第一阶段结论。**

**是，LHTB 比 DS-1000 更匹配你提出的“跨任务类型＋长程执行”目标。我应当调整 v2 的数据集优先级。** 上一版偏向代码任务，方便实验控制，却不足以代表你们真正想研究的通用 harness。

关于“有没有检索过”：前面的讨论已经出现过 LHTB、WeaveBench，但我在整理 v2 时没有把它们落实进核心实验选择，这是方案的遗漏。这次重新核对官方论文与仓库后，我倾向于采用 **Terminal-Bench＋LHTB 为核心，WeaveBench 为跨接口扩展**。

不过，“跨领域”与“任务无关”需要区分：多样任务能检验通用机制，但有限的公开任务集不能证明机制对任意任务有效。

**LHTB 为什么更合适**

[Long-Horizon-Terminal-Bench](https://github.com/zli12321/LHTB) 有 46 个任务，覆盖研究复现、科学计算、软件与逆向工程、多模态分析、游戏等工作流。论文报告的原始实验平均约 231 个交互 episode、85.3 分钟；这些是特定模型与运行设置下的观察值，不是每题固有长度。它提供分级子任务评分，能观察未完全完成时的进展。genui{"citation":{"ref":"turn25view2"}}

对我们的实验，它有三项直接优势：

| 特征 | 能检验什么 |
|---|---|
| 多种任务类型，共用终端环境 | 路由规则是否只适用于代码生成 |
| 持续状态与较长依赖链 | 上下文管理、失败恢复、阶段性模型切换 |
| 部分进展评分 | 在成功率较低时，区分“接近完成”与“基本没进展” |

因此，它更可能暴露真正需要路由的状态：探索时、实现时、诊断失败时、整理产物时，最合适的模型可能不同。这是**待验证假设**，不能从任务长度直接推出。

**但 LHTB 的运行协议必须先核对**

当前官方仓库描述的是 **rebuild-from-artifact 验证**，不能笼统称为 replay-based。更关键的是，部分任务启用 `continue_until_timeout`：agent 宣布完成后，验证未通过就收到二元拒绝并继续，直到通过或超时。仓库要求使用修改后的 Harbor，并增加验证器隔离补丁；也明确注明历史结果与加固后的运行要分别报告。genui{"citation":{"ref":"turn24view0"}}

这对 v2 有实质影响：

- **停止规则不能直接沿用“主动提交即结束”。** 应为 LHTB 单独定义与官方协议一致的运行配置。
- **所有实验组必须获得相同的反馈。** 不能一组收到详细错误，另一组只有拒绝信号。
- **验证过程必须隔离。** 对 agent 隐藏评分文件、测试材料和残留日志。
- **验证调用的时间也要记录。** 中途验证影响实际墙钟时间。
- **“有分级评分”不代表 agent 在线能看到分数。** 当前默认反馈与离线评分必须分开处理。

它也有局限：46 题适合压力测试与机制分析，但不足以轻易确认 3 个百分点的成功率差异。重复每题很多次能减小执行随机性，不能把 46 个任务变成数百个独立任务。

**相近的评测，我会这样取舍**

| 评测 | 与目标的匹配 | 建议用途 |
|---|---|---|
| **Terminal-Bench 2.0** | 多领域终端任务；每题有独立环境、参考解与验证测试 | 通用终端能力主比较 |
| **LHTB** | 更强调长程、持续状态和部分进展 | 长程压力测试与主机制分析 |
| **WeaveBench** | 必须交替使用 GUI 与 CLI，覆盖多种真实工作领域 | 跨接口迁移实验 |

MasRouter 的角色配置可以作为一种可变机制；固定基线应允许研究、游戏、数据分析等任务正常执行，否则比较会天然偏向软件任务。

**第一个可执行试验**

在同一个宿主上比较四组：

1. 开发阶段选定的单模型；
2. 固定异构或固定切换规则；
3. EvoRoute；
4. EvoRoute＋千问决策模型。

每题先运行两次，预算和反馈一致。这个试跑解决四个问题：

- 任务是否能在你们硬件和账户条件下稳定运行；
- 验证器能否拒绝已知错误与伪造产物；
- 长轨迹的成本、时间主要花在哪里；
- 决策模型是否在阶段变化时做出不同选择，而非始终选同一个模型。

- 最终解决率；
- 官方部分进展分数；
- 每题总成本、墙钟时间；
- 预算截止时的有效产物；
- 错误完成声明、验证拒绝后的恢复情况；
- 按任务领域分列的结果。
