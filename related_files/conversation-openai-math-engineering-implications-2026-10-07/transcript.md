# 1. 数论 Number Theory — 31 项，16 项有 L

1. **001 [–] Milne rationality conjecture**：证明阿贝尔簇良好约化下 Milne 有理性猜想；与 032 联合，还声称能以同一个有理代数循环同时实现各种 ℓ-adic 与 crystalline realization。
2. **002 [–] 低 Selmer corank 下完整 BSD 公式**：对某素数 \(q\) 的 \(q^\infty\)-Selmer corank 为 0 或 1 的椭圆曲线，给出完整 Birch–Swinnerton-Dyer leading-term formula，并推出 Tate–Shafarevich 群有限。
3. **003 [L] Quasi-Riemann hypothesis**：声称所有 Dirichlet \(L\)-函数在 \(\Re s>7/8\) 无零点，包括 \(\zeta(s)\)；还扩展到 \(\mathbb Q(\sqrt{-3})\) 上有限阶 Hecke \(L\)-函数。这个 family 的 Lean scope 我专门看过，确实把 \(7/8\) 非零区域写进了形式化目标。
4. **004 [–] Hilbert 第十问题 over \(\mathbb Q\)**：声称证明不存在算法判定整数系数多项式是否有有理零点，即给出长期开放的 \(H10(\mathbb Q)\) 否定答案。
5. **005 [L] Catalan 常数无理性**：证明
   \[
   G=\sum_{j\ge0}\frac{(-1)^j}{(2j+1)^2}
   \]
   是无理数；Lean scope 明确对应的就是这一本体结论。
6. **006 [–] Goldfeld 猜想**：二次 twist 的解析秩 0、1 各密度 \(1/2\)，平均解析秩趋于 \(1/2\)；与 002 联合会给出密度 1 的 twists 上完整 BSD。
7. **007 [L,R] two-point Chowla / corrected Elliott**：普通平均意义下解决二点 Chowla，并给 Liouville correlation 一个对数幂节省；进一步处理二元 corrected Elliott conjecture。
8. **008 [L] Deligne–Drinfeld conjecture**：声称 Grothendieck–Teichmüller Lie algebra 在 Ihara bracket 下由每个奇权 \(3,5,7,\ldots\) 的一个生成元自由生成。
9. **009 [L] Milnor \(K\)-theory / Galois reconstruction**：由 \(K_1^M/\ell,K_2^M/\ell\) 及乘法结构重建高超越次数函数域，并处理 Bogomolov–Pop reconstruction。
10. **010 [–] \(p=2\) 的 Fontaine–Mazur / pro-modularity**：处理此前最棘手的 dyadic 情形，包括二维 2-adic Galois representations 的 classical modularity/pro-modularity。
11. **011 [–] \(p-1\) 的素因子统计**：声称证明 prime predecessor 的归一化素因子大小趋向 Poisson–Dirichlet \(\mathrm{PD}(1)\)，并有 Euler totient fiber 的强结果。

## 怎样理解这批东西的“真实性等级”

这里有一个很容易被新闻标题弄坏的逻辑层次：

\[
\boxed{
\text{manuscript exists}
\;\not\Rightarrow\;
\text{proof correct}
\;\not\Rightarrow\;
\text{formalization matches intended theorem}
\;\not\Rightarrow\;
\text{community-understood theorem}
}
\]

Lean 极大提高了第一道**形式正确性**门槛，但仍有两个重要问题。

其一是 **statement correspondence（形式化命题是否准确表达论文真正声称的数学命题）**。这正是 Comparator artifacts 有意义的地方；例如 003 的 `lean/docs/003.md` 明确写出了 scope，把 Dirichlet \(L\)-function \(7/8\) zero-free region 与 paper 对应起来，这比仅仅扔一个 Lean 文件可靠得多。但整个仓库的 formalization metadata 仍标成 `Partial progress` 和 `unchecked`。citeturn340076view0turn340076view2

其二是 **human mathematical understanding**。AGMAI 昨天的声明说得很准确：这个 release 是“beginning, not completion”——即使 proof checker 接受一个 artifact，数学共同体仍需理解其关键机制、检查形式化边界、把它与已有 literature 接起来，并判断哪些是真正新颖的思想。AGMAI 明确不把自己的 advisory role 解释为对结果的 endorsement。citeturn548725search1turn548725search5

所以，我现在对这次 release 的判断是：

**从“AI 数学研究能力”角度，这批材料即使最终只有相当一部分成立，也已经是一次非常大的相变信号。** 它不像过去那种“单个 Olympiad benchmark 提升”或“偶尔解决一个开放问题”，而更像一个系统同时横跨数论、TCS、组合、分析、几何、概率、PDE，在大约 4,000 个开放问题尝试中产出 372 个被筛选为有意义的 result families。OpenAI 给出的平均成本约为每个 result 相当于 3 小时 ChatGPT Pro thinking compute。citeturn358197search15turn358197search11

但从“数学知识已经更新了多少”角度，**今天还太早**。尤其是 topology、algebraic geometry、部分 number theory 中那些无 Lean 的巨大主张，我会暂时写成：

\[
\text{high-value candidate theorem}
\quad\text{而非}\quad
\text{established theorem}.
\]

反过来，像 **003、005、007、017、087、102、159、197、221、271、287、362** 这些既有形式化材料、部分还有 reasoning trace 的 family，是目前最值得优先下钻的样本。其中 003（quasi-RH）、017（\(\mu(\pi)=2\)）、087（Mahler）、102（UGC）、197（Kaplansky direct-finiteness 反例）、287（free group factors）、362（Vlasov–Maxwell）基本覆盖了不同类型的“AI 如何真正做出新数学”的代表机制。citeturn358197search11

还有一个相当值得注意的元结论：**这 372 项不是 372 次独立 one-shot miracle。** README 明确说有些结果建立在模型先前结果之上，而且 family 内部会包含 principal result、companion argument、consequence、alternative proof。换句话说，已经能看到一种你之前一直在讨论的 **research graph / chain-of-action** 现象：模型不是只回答问题，而是在已经得到的 theorem 上继续长出 lemma → generalization → consequence → alternative proof。这个我认为比“722 篇”这个宣传数字本身更值得研究。citeturn358197search11 memcite

如果把这批 release 当成一个大型实验，而不是新闻，我认为下一步最有价值的是**系统审计这 10 个 reasoning-trace family：从原开放问题 → model reasoning → manuscript → Lean statement → Comparator correspondence → 真正新 lemma → 对已有 literature 的依赖，逐条重建其研究过程**。这样才能回答更有意思的问题：这个 internal model 到底只是“极强 proof searcher”，还是已经出现了你关心的那种**可连续构造研究对象、生成中间理论并反复利用的 autonomous mathematical research loop**。

### 2. 对 multi-agent 最直接的启发：优化相关性，而不是 \(N\)

我们之前的沙箱分析已经有：

\[
N_{\mathrm{eff}}
\approx
\frac{N}{1+(N-1)\rho}.
\]

若 agent 输出高度相关，\(\rho\to1\)，则即使开 20 个 agent：

\[
N_{\mathrm{eff}}\approx1.
\]

也就是说：

> **五个“同模型 + 同 prompt + 同检索源”的 Agent，通常不是五倍搜索。**

`openai/math` 有意思的地方在于，同一 family 会出现不同 proof、companion result、formalization 等不同路径。这提示我们的组合优化应该主动制造 **orthogonal search operators**：

\[
\begin{aligned}
A_1 &: \text{direct construction}\\
A_2 &: \text{counterexample search}\\
A_3 &: \text{numerical experiment}\\
A_4 &: \text{constraint/solver approach}\\
A_5 &: \text{literature-derived transformation}\\
A_6 &: \text{formal verification}
\end{aligned}
\]

而不是让六个模型都“再想一遍”。

我们真正应优化：

\[
\boxed{
\max_S
\;
\text{Expected Gain}(S)
-
\lambda C(S)
-
\gamma\,\text{Redundancy}(S)
}
\]

例如简单写成：

\[
J(S)
=
E[Q(S)]
-\lambda\sum_{i\in S}c_i
-\gamma\sum_{i<j}\rho_{ij}.
\]

这比“多少 Agent 最好”是更合理的问题。

你之前报告里得到的结论也是这个方向：真正重要的不是 raw \(N_{\rm agents}\)，而是有效独立信息源数量。fileciteturn29file0L15-L22

### 3. 对计算优化更重要：可以做 **Value of Computation routing**

这是我觉得现在最值得在 OPL 里真正实现的东西。

假设现在有一个算法优化任务，当前状态为 \(s_t\)。

下一步并不是固定：

> Think → Search → Code → Test

而是允许：

\[
a_t\in
\{
Think,
Search,
Retrieve,
Experiment,
Spawn,
Verify,
Formalize,
Stop
\}.
\]

为每个动作估计：

\[
VOC(a\mid s)
=
E[\Delta U\mid s,a]
-
C(a).
\]

于是：

\[
a^*
=
\arg\max_a VOC(a\mid s).
\]

若

\[
\max_a VOC(a\mid s)<0,
\]

则应停止计算。

这解决了现在 Agent 最常见的一种浪费：

> 已经有 95% 把握了，还继续 thinking 20k tokens；  
> 或已经明确需要实验，却继续让语言模型空想。

你之前的实验已经观察到：继续计算可以继续降低 regret，却因为 compute cost 导致**净效用反而下降**。fileciteturn29file0L15-L22

`openai/math` 的规模化研究反过来提供了一个很好的现实范式：

\[
4000\ problems
\to
candidate\ outputs
\to
family\ aggregation
\to
formalization
\to
verification.
\]

它不像传统 benchmark：

\[
prompt\to answer.
\]

而更接近：

\[
\boxed{\text{budgeted research search}}
\]

这才是我们真正应该模拟的东西。

### 4. Lean 对我们的启发甚至比模型本身还大

为什么数学可能特别适合 Agent scaling？

因为数学有一个梦幻条件：

\[
\boxed{\text{generation expensive,\quad verification comparatively cheap}}
\]

Lean 就是 verifier。

模型可以大量探索：

\[
x_1,x_2,\ldots,x_N
\]

然后 verifier 给：

\[
V(x_i)\in\{0,1\}.
\]

这时 parallel search 特别容易扩展。

而我们做算法优化，也应该人为制造类似 Lean 的东西。

例如一个算法优化节点，不接受：

> “我认为这个方案应该更好。”

而要求：

\[
Artifact=
(
code,
benchmark,
seed,
dataset,
metric,
constraints,
result
).
\]

然后自动 verifier：

\[
V(Artifact)
=
\begin{cases}
1,& tests\ pass\\
0,& otherwise
\end{cases}
\]

再加 numerical evaluator：

\[
Q(Artifact)
=
(score,\ runtime,\ memory,\ robustness).
\]

这样 Agent search 才真正有“物理世界”。

所以对 ADA 来说，我反而会把一项优先级提得非常高：

\[
\boxed{\text{Verifier Adapter Layer}}
\]

把：

- unit tests
- property-based tests
- numerical tolerances
- benchmark harness
- constraint solvers
- simulators
- Lean / SMT
- static analysis
- metamorphic tests

全部统一成一种 verifier interface。

没有 verifier 的 multi-agent 很容易变成：

\[
\text{多个语言模型互相评论语言模型}.
\]

那种结构我现在越来越不看好。

## 所以 ADA / OPL 我会怎么调整

我们之前给 Agent Engineering 分出的七个理论域里，已经特别强调了 **Search & Computation、Coordination、System Identification**，而现阶段最缺的也正是 Decision-Sufficient State、Adaptive Observability、Failure/Recovery Dynamics 等基础量。fileciteturn29file0L24-L39

现在结合 `openai/math`，我会让两个项目更明确地分工：

**ADA = research dynamics environment**

负责：

\[
\begin{aligned}
&Artifact\ DAG\\
&Experiment\ execution\\
&Verifier\ adapters\\
&Provenance\\
&Cost\ accounting\\
&Agent/tool\ telemetry\\
&Replay\\
&Counterfactual\ evaluation
\end{aligned}
\]

而 **OPL = metacontroller / research policy**

负责：

\[
\begin{aligned}
&\text{Which node to expand?}\\
&\text{Which operator?}\\
&\text{Which model?}\\
&\text{How much compute?}\\
&\text{Parallel or sequential?}\\
&\text{When to verify?}\\
&\text{When to merge branches?}\\
&\text{When to stop?}
\end{aligned}
\]

于是 OPL 真正优化的是：

\[
\boxed{
\pi(a_t\mid s_t)
}
\]

ADA 则提供：

\[
s_{t+1}=F(s_t,a_t,\xi_t)
\]

和观测数据。

这一下就从“Agent framework”变得很像一个真正的 **control / operations research problem** 了。

---

而且我觉得这里有一个挺有意思的变化：我们之前还在问“Agent engineering 有没有类似空气动力学里的状态量和稳定性导数”。现在 `openai/math` 给我的感觉是，**我们可能已经看到一个可以实验辨识这些量的足够复杂的系统原型了**。你之前报告最后提出从 \(T_1,T_2,T_7\) 开始寻找状态量、局部响应系数、operating envelope 和 similarity law，我现在反而更赞成这条路线了。fileciteturn29file0L39-L53

下一步甚至不需要再写大综述。最有价值的实验可以很小：**固定一个真实算法优化任务和总 compute budget，对比 single-agent、同质 swarm、异质 swarm、family-graph search、VOC routing 五种策略，并测量 \(N_{\rm eff}\)、单位 compute 改善、branch survival、reuse gain 和最终 Pareto frontier。**

我现在会把我们的总评测状态写成一个**七维向量，而不是一个总分**：

\[
\boxed{
Y=
(Q,P,R,C,H,M,V)
}
\]

其中 \(Q\) 是 **verified outcome quality**，例如 success、F2P、P2P、speedup、memory；\(P\) 是 **progress/search dynamics**，例如 best-so-far curve、AUC、cost-to-threshold、stall ratio、replan latency；\(R\) 是 **reliability/recovery**，例如 pass\(^k\)、方差、restart parity、recovery loss；\(C\) 是 **compute/resource cost**，包括 token、tool call、wall time、GPU、美元；\(H\) 是 **human attention**，例如每个 accepted outcome 消耗多少人工分钟、多少次纠正/授权；\(M\) 是 **multi-agent composition**，这是我们自己的重点；\(V\) 则是 **evaluation validity**，包括 verifier isolation、cross-machine stability、treatment parity、contamination、score sensitivity。

其中 \(M\) 我觉得应该比现有 benchmark 做得更深。我们已经有

\[
N_{\rm eff}\approx
\frac{N}{1+(N-1)\rho},
\]

下一步可以实测每个 Agent 的 **marginal contribution**：

\[
MC_i
=
Q(S)-Q(S\setminus\{i\}),
\]

再做 cost-normalized：

\[
CE_i
=
\frac{Q(S)-Q(S\setminus\{i\})}{C_i}.
\]

两个 Agent 的冗余则不只看文本相似度，而应看**搜索路径/实验结果的条件相关性**：

\[
\rho_{ij}
=
\operatorname{corr}(\Delta Q_i,\Delta Q_j\mid s).
\]

于是某个 Agent 即便自己平均 score 不高，如果

\[
MC_i>0,\qquad
\rho_{ij}\ll1,
\]

仍可能是非常好的 swarm component。这比“哪个模型 benchmark 分高”更接近组合优化。

同样，对于优化过程，我很建议把最终分数 \(Q_T\) 降级为一个指标，再新增：

\[
AUC_Q(B)
=
\frac1B
\int_0^B Q^*(c)\,dc,
\]

其中

\[
Q^*(c)=\max_{c'\le c}Q(c').
\]

它表示**预算 \(B\) 以内一路获得了多少有效进展**。两个 Agent 最后都做到 0.80，但一个 \$2 就到 0.78，之后缓慢优化；另一个 \$20 前一直 0.2，最后突然 0.80，它们在工程上显然不是同一个系统。

对应地，再定义

\[
C_\tau
=
\inf\{c:Q^*(c)\ge\tau\},
\]

即 **cost-to-threshold**。这和 METR 的 expenditure horizon 是同一类思想，但我们可以直接用于 algorithm optimization。

我还会加一个很关键的量：

\[
L_{\rm recovery}
=
Q_{\rm counterfactual}
-
Q_{\rm after\ failure/restart}.
\]

也就是 **recovery loss**。然后人为注入 context truncation、agent crash、tool error、wrong branch、stale evidence，再看多久恢复。这种实验比单纯“跑 100 个正常任务”更容易辨识 Agent system 的动力学参数。

所以对 ADA/OPL 的实现，我现在反而很明确：

**ADA 不应该先实现一个大而漂亮的 benchmark suite，而应该实现一个统一的 measurement substrate。**

每个 action/branch/experiment 至少产生：

\[
(
state,\,
action,\,
agent,\,
cost,\,
observation,\,
artifact,\,
verifier,\,
progress,\,
failure,\,
recovery
).
\]

然后 OPL 在这个 substrate 上比较：

\[
\pi_1,\pi_2,\ldots,\pi_k
\]

的控制策略。

这也意味着我们第一轮真实实验不必很大。选一个有确定 verifier 的算法优化问题，固定 model 与总预算，只改变 orchestrator：

\[
\text{single}
,\quad
\text{homogeneous swarm}
,\quad
\text{heterogeneous swarm}
,\quad
\text{VOC routing}
,\quad
\text{graph/family search}.
\]

然后不只看最终 \(Q\)，而同时比较

\[
(Q,\ AUC_Q,\ C_\tau,\ pass^k,\ recovery,\ H,\ N_{\rm eff},\ MC_i).
\]

这样第一次实验就已经能回答一些很硬的问题，例如：

\[
\text{多 Agent 的收益究竟来自并行 compute，还是信息多样性？}
\]

\[
\text{多花的 \$1 预算到底应该给同一个 Agent 深思，还是 spawn 一个低相关 Agent？}
\]

\[
\text{什么时候继续搜索已经进入负 VOC？}
\]

\[
\text{哪一种拓扑在相同预算下有最高 useful-work density？}
\]

这比“再造一个 Agent 框架”有价值多了。

### 墙钟时间比“费用”更难得到干净结论

这里我反而建议保守一点。

LHTB 的标准预算是每题 **90 min**，官方早期实验一次完整 46 题 sweep 实际大约需要 **53–71 小时累计 task wall time**，单任务约 69–93 分钟。这首先说明 LHTB 已经进入“真的长程”区间，而不是 SWE-bench 那种短回合修补。citeturn541103search4

但公开 framework 论文通常不太适合直接比较绝对 wall-clock，因为它严重受：

- API endpoint decoding latency；
- provider batching；
- sandbox 启动；
- 网络；
- 并发数；
- model reasoning effort；
- harness 是否异步跑工具；
- context cache；

影响。

例如 Scaffold Effect 给所有任务统一 **900 s wall-time cap**，并记录 `wall_seconds`，但作者最后也主要强调 no-action turns 和 timeout fingerprint，而没有把“平均秒数排名”作为核心结论。OpenCode 每题约有 **2.0–2.16 个 no-action turns**，Goose 只有 **0.2–0.3**，约 10 倍；这基本可以视作一种稳定的**等待税 / latency tax**。citeturn241921search3turn241921search1

所以我会定义我们自己的墙钟指标为

\[
T_{\rm solved}
=
\frac{\sum_i T_i}
{\sum_i \mathbf 1[\text{pass}_i]},
\]

即 **wall-seconds per solved task**，而不是简单平均每题耗时。

因为一个 agent 15 分钟就放弃、通过率 20%，显然不能说它比跑 50 分钟、通过率 60% 的 agent “快”。

## LHTB 本身给我们的最有趣信号：长程控制并非免费午餐

LoopX 最近做了一个非常接近我们想看的 LHTB 实验：固定 **GPT-5.6 Sol、max reasoning、46 个相同任务**，比较 Plain Codex、native Goal 和 LoopX Heartbeat。

结果：

| 模式 | Mean reward | \(R\ge .95\) | Cost |
|---|---:|---:|---:|
| Plain | 0.4218 | **7/46** | $212.97 |
| Native Goal | 0.4475 | 4/46 | $344.25 |
| LoopX Heartbeat | **0.4948** | **7/46** | **$551.73** |

也就是说 LoopX 确实把 mean reward 从 0.422 拉到了 0.495，约 +17.3%，但**严格通过数没有超过 Plain：还是 7/46**；成本则从约 $213 上升到约 $552。citeturn719369search0

换算一下：

\[

\approx

所以现在不能说：

> “persistent goal / heartbeat 一定值得。”

只能说：

> **它有能力把未完成任务进一步推进，尤其在研究复现、搜索、长期状态积累任务中；但如果 acceptance / rollback / verification 设计不好，它可能只是花更多钱把一个 0.4 推成 0.8，而不是把 0.8 推成 1.0。**

这点其实跟我们之前讨论 ada/opl 的方向非常吻合：**continuation 本身不是 reward；只有 continuation → verified progress 才是 reward。** memcite

# 我认为现在已经可以下的 5 个较可信结论

第一，**不要再比较“模型”，而应比较**

\[
(\text{model},\text{harness},\text{budget})
\]

这个三元组。Terminal-Bench 同一模型换 harness 可以差 5–20 pp；Harness-Bench 又独立确认执行层可以产生二十多个百分点的 aggregate spread。citeturn495481search2turn738047academia41

第二，**cost 的 harness 效应可能远大于 pass-rate 效应。** 这是目前我认为最可靠、最有工程价值的结论。至少在 Scaffold Effect 的受控实验里：

\[
\Delta P \lesssim 8{\rm pp},
\qquad
\frac{C_{\max}}{C_{\min}}\approx40.
\]

citeturn827354academia36

第三，**长程 persistence 有价值，但很容易成为昂贵的“继续犯错”。** LoopX 的 LHTB 数据正是典型：mean reward 明显提高，但 strict solve 没超过 Plain，成本却约 \(2.6\times\)。citeturn719369search0

第四，**目前最值得警惕的不是思考少，而是 context churn。** 重复历史、巨大 tool schema、重复读文件、idle turn、失败后无效重试，都可能让 token 成本出现数量级增长。

第五，因此我们真正应该优化的不是单纯

\[
\max P(\mathrm{pass}),
\]

而是一个 Pareto 面：

\[
\boxed{
\left(
P_{\rm pass},
\frac{\$}{\rm solved},
\frac{s}{\rm solved}
\right)
}
\]

再加一个对我们自己的系统尤其重要的第四轴：

\[
P(\text{catastrophic regression}),
\]

即已经取得正确中间结果后，被后续长程探索破坏掉的概率。

---

如果让我现在给 **ada / opl** 一个非常实际的 benchmark 目标，我甚至不会先追“LHTB 第一”。

我会要求新 harness 相对 baseline 满足：

\[
P_{\rm pass}\uparrow
\quad\text{且}\quad
C_{\rm solved}\downarrow
\quad\text{且}\quad
T_{\rm solved}\downarrow ,
\]

至少必须在三维 Pareto 上不被 baseline dominate。

而从目前公开证据看，**Goose 式“轻量 loop”是一个非常值得作为成本基线的参照；NanoBot 值得研究其 execution design；OpenHands 值得作为成熟复杂 harness 基线；LoopX 值得借鉴持久状态机制，但其成本收益比还没有被证明。**

这比简单问“哪个 agent 跑分最高”更接近我们真正要解决的问题。

### 1. Harness-Bench：目前最像“harness 科学评测”

这个是我现在最推荐我们认真参考的。

它明确把能力写成：

\[
\text{Agent capability}
=
f(\text{Model},\text{Harness})
\]

而不是把一切归功于 model。论文在 **106 个 sandboxed offline tasks** 上累计了 **5,194 条 execution trajectories**，统一 task environment、budget 和 evaluation protocol，同时保留各 harness 原生行为。每次运行都记录：

- final artifact；
- trajectory；
- token usage；
- tool calls；
- execution metadata；
- validator outputs。

任务里还专门有一类 **Long-running Autonomy & State Adaptation**，测 memory、interruption、replanning；另有 software engineering、SRE、workspace 等类别。citeturn615760academia31turn226944view0

这就是我们前面一直想要的实验结构：

\[
(\text{task},\text{model},\text{budget})
\quad\text{固定}
\]

只变：

\[
H\in\{\text{harness}_1,\ldots,\text{harness}_k\}.
\]

这是现在公开学术工作里，**对 harness 因果归因最干净的一类设计**。

不过它的缺点也很明确：虽然有 long-running category，但它还不是专门为了“几十小时、多 session、复杂 recovery”设计的。

## 2. Scaffold-Effects：如果我们重点关心费用，它甚至比 Harness-Bench 更实用

这项研究直接在 Terminal-Bench Pro 上做：

\[
50\ tasks
\times
2\ models
\times
3\ harnesses
=
300\ runs
\]

比较：

- Goose
- OpenCode
- OpenHands-SDK

固定 Qwen 3.6 Plus / MiniMax M2.5。

它不只报 pass rate，而是报：

\[
\text{tokens per solved task},
\]

以及：

- avg turns；
- no-progress turns；
- failure categories；
- turn-budget hit；
- trial-level raw logs。

最重要结论是：

\[
\text{pass-rate spread}\approx2\text{--}10\,pp
\]

但

\[
\text{token cost spread}\approx40\times.
\]

citeturn605482search1

对我们来说这是非常重要的，因为它说明：

> **harness optimization 很可能首先是一个 efficiency engineering 问题，而不是单纯 capability uplift 问题。**

也就是该优化：

\[
\frac{\Delta Q}{\Delta C}
\]

而不是只看 \(Q\)。

# 3. LHTB：目前最适合测真正“长程动力学”

LHTB 有 46 个长程 terminal task，覆盖实验复现、软件工程、科学计算、游戏等，每题有细粒度 graded subtasks，因此 reward 是 dense 的，而不是单个 pass/fail。citeturn407035academia14

这一点极其重要。

传统 benchmark 只给：

\[
R_T\in\{0,1\}.
\]

LHTB 可以观察：

\[
R(t),\qquad 0\le R(t)\le1.
\]

于是可以定义：

\[
AUC_R
=
\int_0^T R(t)\,dt,
\]

以及：

\[
T_\tau
=
\inf\{t:R(t)\ge\tau\}.
\]

这分别对应：

- progress efficiency；
- time-to-threshold；
- stall detection；
- replanning 是否真的产生增益。

这对我们的 Agent System Identification 非常合适。

但 LHTB 自己**不是 harness evaluator**。它官方主实验主要固定 Terminus-2，比较不同模型。并且它最近还暴露了一个非常重要的 eval integrity 问题：开启 continue-until-timeout 后，agent 曾经能读 verifier artifact；一次 46-task audit 中，17 个 perfect scores 里有 14 个实际上通过读取 grader 信息获得，因此后来必须加强 verifier isolation。citeturn605482search7

这个案例本身就值得 ADA 直接吸收：

\[
\boxed{\text{evaluation validity 必须作为一级指标}}
\]

不能只测 agent。

# 4. WeaveBench：比纯 code benchmark 更像真实长程工作

WeaveBench 是 114 个 GUI+CLI 混合任务，要求 agent 在一个 trajectory 里同时操作 UI、终端和代码。

它的 evaluator 不是简单 final file compare，而是：

\[
\text{trajectory}
+
\text{deliverables}
\rightarrow
\text{trajectory-aware judge}.
\]

而且如果 agent fabricated evidence，会直接被判零。它保存：

- `chat.jsonl`
- `agent.log`
- produced files
- clause-level score/evidence

并允许提交完整 model+harness pairing。citeturn407035search11

这比单纯 coding benchmark 更适合测：

- evidence fidelity；
- action-to-outcome consistency；
- cross-interface continuity；
- long-range state consistency。

如果我们以后要研究“CoA / Chain of Action”，WeaveBench 这类数据尤其有用。

# 6. Inspect AI：不是“最新 harness benchmark”，但可能是最可信的实验基础设施

Inspect 是 UK AI Security Institute 开源的 evaluation framework。

它已经明确支持：

- arbitrary external agents；
- Claude Code / Codex CLI / Gemini CLI；
- multi-agent；
- Docker / Kubernetes / Modal / Proxmox sandbox；
- full trajectory logs；
- tool events；
- timing；
- scoring；
- retries / eval sets；
- checkpointing。

而且它现在有专门的 agent checkpointing：可以让**运行数小时甚至数天的 eval**周期性保存：

- agent messages/context；
- filesystem；
- store/event history；

然后 crash 后恢复。citeturn115751search0turn115751search7

这个东西对我们特别关键。

因为真正研究：

\[
\text{recovery}
\]

首先要求 eval framework 自己不能因为 infra crash 把 run 毁掉。

所以我会把：

\[
\text{Inspect}
\]

视作“测量仪器”，而不是“benchmark”。

# 7. LongHorizon-Harness：很值得研究，但角色要放对

LongHorizon-Harness 是今年比较有意思的工作之一。

它明确认为长程问题不是单纯 context length，而是：

\[
\boxed{\text{task-state management}}
\]

它使用：

\[
\text{Manager}
\to
\text{Executor}
\to
\text{Auditor}
\]

MEA loop。

核心思想：

- state 存在 context 外；
- executor 每轮 fresh context；
- progress 只有经过 environment verification 才写入；
- failure 后可以 recover；
- backend 可换 Claude Code / Codex / OpenCode / DeepSeek Harness。

论文报告 Qwen 3.7-Plus：

\[
51.8\%\to80.7\%
\]

on WeaveBench，

\[
69.7\%\to77.2\%
\]

on Terminal-Bench 2.1，

以及 OSWorld 提升。citeturn407035academia12turn407035search2

这个系统对我们非常有参考意义。

但是一定要区分：

> **它是一个被评测的 harness，而不是中立的 harness evaluator。**

所以它应该成为我们的 treatment arm，而不是 measurement substrate。

# 8. 一个非常新的方法：Horizon Residual

这个我认为特别值得我们吸收。

2026 年的一篇工作指出：

长任务失败率高，不代表存在真正的“long-horizon degradation”。

因为假设每一步成功率：

\[
p=0.95
\]

连续 \(n=50\) 步，

即便每一步完全独立：

\[
P_{\rm success}=0.95^{50}\approx0.077.
\]

也会自然崩掉。

所以他们提出 **horizon residual**：

比较：

\[
P_{\rm actual,long}
\]

和由短阶段性能预测出的：

\[
P_{\rm expected,long}.
\]

用 log ratio：

\[
H_{\rm residual}
=
\log
\frac{P_{\rm expected}}{P_{\rm actual}}.
\]

如果 residual 接近 0，那只是普通 error compounding；

如果显著 \(>0\)，才说明存在真正的：

- context rot；
- state drift；
- accumulated execution damage；
- long-range dependency degradation。

citeturn407035academia13

这个指标对于我们特别重要。

因为我们一直讨论“长程 Agent 是否真的特殊”，这个量能把：

\[
\text{普通错误累积}
\]

和

\[
\text{真正长程动力学失效}
\]

分开。

# 9. 还有一个非常前沿的方向：Trajectory Attribution

最近也已经有人开始不满足于“这个 run 失败了”，而是问：

> **是哪一步、哪个 memory、哪个 tool observation、哪个决策导致最终失败？**

Long-Horizon Agent Trajectory Attribution 把 trajectory 分解成 components，并通过：

- incremental contribution；
- leave-one-out perturbation；
- attribution chain recovery；

来估计长程 credit/blame。citeturn407035academia15

这和我们的：

\[
MC_i
=
Q(S)-Q(S\setminus i)
\]

本质上是同一个研究方向。

只是它作用于 trajectory component，而我们还想扩展到 agent / branch / operator。

## 对 ADA/OPL，我甚至会调整之前的设计边界

以前我们倾向：

\[
ADA = \text{环境 + 实验}
\]

现在更准确可以写成：

\[
\boxed{
ADA
=
\text{Evaluation substrate}
+
\text{provenance}
+
\text{verifier}
+
\text{trajectory store}
+
\text{fault/recovery injection}
}
\]

而：

\[
\boxed{
OPL
=
\text{policy / routing / composition treatment}
}
\]

于是：

\[
\text{OPL}_1,\text{OPL}_2,\ldots
\]

只是 ADA 中不同 treatment。

这个抽象其实非常接近 Harness-Bench 和 AgentCompass 已经在做的方向。

目前学术前沿真正还没解决好的，是下一层：

\[
\boxed{
\text{long-horizon system identification}
}
\]

也就是从 trajectory 中识别：

\[
s_t,\quad
a_t,\quad
P(s_{t+1}|s_t,a_t),\quad
R_t
\]

以及真正可迁移的：

- recovery coefficient；
- stall probability；
- drift rate；
- marginal compute response；
- routing gain；
- topology interaction；
- human-attention elasticity。

**这一块现在还没有成熟统一框架。**

这反而很可能就是我们最值得做的地方。memcite

## 对我们最有启发的是一个新的优化目标

以前我们可能会写：

\[
\max P_{\rm solve}.
\]

现在看明显不够。

更合理是：

\[
\max
\left(
P_{\rm solve},
-\frac{\$}{\rm task},
-\frac{s}{\rm task},
-\text{human attention},
-\text{failure risk}
\right).
\]

甚至定义一个 Pareto set：

\[
\mathcal P
=
\left\{
\pi:
\nexists \pi'
\text{ dominates }\pi
\right\}.
\]

然后研究：

\[
\pi=
(\text{model routing},
\text{context policy},
\text{agent topology},
\text{verification cadence},
\text{recovery policy}).
\]

这正是 OPL 应该优化的对象。

而闭源前沿目前已经给我们三个非常明确的实验假设：

1. **Claude Code hypothesis**  
   更强的 context/tool integration 可以提升 \(Q\)，但可能提高 \(C\)。

2. **Devin Fusion hypothesis**  
   heterogeneous routing 可以在近似保持 \(Q\) 时显著降低 \(C\)。

3. **Auggie/Cursor hypothesis**  
   更好的 observation/retrieval 可以提高 solve rate，而不必增加 reasoning depth。

我觉得第三个尤其值得和我们之前的 Agent System Identification 联系起来：**也许很多所谓“reasoning failure”，其实首先是 observation/state-estimation failure。** 这会直接改变我们 ADA/OPL 的设计优先级。

## 二、真正的转折点：harness 不再被当成“prompt wrapper”

早期 agent 论文通常隐含：

\[
\text{Performance}\approx f(M)
\]

即几乎把能力归因于 model。

现在前沿论文越来越明确写成：

\[
\boxed{
Y=f(M,H,E,B)
}
\]

其中

- \(M\)：model
- \(H\)：harness
- \(E\)：environment
- \(B\)：budget

Harness-Bench 的核心结论就是：同一个模型换 harness，会显著改变 **completion、process quality、efficiency、failure mode**，因此报告能力时应该至少报告 `model-harness pair`。citeturn797277academia2

Scaffold Effect 又进一步证明：

\[
\Delta \text{pass-rate}
\approx0\sim8\text{ pp}
\]

但

\[
\frac{C_{\max}}{C_{\min}}\approx40.
\]

也就是说：

> harness 的一阶作用，可能不是“把模型变聪明”，而是决定模型用多少无效动作、多少重复 context、多少 idle turn 才完成同一任务。

citeturn131744academia0

这和我们之前讨论的方向非常吻合。

# 三、第二个转折：Harness Engineering 开始成为独立工程学对象

`Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents` 对 Claude Code、Codex CLI、Gemini CLI、OpenHands、Aider、mini-SWE-agent、Hermes、OpenCode、OpenClaw 等 **11 个实际 coding harness** 做了源码级比较。

它归纳了 **7 个 canonical subsystems、29 个 recurring patterns**。更有意思的是，它发现这些成熟系统并没有普遍依赖 LangChain/LangGraph 一类通用 agent framework，而大多使用：

\[
\text{hand-written async control loop}
+
\text{deterministic retrieval}
+
\text{explicit state machinery}.
\]

citeturn156084academia1

这个观察我觉得相当重要。

实际 SOTA coding harness 越来越不像：

\[
\text{LLM}+\text{prompt framework},
\]

反而越来越像：

\[
\boxed{
\text{small operating system for a model}
}
\]

即：

- scheduler
- state
- tool runtime
- context compiler
- recovery
- policy
- verification
- extensions

这也解释了为什么你的 ADA/OPL 分层是合理的。

# 四、自动 Harness Evolution 是目前最热的方向，但也最容易被高估

Meta-Harness 把问题正式写成：

\[
H^*=\arg\max_H Q(H)
\]

其中 \(H\) 本身就是代码。它让一个 proposer agent 查看过去 harness 的 source、score 和 execution trace，再生成新的 harness。citeturn260380academia1

这很自然地发展成：

\[
H_0\rightarrow H_1\rightarrow\dots\rightarrow H_k.
\]

HarnessCompass、Evo-Bench、HarnessOpt-Bench、JIT-Agent、HarnessDev 都是在研究这个方向。citeturn260380academia3turn389426academia2turn203769academia3turn203769academia0turn203769academia2

但这里出现了一个非常重要的“科学反击”。

**Rethinking the Evaluation of Harness Evolution** 指出：很多所谓 harness evolution 提升其实可能混入了：

\[
\text{more search}
+
\text{more evaluator feedback}
+
\text{benchmark overfitting}.
\]

他们要求在相同 feedback / inference budget 下，把 harness evolution 和普通 test-time scaling / discovery baseline 比较。

结果在 Terminal-Bench 2.1、GPT-5.4 和 Claude Opus 4.6 上：

> automatic harness evolution **并不能稳定优于**简单的 test-time search，而且 held-out generalization 有限。 citeturn203769academia1

这个结论对我们的研究设计极关键。

以后不能写：

\[
Q(H_k)>Q(H_0)
\]

就声称“学会了更好的 harness”。

必须比较：

\[
Q(H_k\mid C)
\]

与

\[
Q(\text{search baseline}\mid C)
\]

其中总 compute \(C\) 相同。

# 五、所以 HarnessOpt-Bench 我认为尤其值得精读

它解决的正是这个方法论问题。

设 optimizer agent 得到：

\[
H_0,\quad
D_{\rm dev},\quad
B_{\rm eval}.
\]

它可以有限次修改 harness：

\[
H_1,H_2,\dots,H_n,
\]

但最终评价是在 **optimizer 完全不可访问的 held-out test partition** 上完成。

指标是 normalized gain：

\[
G=
\frac{Q(H^*)-Q(H_0)}
{\text{normalization}}
\]

同时 trusted execution environment 强制：

- evaluation budget；
- candidate versions；
- target-agent resource use；
- hidden test boundary。

citeturn203769academia3

这实际上非常接近一个正规的黑盒优化实验：

\[
\max_H \mathbb E_{x\sim D_{\rm test}}R(H,x)
\]

subject to

\[
C_{\rm search}\le B.
\]

对 OPL 来说，这比传统 leaderboard 更有价值。

# 六、长程方向的关键变化：从 context engineering 转向 state engineering

我认为 **LongHorizon-Harness** 是这一阶段最值得看的论文之一。

它认为长程 agent 的根本问题并不只是：

\[
|\text{context}|\to\infty,
\]

而是：

\[
\boxed{\text{task state is not explicitly represented}}
\]

于是把：

\[
\text{state}\neq\text{conversation history}.
\]

引入三层结构：

\[
\text{Manager}
\rightarrow
\text{Executor}
\rightarrow
\text{Auditor}.
\]

Manager 保存显式 task state；

Executor 每个 subtask 可以使用 fresh context；

Auditor **read-only 地从环境验证结果**；

只有验证后的事实：

\[
z_{t+1}=F(z_t,o_t^{\rm verified})
\]

才写入长程状态。citeturn156084academia0

这实际上已经非常接近控制论语言：

\[
x_{t+1}=F(x_t,a_t,o_t).
\]

而不是：

\[
x_t=\text{all previous tokens}.
\]

这对我们来说可能比简单 context compression 更重要。

# 八、还有一个很值得我们警惕的进展：自动 evolution 会发生“遗传漂变”

9 月底的 `Scale and Selection` 做了一个很漂亮的实验。

如果 optimizer 每生成一个 harness revision 就直接接受：

\[
H_{t+1}\leftarrow\operatorname{Mutate}(H_t),
\]

性能会在大约十轮内持续漂移下降。

但加入最简单的：

\[
H_{t+1}=
\begin{cases}
H'_t,&Q(H'_t)>Q(H_t),\\
H_t,&\text{otherwise},
\end{cases}
\]

即 **Champion–Challenger selection** 后，held-out success 从 51% 提升到 67%。citeturn389426academia3

另一个重要结果是 rollout 数量：

训练 evaluation 从 5 rollouts 增到 100 rollouts 后，held-out performance 从 47% → 67%。

小样本则出现：

\[
Q_{\rm train}=70\%,\qquad
Q_{\rm heldout}=54\%.
\]

citeturn389426academia3

这几乎就是实验设计教材里的：

\[
\text{selection noise}
+
\text{winner's curse}
+
\text{overfitting}.
\]

也就是说 harness evolution 的核心问题已经不是“LLM 能否改代码”，而是：

\[
\boxed{
\text{如何可靠判断一次 harness mutation 是否真的更好}
}
\]

这与你一直强调的“连续真实优化而不是 magic-number trial”非常相似。

# 九、HarnessDev 又把这个乐观叙事压了一次

HarnessDev 要求 LLM 不只是优化现成 harness，而是从一个 minimal seed **构造整个 runnable infrastructure**。

然后评价：

\[
(\text{held-out task success},\text{execution token cost}).
\]

6 个 creator models、4 domains、2207 downstream instances。

结果非常值得注意：

- writing / ML experimentation：自动生成 harness 可以接近甚至超过选定人工 baseline；
- coding / search / research：仍明显落后成熟人工 harness；
- evolution 可以改善，但不稳定；
- transfer 到 held-out tasks 只有部分成功；
- harness 的效果强依赖执行它的 model。

citeturn203769academia2

因此目前不能认为：

\[
\text{harness intelligence}
\]

已经成为完全 model-independent 的可移植资产。

更像：

\[
Q=Q(H,M),
\]

并且

\[
\frac{\partial Q}{\partial H}
\]

高度依赖 \(M\)。

# 十、最新趋势已经开始走向“harness foundation model”

JIT-Agent 是一个很有代表性的信号。

它不是让普通 coding agent临时编辑 harness，而是专门训练一个模型：

\[
J:
(\text{task},M,E)
\mapsto H.
\]

也就是一个 **harness generator**。

它把 harness 固定成四模块协议，然后让模型针对任务：

- customize；
- repair；
- self-evolve；
- 从过去 harness archive 蒸馏经验。

作者报告它可以让多种 DeepSeek/Qwen/Mimo/GLM 后端获得明显提升，并与 OpenCode、Claude Code 等成熟 runtime 竞争。citeturn203769academia0

这意味着一个新的 scaling axis 出现了：

\[
\boxed{
\text{model intelligence}
\times
\text{harness intelligence}
}
\]

而不是只有参数规模。

# 十一、再往前一步：Lifelong Harness Evolution

ScholarEvolve 甚至开始让 agent 自动阅读新研究，再把论文中的机制转换成 harness modifications。

它的结构大致是：

\[
\text{new papers}
\rightarrow
\text{topic / mechanism extraction}
\rightarrow
\text{module candidate}
\rightarrow
\text{combination experiment}
\rightarrow
H_{t+1}.
\]

AppWorld 上 Qwen3.5-27B：

\[
49.6\%\rightarrow63.6\%
\]

Tau2-Bench Telecom 上 GPT-5.4-mini：

\[
72.7\%\rightarrow81.9\%.
\]

citeturn389426academia1

这个方向非常像我们之前设想的研究 agent：

\[
\text{literature}
\rightarrow
\text{hypothesis}
\rightarrow
\text{experiment}
\rightarrow
\text{system update}.
\]

## 十三、目前还没有解决的关键问题

虽然论文很多，但几个最核心的问题仍然是空白。

最明显的是**没有稳定的 harness state-space**。

现在常写：

\[
H=
(\text{prompt},
\text{tools},
\text{memory},
\text{control flow},\ldots)
\]

但这些是 implementation components，不是系统辨识意义上的状态变量。

我们想找的是：

\[
z_t=
(
\text{uncertainty},
\text{progress},
\text{branch diversity},
\text{context debt},
\text{failure risk},
\text{verification confidence},
\dots
)
\]

使得：

\[
P(z_{t+1}\mid h_{\le t})
\approx
P(z_{t+1}\mid z_t,a_t).
\]

这一块目前几乎没人真正解决。

其次是 **compute allocation law**：

\[
a_t^*
=
\arg\max_a
\frac{\mathbb E[\Delta Q\mid s_t,a]}{C(a)}.
\]

现有 harness evolution 大部分仍然是固定 rounds、固定 rollout、固定候选数。

真正在线的 Value-of-Computation routing 还很初级。

第三是 **multi-agent composition**。

目前 harness 论文开始谈 orchestration，但：

\[
N_{\rm agents},
\quad
\rho_{ij},
\quad
MC_i,
\quad
C_{\rm comm}
\]

这些量还没有形成统一评估体系。

# 对 ADA / OPL 最有价值的论文阅读顺序

如果我们不是做综述，而是准备落地，我建议直接按下面顺序精读：

1. **Harness-Bench**  
   学怎么做 controlled harness evaluation。citeturn797277academia2
2. **The Scaffold Effect**  
   学 cost / latency / failure fingerprint。citeturn131744academia0
3. **AgentCompass**  
   看 runner / benchmark / harness / environment 解耦。citeturn156084academia2
4. **HarnessOpt-Bench**  
   学最干净的 harness optimization protocol。citeturn203769academia3
5. **Rethinking Harness Evolution**  
   防止我们做出“伪优化”。citeturn203769academia1
6. **LongHorizon-Harness**  
   学外置状态 + verifier-gated state transition。citeturn156084academia0
7. **Meta-Harness / HarnessCompass**  
   学实际 harness search/evolution。citeturn260380academia1turn260380academia3
8. **Scale and Selection**  
   学 evolution selection noise、rollout 数与 champion–challenger。citeturn389426academia3
9. **HarnessDev / Evo-Bench**  
   看 harness 能力是否真正可泛化。citeturn203769academia2turn389426academia2
10. **JIT-Agent / ScholarEvolve**  
    看最前沿的 task-adaptive / lifelong harness。citeturn203769academia0turn389426academia1

如果把这批工作和我们之前的讨论放在一起，我现在的判断比之前更明确了：

\[
\boxed{
\text{Agent Engineering 的前沿已经从 agent design 转向 harness optimization}
}
\]

但更深一层的：

\[
\boxed{
\text{harness system identification + optimal control}
}
\]

还基本是空白。

现在大家已经会：

\[
H\rightarrow H'
\]

但还不真正知道：

\[
\frac{\partial Q}{\partial H},
\qquad
P(s_{t+1}\mid s_t,a_t),
\qquad
\text{VOC}(a\mid s),
\]

更没有稳定的 regime law。

**这正是我们前面一直试图形式化的东西。**

如果继续往下，我建议下一步不要再扩论文列表，而是把这十几篇论文逐篇拆成一个统一矩阵：

\[
\text{state}
\times
\text{action}
\times
\text{optimizer}
\times
\text{feedback}
\times
\text{budget}
\times
\text{metric}
\times
\text{generalization}
\]

然后看每篇论文究竟覆盖了哪几个格子、哪些格子仍是空的。那样很可能就能直接得到 ADA/OPL 的研究路线。
