**二、从第一性原理看，轨迹为什么有价值**

设 agent 与环境交互，历史为

\[
H_t=(o_0,a_0,o_1,\ldots,a_{t-1},o_t),
\]

最终目标是在成本约束下提高任务效用：

\[
\max_\pi \mathbb E_\pi[U(Y)]
\quad
\text{s.t.}\quad
\mathbb E_\pi[C]\le B.
\]

终态告诉我们“结果怎样”；轨迹额外告诉我们：

- 决策当时有哪些信息；
- agent 采取了什么行动；
- 行动之后增加了什么证据、修改了什么产物；
- 哪些错误被修复，哪些仍影响后续决策；
- 成本花在哪些状态转换上。

因此，我认为轨迹有三层价值：

\[
\underbrace{\text{重建发生了什么}}_{\text{可观测性}}
\;\longrightarrow\;
\underbrace{\text{预测接下来会怎样}}_{\text{状态估计}}
\;\longrightarrow\;
\underbrace{\text{判断改变什么会更好}}_{\text{干预选择}}.
\]

**第三层才直接对应 agent 设计增益，前两层是它的基础。**

还要注意：记录下来的 reasoning 文本只是可观察输出，不能等同于模型内部的真实因果过程；时间上先出现的文字，也不能自动认定为后续决策的原因。

**三、最值得追求的六类增益**

**1．把“历史摘要”改造成“可行动的状态估计”**

长任务的核心困难之一，是当前上下文不能可靠表达全部相关状态。我们需要从轨迹构造：

\[
z_t=f(H_t),
\]

其中 \(z_t\) 保留对未来行动选择有用的信息。例如：

| 状态维度 | 你这份实验中的实例 |
|---|---|
| 已证实事实 | checker 仅检验公开请求的接口行为 |
| 未识别因素 | 硬件共线，部分系数无法从公开数据识别 |
| 当前候选 | A、B、混合模型及各自版本 |
| 证据适用范围 | 五设计 LOCO；更严格 leave-k；无标签压力测试 |
| 未解决分歧 | probe 尾部形状、独立变化硬件的响应 |
| 执行状态 | canonical 文件是否真正复制到评分路径 |
| 剩余资源 | 可用时间、尚可执行的验证次数 |

这里的压缩目标应当是**保留决策相关信息**。例如“双方已同意 B”远不如“双方选 B，但其 mispredict_penalty 响应未被识别，五设计 regret 不能验证二十四设计选择”有用。

ACE 将上下文作为通过生成、反思、整理而持续更新的 playbook，并用结构化增量更新减少反复重写造成的信息丢失。这支持上述工程方向，但并不保证任意摘要都能提升表现。genui{"citation":{"ref":"turn4view1"}}

我的建议是：让状态更新以**新证据、假设撤回、产物变化**为触发条件，而不是固定每若干轮生成一次长总结。

**2．把错误定位升级成“错误生命周期”**

一个错误至少有三个不同时间：

\[
t_{\mathrm{introduced}},\qquad
t_{\mathrm{detected}},\qquad
t_{\mathrm{resolved}}.
\]

再加上是否残留后果，就能区分：

- 已修复且无残留；
- 已修复但浪费了大量预算；
- 未修复但与最终失败无关；
- 未修复并影响最终产物。

m4 的优化器问题属于非常好的样本：它是真实局部错误，而且被发现修复。不能因为整条轨迹最终失败，就将这次修复视为无效动作；也不能把它直接指定为终局失败根因。

这正是 TrajDebug 的主要推进：在识别错误之后，追踪其解决状态和终态影响，再筛选关键错误。其实验同时区分已知失败后的重做和向未见任务迁移失败记忆；论文报告后者在三个设置上提升约 **4.48—6.57 个百分点**，但这些是特定模型与基准上的结果。genui{"citation":{"ref":"turn3view5"}}

对你的系统，适合增加一个很小的记录单元：

> 错误/风险 → 原始证据 → 影响的决策或产物 → 修复事件 → 修复验证 → 残留不确定性。

这比给每一步打一个“好/坏分”更接近可用的控制信号。

**3．衡量协作是否产生了“有效增量”**

目前 `adoption` 不能承担这个角色。

我检查了 `ckpt-m2.json` 的事件样本：其中包含双方重复的任务阈值、文件名、协议命令等 n-gram。m3 统计为 677 个跨侧事件，m4 为 1471 个，**这些数量不能解释为知识采纳次数，更不能解释为贡献量**。共同输入可以产生同样的文字重合。

应当把一次候选贡献展开为：

\[
\text{新证据}
\rightarrow
\text{对方实际接触}
\rightarrow
\text{判断改变}
\rightarrow
\text{实现改变}
\rightarrow
\text{验证结果}.
\]

这些边有不同证据强度：

- 文件读取或工具调用证明“接触”；
- 显式引用证明“宣称依据”；
- diff 证明“实现变化”；
- 对照重放才能支持“结果增益”。

m3 中“揭示 L3DO 风险→接受修订→选择混合模型”就是可研究的链条。它比两个 agent 的聊天量、分歧数或文本相似度更有意义。

进而，协作多样性也应从**语言差异**改为**行为差异**：对相同输入预测是否不同、错误是否互补、相同证据是否导致不同选择。两个描述不同的方案可能行为相同；两个措辞相似的方案也可能在关键边界上完全不同。

**4．将审查与模型路由统一为“干预价值估计”**

轨迹前缀可以帮助选择下一步：

\[
u_t\in
\{\text{继续、复现、审查、换模型、换方法、分支、停止}\}.
\]

理想的决策依据是：

\[
\Delta(u\mid H_t)
=
\mathbb E[U(Y)\mid H_t,\operatorname{do}(u)]
-
\mathbb E[U(Y)\mid H_t,\operatorname{do}(u_0)],
\]

再考虑额外费用和时间。其中 \(u_0\) 是原策略继续运行。

**预测“可能失败”与判断“值得干预”是两件事。** 某些高风险状态已经无法挽回；某些看似正常的状态，却只需一次便宜的版本核验就能避免严重错误。

对这份实验，可提出具体触发候选：

- 成功声明没有对应执行事件 → 核验实际交付路径；
- 选择依据混用了不同验证协议 → 统一估计器重算；
- 共识建立在无法识别的响应上 → 保留备选并做决策敏感性测试；
- 长期重复拟合却没有新证据 → 更换实验问题或停止搜索。

EvoRoute 已将逐步执行经验用于动态模型选择，并联合考虑质量、费用、时延。可借鉴的是“状态条件下使用历史经验”，而从模型选择扩展到上述干预集合，是我针对你的系统提出的延伸。genui{"citation":{"ref":"turn2view1"}}

**5．让轨迹承担“实验设计”的作用**

对于科学任务，失败可能源于不可识别性，而非某个明显错误。

m4 已明确记录：公开硬件组合共线，某些响应无法判定。此时再多一次相同数据上的拟合，可能只是在不同先验之间移动。

设 \(h\) 表示竞争假设，候选实验 \(e\) 返回观测 \(y\)。普通信息增益是：

\[
\operatorname{IG}(e)
=
H(h\mid H_t)
-
\mathbb E_y[H(h\mid H_t,e,y)].
\]

但对 agent 更合适的是**决策信息价值**：

\[
\operatorname{VOI}(e)
=
\mathbb E_y\!\left[\max_d\mathbb E[U(d)\mid H_t,e,y]\right]
-
\max_d\mathbb E[U(d)\mid H_t].
\]

它追问：这个实验的结果，有没有可能改变最终选择？

应用到 microarch：

- 若某个未知系数怎么变都不改变候选排序，继续识别它的价值可能很低；
- 若某个未识别响应会翻转最优设计，就值得优先研究；
- 若无法获得新的真实标签，可以报告敏感性与稳健性，但不能声称已经验证真实响应。

这带来一个更深的设计方向：**从轨迹中识别“证据已经耗尽”的状态，避免 agent 把继续推理误当成新增信息。**

**6．把跨任务经验编译成可检验规则**

这两条轨迹能提炼出一些候选规则：

- 交付完成应绑定实际目标路径的产物 hash 和验证事件；
- 保存的最优拟合应在独立重拟合与实际导出产物上复核；
- 选择指标须声明训练内、折外及跨折聚合的区别；
- 模型选择与最终报告若复用同一组折，应记录选择偏差；
- 任务失败不能抹掉已验证的局部修复。

这些规则可以进入 prompt、工具包装器、轻量校验器或记忆检索，不必都靠微调。

GEPA 明确利用执行轨迹和自然语言反思提出、测试 prompt 更新，并保留互补候选；Agent Lightning 则提供执行与训练解耦、将轨迹转化为训练转移的路径。两者说明轨迹可以服务于不同优化层级，但不能把“能从轨迹学习”理解成“成功轨迹的所有步骤都应模仿”。genui{"citation":{"refs":["turn4view0","turn5view1"]}}

**五、针对你的系统，怎样把可能增益变成可验证结论**

我建议以“决策片段”作为分析单元，同时保留原始事件索引：

\[
D_j=
(\text{触发问题},\text{当时证据},\text{候选动作},
\text{实际选择},\text{产物变化},\text{验证},\text{成本}).
\]

优先验证以下四个假设：

| 假设 | 干预 | 有意义的验证标准 |
|---|---|---|
| 版本绑定能减少虚假完成 | 自动绑定声明、目标文件 hash、验证事件 | 旧产物交付率下降；额外时间可接受 |
| 定向审查优于泛泛互评 | 针对验证协议、候选选择和未识别因素组织审查 | 等预算下终态指标提高；同时统计误纠正 |
| 行为互补优于文字分歧 | 按预测分歧与错误互补性组织双侧探索 | 等总预算优于单侧加算力及原双侧方案 |
| 轨迹条件干预优于固定轮次 | 仅在可识别触发状态进行审查、复现或分支 | 计入监控成本后，提高成功率或降低成本 |

实验上有三个关键约束：

1. **分支时保持前缀一致，后缀允许自然演化。**

2. **在线判别器只能看到前缀。**  
   可以用完整失败轨迹做离线归因，但不能把后来才出现的隐藏 regret 或最终共识泄露给当时的调度器。

3. **以任务/独立运行作为统计单位。**  
   数千条事件不是数千个独立样本。重复随机运行并跨任务检验，报告配对差异、置信区间和全部成本；样本量由希望检出的改善幅度与试运行方差决定。

最新且与你的问题最接近的是 **AIDE²**。论文报告：外层修改 harness，内层在固定预算下执行任务，按独立于内层公开反馈的成绩筛选。其发现的机制包括策略级 bandit、周期性分支、有界上下文和条件触发的失败记忆。值得注意的是，论文通过重放发现一个所谓稳健选择惩罚**从未改变候选排序**；同时，其“改进后的 agent 是否更擅长继续自我改进”的实验仍不确定。它证明了这条路线可研究，也提醒我们必须验证机制是否真正改变行为。genui{"citation":{"ref":"turn12view0"}}

**5．我认为我们应把“轨迹”进一步分成两个相互连接的对象**

一个是行动轨迹：

\[
H_t=(o_0,a_0,\ldots,o_t).
\]

另一个是实验谱系：

\[
\mathcal G_t=(V_t,E_t),
\]

其中每个节点是一个可运行候选，边表示改进、修复、复现、组合等关系。m3 的混合模型有两个来源，因此严格说更适合用 DAG，而非只允许单父节点的树。

每个候选至少绑定：

\[
v=
(\text{产物 hash},\text{父候选},
\text{实验假设},\text{评测协议版本},
\text{公开结果},\text{成本},\text{证据索引}).
\]

这两个对象分别回答：

- 行动轨迹：为什么决定做这个实验？
- 实验谱系：这个实验实际产生了什么，继承了什么？

**只保存行动日志，难以评价产物进步；只保存最优产物，难以解释搜索过程。** 你现有的 Git、ledger、轨迹和 checkpoint 已经覆盖许多字段，主要缺的是统一关联和自动评测，而不是重新造一套庞大框架。

**6．由此可以得到一个非常有用的增益分解**

设截至成本 \(b\)，已产生候选集合 \(\mathcal C_b\)，最终选择为 \(\hat x_b\)，用预先定义的任务效用 \(U\) 评价：

\[
Q^*(b)=\max_{x\in\mathcal C_b}U(x),
\]

\[
G_{\mathrm{select}}(b)=Q^*(b)-U(\hat x_b).
\]

这里 \(Q^*\) 是**事后分析上界**，不能交给运行中的 agent。

它把能力分成：

- **搜索能力**：能否产生更好的候选；
- **选择能力**：能否从已有候选里选出好的；
- **交付能力**：最终提交的是否就是选定并验证的产物。

对当前数据，若 \(U\) 定义为“三项科学门槛全部通过”：

- m3 的候选上界为 1，最终也是 1；
- m4 的已保存候选上界为 0，最终也是 0。

因此，**m4 的首要问题不能仅靠换一个最终选择器解决**。而若研究连续指标，就能看到其后期修改损失了误差和排序性能。这两种评价都应保留，不能用其中一种替代另一种。

进一步可以画出四条随成本变化的曲线：

| 曲线 | 用途 |
|---|---|
| 当前产物的隐藏表现 | 观察退化和恢复 |
| 历史候选的事后最优表现 | 观察搜索是否仍在发现有效候选 |
| 仅依据公开证据选出的候选表现 | 测量选择策略 |
| 当前真实交付文件的表现 | 识别版本与收尾错误 |

它们比“累计工具调用数”“累计思考长度”更直接地衡量研究效率。

**7．这会怎样改变具体 agent 设计**

我最看好的不是固定增加审查轮数，而是以下三种可以独立实验的改动。

**第一，保存候选档案，并将公开代理的可靠性作为研究对象。**

候选没有赢得当前代理分数，也可以保留；淘汰时记录依据。评价应绑定数据划分、估计器、参数选择方式和产物版本。

m3 的 B 被严格留出暴露了风险，但真实隐藏 Top-1 很好；这不说明严格留出错误，而说明**代理之间的分歧本身携带不确定性，不能被包装成确定排序**。

**第二，按“策略和证据来源”分配探索预算。**

AIDE² 的策略级分支给了参考，但我们不必照抄其策略名称和固定间隔。你这里可比较：

- 沿当前最优候选继续优化；
- 从同一候选换建模假设；
- 让另一侧复现评估；
- 检验会改变最终决策的未识别因素；
- 保留互补候选并测试组合。

重要的是：候选档案保留行为差异，调度器根据轨迹决定下一份预算花在哪里。**多样性是需要成本约束的搜索资源，不是越多越好。**

**第三，将审查贡献拆成不同结果。**

例如 m4 的斜率审查至少可能有三种不同价值：

1. 消除函数边界上的不合理行为；
2. 改善公开交叉验证；
3. 改善最终任务表现。

**代理指标能不能改善最终成果？**

其中 \(s_t\) 只含当时可见信息；\(a_t\) 可以是拟合、修改、评估、组合、继续或停止；\(q\) 保留多维质量指标。隐藏评分只进入分析标签，不能倒灌进 \(s_t\)。

**联合优化首先应画出“随预算变化的可达质量”，而不是马上加权成一个总分。**

对每个时间点、每个累计成本，区分两个量：

- **已生成候选中的最好成绩**：衡量搜索是否产生了好东西，是事后上界。
- **当时选择规则会提交的成绩**：衡量 agent 能否识别好东西，才接近实际能力。

两者的差距就是**候选选择损失**。如果好模型早已出现，但最终没选中，应改选择机制；如果直到最后都没有好模型，应改实验生成或预算分配。继续增加推理长度，对这两种问题的作用完全不同。

对成本、时间和质量，我会报告 Pareto 前沿及三类约束比较：

\[
\begin{aligned}
&\min C &&\text{满足 }T\le T_0,\ q\in\mathcal Q_{\rm target},\\
&\min T &&\text{满足 }C\le C_0,\ q\in\mathcal Q_{\rm target},\\
&\max Q &&\text{满足 }C\le C_0,\ T\le T_0.
\end{aligned}
\]

本任务的 \(\mathcal Q_{\rm target}\) 就是三项评分门槛。没有你的资源偏好时，随意把“秒、token、误差”加权相加，会掩盖真实权衡。

另外，**并行任务的耗时不能简单相加**。减少一个不在关键路径上的实验，可能省钱却不缩短完成时间；增加并行分支可能更快却更贵。必须从事件依赖关系重建关键路径。

**具体如何从现有轨迹检验改进？**

我会依次处理三类干预，其证据强度不同：

1. **确定性节省：重复验证、无效执行、产物交付。**  
   检查同一模型、同一数据、同一测试环境是否重复计算；只有缓存键完全一致时才复用。测算实际省掉的调用与计算时间。已有统计表明，完全相同的 shell 命令重复不多，因此不能预设这里有巨大收益。

2. **候选选择与停止规则：做时间截断回放。**  
   在历史检查点，仅向规则提供当时已有的代理结果与候选；让它选择或停止，再用隐藏评分评判。报告“节省多少成本/时间、损失或改善多少质量”。  
   **不能用“第一次出现隐藏达标模型”直接当作停止规则**，那依赖在线不可见答案，只能作为节省空间的上界。

3. **改变后续研究路线：必须重新运行。**  
   如果规则会提前放弃 B、要求 A 做新实验，或者改变两者交流，那么历史后续已经不再适用。离线轨迹无法给出这条新路线的结果；需要从可恢复检查点继续，或做完整配对重跑。现有材料缺少完整环境状态，不能假装完成这种反事实实验。

代理指标的校准则重点统计：**错误接受率、错误拒绝率、候选排序错误，以及由这些错误产生的资源浪费**。相比一个整体相关系数，这些量更贴近你的优化目标。候选之间有祖先关系，不能把同一轨迹的十几个版本当作十几个独立样本。

就目前已有证据，我会把结论改写为：

**已经发现了“产物质量的剩余提升空间”；尚未测出“研究过程的净效率提升”。下一步最关键的实验是重建成本—时间—质量曲线，并分解候选生成与候选选择的损失。** 只有当某个仅使用当时可见信息的规则，在减少成本或用时后仍保持或提高最终质量，才能说我们真正改善了 agent，而不只是事后改善了它留下的模型。

\[

=
\underbrace{1-Q^*_{\mathrm{pool}}}_{\text{池内缺少正确答案}}
+
\underbrace{Q^*_{\mathrm{pool}}-Q_{\mathrm{final}}}_{\text{已有正确项未被选中}}.
\]

这里 \(Q^*_{\mathrm{pool}}\) 是逐簇择优的诊断上界，不能在线使用。

- **tumor-2：选择和候选生成都需要改善。** 共识过程丢失了已有正确判断，同时池内仍缺必要答案。

|---|:---:|:---:|

**1．AiiDA：最值得借鉴的成熟科研溯源架构**

[论文](https://arxiv.org/abs/2003.12476) · [代码](https://github.com/aiidateam/aiida-core)

AiiDA 的核心已经非常接近你的需求：把 **数据、计算、工作流及其连接关系**持久化，支持查询、执行恢复、计算缓存和溯源导出。尤其有价值的是，它明确区分：

- **Data provenance**：什么输入经什么计算生成什么输出。
- **Logical provenance**：为什么选择该输入、为什么调用该计算。

前者构成 DAG，后者不要求无环。这恰好对应我们需要区分的“产物生成过程”与“研究决策过程”。genui{"citation":{"refs":["turn4view0","turn5view0"]}}

代码建议从这些位置读起：

- [`src/aiida/orm/nodes/`](https://github.com/aiidateam/aiida-core/tree/main/src/aiida/orm/nodes)：节点、连接、属性和缓存。
- [`caching.py`](https://github.com/aiidateam/aiida-core/blob/main/src/aiida/orm/nodes/caching.py)：哪些对象参与身份计算、缓存来源如何记录。
- [`src/aiida/engine/`](https://github.com/aiidateam/aiida-core/tree/main/src/aiida/engine)：执行与恢复。

**对我们最直接的启发：把一次“选择候选”也保存成过程节点。** 这样不仅知道最终提交了什么，还知道当时有哪些候选、依据什么证据选择、使用了哪个规则版本。

边界是：AiiDA 擅长计算溯源；“某个结论是否可信”“两个科学判断冲突如何处理”仍需要上层语义。也不必为了借鉴其数据模型，立即接管整个执行框架。

**2．Mandala：与你设想最贴近的计算对象模型，尤其值得精读**

[论文：Compositional Memoization](https://amakelov.github.io/scipy-mandala.pdf) · [代码](https://github.com/amakelov/mandala)

它以**函数调用**作为保存、查询、版本与复用的基本单位，并用 `ComputationFrame` 把大量实验组织成可查询的计算图。论文里有一个特别值得吸收的设计：

\[
\text{content ID}\neq\text{history ID}.
\]

- **content ID**：内容是否相同，用于去重和复用。
- **history ID**：内容是经哪条计算路径产生的，用于保留来源。

两个实验都输出相同数组，可以共用物理存储，但仍保留不同的研究历史。genui{"citation":{"ref":"turn6view1"}}

我核对了 [`mandala/model.py`](https://github.com/amakelov/mandala/blob/main/mandala/model.py)：`Ref` 确实同时保存 `cid`、`hid`；`Op` 分别计算调用的内容身份与历史身份。

这个区别对我们的多 agent 实验很重要：

> **相同答案不等于独立证据；不同执行也不意味着必须重复保存相同产物。**

不过，Mandala 的 README 仍标明 alpha，并提示较大调用集合的性能瓶颈。因此我会**优先借鉴其模型与查询思想，暂不直接把它当作整个科研系统的生产底座**。genui{"citation":{"ref":"turn4view5"}}

**3．redun：最值得做小规模接入实验的执行与缓存底座**

[代码](https://github.com/insitro/redun) · [设计文档](https://insitro.github.io/redun/design.html)

redun 通过 Python 任务构建动态计算图，记录调用历史，支持并行执行、缓存与增量重算。它适合将现有训练、评分、转换和验证脚本逐步包起来。genui{"citation":{"ref":"turn2view0"}}

我查看了 [`redun/backends/db/__init__.py`](https://github.com/insitro/redun/blob/main/redun/backends/db/__init__.py)，其中明确分开：

| 对象 | 作用 |
|---|---|
| `Value` | 内容值及其身份 |
| `CallNode` | 任务、参数、结果之间的关系 |
| `Job` | 某一次执行，含起止时间、缓存状态 |
| `Execution` | 一次完整运行 |
| `Tag / TagEdit` | 元数据及其修改关系 |

**这比“每个产物挂一个 token 总数”更适合成本研究。** 同一结果可以被多个运行复用，但执行次数、缓存命中与实际资源消耗仍分别记录。

需要仔细处理其缓存边界：官方文档明确指出，普通辅助函数的修改未必自动触发重算；默认文件身份也可能使用路径、大小、修改时间，而非完整内容哈希。接入科研验证时，应显式绑定代码、环境、数据摘要和随机性设置。genui{"citation":{"ref":"turn5view1"}}

对于重复随机实验，还必须区分：

- **复用旧结果**；
- **新增一次独立重复**。

缓存命中不能增加有效样本量。

